# DocRepo specification

This file describes what DocRepo does and how it's built. It grows phase by phase (see `PROGRESS.md`): sections for finished phases are complete, and later ones are summaries. The hard rules are in `.github/copilot-instructions.md` and apply to everything here.

## 1. What DocRepo is

A Windows desktop tool for someone who manages many projects at once. Information arrives all day as emails, quick notes and documents, many of them on a shared LAN drive. DocRepo lets its owner capture any of it in seconds and organize it as a tree of tasks, where projects are the top-level tasks.

- **Capture app:** runs in the background with a tray icon. A global hotkey opens a small capture window.
- **Browse tool:** a separate window for the task tree, lists, agendas, capacity, people, labels, documents, search and settings (section 8).
- **Capture first.** Every capture is saved at once, with no AI involved. DocRepo never calls an AI. Its Copy prompt button builds a prompt for the owner to paste into an AI chat, and the answer is pasted back as text.

## 2. How it's built and installed

- Developed on the owner's personal computer, in Python 3.12 with PySide6, and published to a public GitHub repo, https://github.com/eckertco2/DocRepo.
- On the corporate computer, the owner downloads the repo, makes a `.venv` and runs `pip install -r requirements.txt`. That computer's pip settings fetch the packages from the company's package repository. DocRepo's code never refers to it.
- No packaging into an .exe. DocRepo runs as `python -m docrepo` from its folder.
- `README.md` has the steps for installing and updating.

## 3. Data root and settings (phase 1, built)

### Where the data root is
DocRepo keeps all its data in one folder, the **data root**, on the local drive. It must not be inside a OneDrive folder, and for real use it must be outside DocRepo's code folder, so updates never touch it.

DocRepo picks the data root from, in order:
1. `--data-root PATH` on the command line (for development and tests);
2. the `DOCREPO_DATA_ROOT` environment variable;
3. `%LOCALAPPDATA%\DocRepo\location.json`, which holds `{"data_root": "<path>"}` and is written by `set-data-root` or the browse tool's Settings view (8.9).

### Folders
`init` creates `Captures`, `Tasks`, `Documents`, `Mods`, `Config\prompts` and `System\logs` in the data root, plus `Config\settings.json` and the database, `System\docs.db`. Other folders, such as a task's `Files`, appear only when needed.

### settings.json

| Field | Meaning | Default |
|---|---|---|
| `schema_version` | Format version of this file | 1 |
| `me` | The owner's person ID, such as `P001` | none |
| `hotkey` | The capture window's hotkey | Ctrl+Shift+Space |
| `browse_hotkey`, `note_hotkey`, `new_task_hotkey`, `update_hotkey`, `agenda_hotkey`, `today_hotkey`, `pin_hotkey`, `outlook_hotkey` | More hotkeys (7.1): the browse tool, each capture type, Add to agenda, a quick task on Today, Pin (release 5.17), and the email selected in Outlook (release 5.33.1) | empty, so off |
| `backup_dir` | The backup folder | none |
| `backup_every_days` | How often a backup is made, in days (9.1) | 7 |
| `backup_keep` | How many copies of docs.db the backup folder keeps | 8 |
| `doc_check_minutes` | How often tracked documents are checked for changes | 60 |
| `reminder_time` | When each day's reminders are shown | 08:00 |
| `extracted_text_cap_chars` | Most text kept per extracted file | 200000 |
| `prompt_warn_chars` | Copy prompt warns above this length | 60000 |
| `capacity_horizon_years` | How far ahead routine tasks fill the capacity calendar | 5 |
| `workdays` | Days the capacity calendar spreads hours over | Mon to Fri |
| `event_words` | Words Parse and populate reads as events, for deadlines | turnaround, shutdown, audit, inspection, outage, walkthrough |
| `reference_fields` | The reference fields' names (6.3, release 5.9), such as a change record's number. The code names none | none |

| `show_hints` | Show hints: help text, the **i** buttons and key badges, in every window (section 11) | false |

| `outlook_category_colour` | The colour a category gets when DocRepo puts it on Outlook's list of categories (release 5.33.1, 7.5): one of Outlook's 25 colours, or None to leave the list alone | Teal |

A missing file gives the defaults. An unreadable file stops DocRepo with an error; it's never overwritten silently. Unknown fields are ignored with a warning in the log.

## 4. Guarded writes (phase 1, built)

`docrepo/safe_fs.py` is the only code that writes, copies or moves files, or creates folders.

- **Allowed places:** the data root, the backup folder (if set) and `%LOCALAPPDATA%\DocRepo\`.
- **Checks on every path:** it must be a full path with a drive or a `\\server\share`. Device paths (`\\?\`, `\\.\`), alternate data streams, names ending in a dot or space, characters Windows forbids and reserved device names (CON, NUL, COM1 and so on) are refused. The path is then resolved through `..`, symlinks and junctions, and must land inside an allowed place.
- **Writing:** `write_text` writes only `.md`, `.json`, `.txt` and `.log` files, as UTF-8, atomically (a temporary file in the same folder replaces the target).
- **Pictures:** `write_picture` (release 5.27, decision 127) writes a picture the owner pasted, as a `.png` file only, atomically, and never over a file that's there.
- **Copying:** `copy_file` copies a file the owner asked to keep. It only reads the source, and never overwrites.
- **Moving:** `move` moves only from one allowed place to another, and never overwrites.
- **Replacing:** `replace_file` (copy over) and `replace` (move over) work only inside a SafeFS's replace roots. `make_safe_fs` makes the backup folder the only one, and none when the backup folder is inside the data root or holds it, so a backup can bring its copies up to date (9.1) while nothing in the data root is ever overwritten by a copy.
- **The Startup shortcut:** `DocRepo.lnk` in `%LOCALAPPDATA%\DocRepo\` is written by Windows' shell, to a path `checked_path` allows (9.2).
- **No delete function.** Every refusal is logged.
- Code that writes on its own (SQLite, the log, Outlook's SaveAs) gets its path from `checked_path` first.

## 5. Command line (phase 1, built)

`python -m docrepo [--data-root PATH] COMMAND`

| Command | What it does |
|---|---|
| `where` | Shows the data root, what chose it, and whether it's set up. |
| `set-data-root PATH` | Records the data root in `location.json`, after checking it isn't in OneDrive or the code folder. |
| `init` | Creates the data root's folders, default settings and database, and starts the log. |
| `try-write PATH` | Writes a small test file at PATH if DocRepo is allowed to, to check the guard. |
| `load-sample [--as-of WHEN]` | Fills a new, empty data root with the made-up sample data (section 6.10). Refuses a database that holds anything. |
| `rebuild [--as-of WHEN]` | Rebuilds the capacity calendar and every generated page from `docs.db`, and the search index from the capture and document files. |
| `report [--as-of WHEN] [--week DATE]` | Prints what DocRepo works out: capacity for 9 weeks, days until due, the lists, labels and parent chains, raw text logs and agendas. |
| `app` | Starts the capture app (section 7). Use `pythonw` instead of `python` for no console window. |
| `browse` | Opens the browse tool (section 8), starting the app first if it isn't running. |
| `backup` | Makes a backup now (9.1). |
| `make-shortcut` | Makes `DocRepo.lnk`, the Startup shortcut, in `%LOCALAPPDATA%\DocRepo\`, and says where to move it (9.2). |
| `set-hotkey KEYS` | Sets the capture window's hotkey, such as `"Ctrl+Alt+Space"`. It needs Ctrl, Alt or Win. Takes effect when the app next starts. The browse tool's Settings view does the same, at once. |
| `outlook-check` (or `troubleshoot`) | Makes the troubleshooting report (9.4), without the capture window's drags and pastes, prints it and saves it in `System\diagnostics`. |

`--as-of` takes `YYYY-MM-DD` or `"YYYY-MM-DD HH:MM"` and makes the command work as if it were then. It's for testing.

DocRepo's log is `System\logs\docrepo.log` in the data root, rotated at 1 MB with 5 old files kept. It records IDs, file names and actions, never captured content. The app logs any error nothing caught, with its traceback, and says so once in a notification (under `pythonw` it would otherwise vanish).

## 6. Data model (phase 2, built)

The words used here are defined in `GLOSSARY.md`.

### 6.1 The database
- `System\docs.db`, SQLite, is the source of truth. Folders never encode the task tree: task folders are named by ID only, and nothing moves when a task is renamed or gets another parent.
- `docrepo/db.py` creates the schema and keeps its version in SQLite's `user_version` (now 18). An older DocRepo database is brought up to date when it's opened (version 2, phase 3: each document's text status, size, modified time and checksum, plus `app_state` and `reminders_shown`; version 3, phase 4: the search index, `search_text`; version 4, release 5.3: `discarded` and `discard_reason` on tasks and captures, and `agenda_items` made again, keeping its rows, so an item can close as Done; version 5, release 5.4: `email_layer_0` on captures; version 6, release 5.7: `formatted` on captures; version 7, release 5.8: `from_notes`, `item` and `meeting` on captures; version 8, release 5.9: `email`, `person_group` and `role` on people, `parent` on labels, `plant_event` on tasks, and `task_references`; version 9, release 5.23: `priority` and `priority_rank` on tasks). A database from a newer DocRepo, or one that isn't DocRepo's, is refused rather than changed. Version 10 (release 5.25): `task_pages` (each task's notes page), `task_page_versions` (the page as it stood at the end of each day it changed, when the owner last edited it that day, and whether they did), tasks' `day_headings`, and the search index made again with pages in it. Version 11 (release 5.27): `page_made` on captures, for a picture pasted or a file dropped on a notes page (6.11). Version 12 (release 5.31): `task_dates`. Version 13 (release 5.35): `document_uses` and `task_pins`, for the Task view (8.10). Version 14 (release 5.44): the tables of task templates (6.12). Version 15 (release 5.45): `template_log`, a template's Changes list. Version 16 (release 5.46): `duration`, `calendar_days`, `lead_per_day` and `assignee_per_day` on tasks and template rows (6.13). Version 17 (release 5.47): `involvement` on `task_people` and `template_row_people` (6.14). Version 18 (release 5.49): `lead_per_week` and `assignee_per_week` on tasks and template rows (6.13).
- Foreign keys are on. Every change runs inside one transaction, so a save happens completely or not at all.
- The tables:

| Table | Holds |
|---|---|
| `tasks` | Each task's fields (6.3). |
| `task_parents` | Parent links, oldest first. A task can have several parents. |
| `task_people` | Each task's leads and assignees, in order, with each one's Involvement (release 5.47, 6.14). |
| `task_labels` | Each task's own labels. |
| `task_references` | Each task's reference field values, by the field's name (6.3, release 5.9). |
| `task_dates` | Each task's key dates (release 5.31, schema version 12): a start, an end or both, a description, ticks for a plant activity and a hard deadline, the day it was done, and its place in the task's order. |
| `people`, `person_aliases` | The people list (6.4), with each person's email, group and role (release 5.9). |
| `labels`, `label_keywords` | Labels, each with the label it's under, if any (release 5.9), and the keywords Parse and populate looks for. |
| `status_log` | Field changes (6.6). |
| `captures` | Each capture: when it was saved, its source, capture types, picked task, created task, filing, title, summary, whether its content text is formatted, and for release 5.8's items and meeting notes, the notes an item came from, what it is (task, note, update, decision, or `notes` for a meeting's notes) and the meeting the notes made. Its content text is in its `capture.md`. |
| `documents`, `capture_documents`, `capture_attachments` | Documents (tracked originals and email attachments), and each capture's files with their Save a copy and Extract information choices. |
| `document_versions` | Changes found in tracked originals, with any pasted summary. |
| `saved_copies` | Copies in a task's `Files` folder, and replaced ones in `_old versions`. |
| `agenda_items` | Agenda items (6.7). |
| `work_calendar` | The capacity calendar (6.8). |
| `id_counters` | The last ID handed out of each kind. |
| `search_text` | The search index: each capture's and document's text (8.8). A cache, rebuilt by `rebuild`. |
| `document_uses` | What the owner did with a file from DocRepo: opened it, showed it in File Explorer, or copied its path or link, with when and from which task (release 5.35, 8.10). |
| `task_pins` | Each task's pinned files, its key documents, in the owner's order (release 5.35, 8.10). |
| `templates`, `template_rows`, `template_row_people`, `template_row_labels` | Task templates and their rows (release 5.44, 6.12). |
| `task_template`, `task_links` | Which row a task was made from and its tree's top task, and the fields still following that row (release 5.44, 6.12). |
| `template_log` | A template's Changes list: one line a save, in its words as they stood (release 5.45, 6.12). |

### 6.2 IDs
- Tasks `T000001`, captures `C000001`, documents `D000001`, people `P001`. Mods log entries are `M0001` (phase 3).
- IDs count up and are never reused, even if a record were removed.

### 6.3 Tasks
- **Fields:** title, state, current status, description, start, due, deadline and its description, reminder, recurrence and repeat until, urgent, meeting, plant event (release 5.9), priority (release 5.23), leads and assignees, lead hours and assignee hours, labels, inherit parent labels (on by default), created (the day), created by (the capture that created it, or "Excel import"), and its reference fields (release 5.9).
- **States:** Not started, In progress, Parked, Closed. Closed means done or cancelled. Closing records the day it closed; reopening clears it. Open means Not started or In progress.
- **Start** defaults to the day the task was created.
- **Recurrence:** Daily, Weekly, Bi-weekly, Monthly, Quarterly or Yearly. A task with one is a routine task. Repeat until can be set only with a recurrence, and clearing the recurrence clears it. Closing a routine task ends the recurrence.
- **Hours** are per person in the role: a total for a one-time task, per occurrence for a routine one. Every lead gets the full lead hours and every assignee the full assignee hours; someone in both roles gets both.
- **The tree:** a task with no parent is a top-level task (a project). A task can have several parents and shows under each. A link that would put a task under itself is refused. Ancestors are every chain upward, without repeats; a chain runs from a top-level task down to the task.
- **Scopes:** this task, with ancestors, with subtasks (descendants), and family (ancestors and descendants).
- **Labels:** a task's own labels come first, then every parent's labels (their own and inherited), unless the task's inherit switch is off.
- **Discarded** (release 5.3, M0021): a task made by mistake can be discarded, with a reason. It keeps its state and everything else, but it's hidden from the task tree, the lists, the counts, the pickers, search, the capacity calendar and `Contents.md`, and kept in the browse tool's Discarded view. Bringing it back clears `discarded` and `discard_reason`. Both go into the status log as "Discarded" (the reason, or None when it's brought back). Nothing is deleted.
- **Key dates** (release 5.31; the design workspace's key dates plan, decisions 146 to 155; `docrepo/key_dates.py`, `tasks.set_key_dates`): any number of dated line items on a task, beside its own Start, Due and Deadline, which still drive the lists, Today, reminders, Capacity and the timeline's bar. Each has a start, an end or both (a start alone is a beginning, "from"; an end alone a target, "by"; both a window; one day at both ends a milestone, "on"), an optional description, and three ticks: **Plant activity** (it's a plant event of its own: the timeline's lane and band, and the "falls during" lines), **Deadline** (a red diamond at its end) and **Done** (the day it was ticked). Every change is in the status log ("Key date added: …", "Key date changed: …", "Key date taken off: …", "Key date done: …"), a new order alone not. They carry no hours. An open key date with an end is due on it on Today and the Overdue and next 7 days list, each a row of its own, and overdue once passed; one with only a start shows from a week before it starts and is never overdue. Done ones stay on the task page and the timeline, grey. They're typed in a capture as a `**key date,` line (release 5.38; `**key date, Dec 1 to 5 trial execution window, plant activity.`, `**key date, by Nov 25 target for trial preparations, deadline.`, `**key date, from Oct 1 trial planning period.`; `items.read_key_date`, its rules in the test vectors' "Quick input"), which goes on its `#` task, the task item it's under, or the capture's task, makes no capture of its own and keeps its line in the notes; or in the capture window's Key dates rows for New task and Update (Update's start as the task's own). They're entered in Edit task's Key dates section (a line each: Start, End, Description and the three ticks; moved up and down, removed, Add key date; a line needs a start, an end or both, and its end can't be before its start) and Quick edit's compact one (removed and added only), shown on the task page under When (Done ticked there, done ones grey, Make it a subtask), and on the Overdue and next 7 days list (under a Key dates heading) and Today's Due in the next 7 days, a row each with Done, counted in the sidebar, Mine only filtering by the task's people. **Make it a subtask** makes a key date a subtask of its task, its dates its Start and Due (a Deadline when ticked as one, Plant event when a plant activity, closed when done), and takes it off. Task.md has a Key dates section.
- **Plant event** (release 5.9, M0028, decision 22): a tick box for an outage, a turnaround or the like. The timeline shades a plant event down the whole chart from its Start to its Due (or Deadline), whatever the filters, and since release 5.29 shows it in a lane of its own under the scale, and the capacity view names it over its weeks; where dates are picked (New task, Update, Edit task), a line names a plant event they fall in, such as "Start and Due fall during Spring outage, Tue 3 Nov to Sat 14 Nov." (`timeline.during_text`; a task's own event doesn't count). It's ticked by hand, in Edit selected, by `**event,` (6.5), or by Parse and populate from "plant event" or "major event" (7.3, release 5.18); the event words alone never tick it.
- **Reference fields** (release 5.9, M0034, decision 20): numbers from other systems, such as a change record's. Their names are entered in Settings (`reference_fields`), so the code names no company system. A task has a value for each field, or none (`task_references`); a change goes into the status log under the field's name. Taking a name out of Settings takes its boxes away, and values a task already has still show.
- **Priority** (release 5.23, M0029, M0030, decision 23; `docrepo/priorities.py`): a bucket, Critical, High, Medium or Parking lot, with a place in it (`priority_rank`), or none: Not ranked. A move to another bucket goes into the status log as Priority ("Ranked Critical.", "Priority moved to High.", "No longer ranked."); a move within a bucket doesn't. Urgent stays a flag of its own, and Parking lot isn't Parked: it's an open task ranked lowest. Rows show the priority only when it's Critical, beside Urgent; the task page, the Priorities board and Edit task show every bucket, and `Task.md` has a Priority row when it's set.
- `docrepo/tasks.py` creates and changes tasks. Each change goes into the status log, and the task's capacity calendar rows are rebuilt in the same transaction.

### 6.4 People and labels
- Each person has a name, aliases, hours a week (or not set), a status, active or retired, and (release 5.9, M0031, M0033, M0038) an email address, a group and a role, each optional. DocRepo only keeps the address: it never sends email or opens a mail link. A person is in one group at most (decision 19), picked from the groups already used or typed new. Task roles and the calendar store the ID, so renaming someone changes nothing else. One person is me: `me` in `settings.json`.
- Labels have a name (unique, any case), keywords (the name, if none are given) and a status. Renaming a label keeps it on its tasks.
- **Nested labels** (release 5.9, M0051, decision 21): a label can be under a parent label, one level only, so a parent label isn't under another and a label with labels under it can't go under one. A parent label is a heading that tasks don't get on their own: the label pickers show a sublabel as "Production line › Line 1", found by either name, and never offer the parent. Keywords and Find matching tasks stay per sublabel.
- Retired people and labels are hidden from pickers and lists, never deleted.

### 6.5 Captures and documents
- A capture belongs to the task it created; to the task it picked, unless it only made a subtask there (New task without Update); and to the task it was filed to. A capture with no task and no agenda item is unfiled, and waits in the Unfiled view.
- A capture is listed by an email's subject, or else the first sentence of its content text (without email header lines and file path lines, cut at 100 characters), or else its first file's name. Full stops after abbreviations such as "Dr." and "Oct. 19" don't end a sentence.
- A document belongs to the tasks of the captures it came in with, and to the tasks it has saved copies in. Its document versions join the raw text log of each of those tasks.
- **A link** (release 5.4, M0001; `docrepo/links.py`) is a document whose original is a web or SharePoint address (http or https, no spaces), matched exactly rather than in any case. DocRepo keeps only the address: it never fetches a link, so a link has no extracted text (`text_status` none) and no saved copy, and it never opens one; Copy link puts it on the clipboard (round 1 plan, decision 5). It's listed by the file its address names (SharePoint's `file=`, else the path's last part, such as "Pump spec.docx"), else by its host. A capture whose only files are links is typed, not file_path.
- `capture.md`: front matter whose values are JSON (also valid YAML), then the content text, then a "Summary" section if a summary was pasted. The fields, in order: `id`, `saved`, `source` (typed, outlook_email or file_path), `task` (the picked task, else the task it was filed to, else null), `capture_types` (note, new_task, update), `filed`, `edited`, `created_task`, `changes` (field, from, to), `agenda` (subject and target of each item it added), `documents` (id, name, original, description, save_a_copy, extract), `email_layer_0` (release 5.4: what email layer 0 kept from an email and what it left out, 7.5), `content_format` (release 5.7: "markdown" when the content text is formatted), `meeting` (release 5.8: the meeting the notes made), `items` (the captures of the items they made), `from_notes` (an item's notes), `item` (what it is) and `summary_type`. `filed`, `edited`, `created_task`, `changes`, `agenda`, `email_layer_0`, `content_format`, `meeting`, `items`, `from_notes` and `item` appear only when they apply.
- **Formatted content text** (release 5.7, M0045; `docrepo/markup.py`): content text with any formatting or list is kept in `capture.md` as a small, readable piece of Markdown, one block per line: `**bold**`, `*italic*`, `~~strikethrough~~`, `<u>underline</u>` and `<mark class="yellow">highlight</mark>` (yellow, green or pink); a list item is two spaces a level, then `- ` or a number and `. `; any other line is a line of text. A backslash keeps `*`, `~` and `<` as themselves, and `-` or `1.` at a line's start, so a line of text that starts like a list item stays text; a backslash before anything else is just a backslash, so paths read as they are. An email's text in a formatted capture is escaped that way, so it reads back exactly. Content text with no formatting is kept as plain text, as before, with no `content_format`. Whatever reads content text for its words (the title, a new task's description, Parse and populate, an agenda note, search) reads the markup without its marks (`markup.to_plain`); list items keep their `- ` and numbers. Copy prompt sends the markup itself: an LLM reads Markdown. **Checklist lines** (release 5.26, decision 86): a list item whose text starts with a box, `- [ ] ` or `- [x] ` (`markup.CHECK`, `check_of`), shown as Qt's list item with a box (`<li class="checked">`), a ticked one's words grey; `to_plain` keeps the box as text. A checklist line's `@` names stay names: it never makes a task item (decision 87, `items.read`), and it's never a new task's description. **Headings** (release 5.28, the mods log round 4): `# `, `## ` or `### ` and the heading's words, kept as typed without marks, as on the notes page (`markup.HEADING`, `heading_of`); a line of text that would read as one starts with a backslash (`escape_heading`, `text_of`). `to_plain` gives a heading's words alone, so `#Rigging plan` on a heading line is still an item's `#`; pages show a heading as Qt's, a step larger than the text, and the raw text log in bold.
- **Items** (release 5.8, M0048 phase 2, M0049, M0052; `docrepo/items.py`): in any capture, a block of the content text with an operator becomes an item: a task, a note, an update or a decision. Operators are read from the content text's words (never an added email), and only after a space, a "(" or a line's start, so an address such as tom@example.com stays text.
  - `@Tom` or `@Tom Becker` (a name or alias, the longest that fits; a word that isn't on the people list is a new person): a task, with Tom an assignee, several allowed. `@L.Tom`: a task, with Tom its lead. `@__`: a task with no one yet. A task has no lead without `@L.`.
  - `#Rigging plan` or `#T000012`: a link to that task, only when it names one (by title or ID), so "Pump #3" stays text. With no `@` or `**`, the block is a note on it. A line that's only `#` tasks is a **heading**: it covers the lines under it until the next heading, and the plain lines under it are one note on its task. A note naming only the capture's own task (a Note's or an Update's picked task) makes no item: its lines are already the capture's note on it (release 5.32, the knowledge base's decision 28).
  - `**name,`, then the rest (release 5.38, the design workspace's quick input plan, decisions 200 to 209): every `**` name comes from one table, `items.OPERATORS`, and isn't case-sensitive. An entry says either what a line is or which field it fills. Adding a parameter that's a field `tasks.update_task` knows is one entry there, and its match in the mockup's `items.js`.
  - **What a line is:** `**t,` or `**task,`, `**n,` or `**note,`: a task or a note, said outright. `**closed,`, `**done,`, `**parked,`, `**in progress,`, `**started,` (and the quick update's other state words): an update to the `#` task with that state, the rest its current status; `**u,` or `**update,`: an update with no state change. `**decision,`: a decision. `**event,` (release 5.9, decision 22): a task with Plant event ticked, such as `**event, Spring outage, 3 to 14 Nov.`; the end date its own name made a Deadline is its Due, so it runs from its Start to its Due. A task item whose block says "plant event" or "major event" is one too, and `**event,` on a New task's own first line ticks the new task's Plant event (release 5.18, M0059). These take their whole line and the list items under it. With nothing to say they need no comma: `#Rigging plan **closed.`
  - **A parameter:** one sentence fills a field: `**due, 5 Nov.`, `**lead, Tom.`, `**key date, trial window from 1 Nov to 5 Nov 2027, plant activity.` The names: start, due, deadline (the words after its date are its description), deadline description, reminder, repeat until, key date, lead, assignee, lead hours, assignee hours (or hours), title, description, status, state, priority, recurrence, urgent, plant event, meeting (yes or no), label, parent, and each reference field in Settings, with or without its "#" or "no.". The sentence ends by the sentence rules ("Nov. 1" doesn't end it) or at the line's end, the words after it stay in the notes, and several can share a line. It's for input: a filled field on an existing task stays, and its card says so; a list (key date, lead, assignee, label, parent) adds; on a task being made in this capture, a new task or a task item, the line's value is used, even over the form. Each makes a card, with no capture of its own, and its line stays in the notes. It goes on the nearest of: a `#` task in its sentence, the task item on its line, a `#` task on its line, the task item it's listed under, the new task it's listed under, a `#` above, the capture's task. A window's start takes its end's year when only the end has one ("1 Nov to 5 Nov 2027").
  - **What can't be read:** a name not in the table, a sentence that can't be read, or an old form such as `**Closed. Mike confirmed` or `**date Dec 1` makes a card that can't be ticked, saying what's wrong or what to write. The line stays in the notes, Save goes ahead, and its message says how many lines weren't used. Saved captures are never read again for operators, so old lines stay as written, and what they made stays. `**` and a space is never an operator. A `**` type wins; else an `@` makes a task; else a `#` alone makes a note.
  - **A block** is a line, with the list items under it that have no operator of their own; a list item under it with an operator is a block of its own, and a task item listed under another task item becomes its subtask. With New task checked, the first line is the new task itself: its `@`, `@L.` and `#` fill its own assignees, lead and parents.
  - **Where an item goes:** a task under the capture's task (or the meeting, or the new task) and under each `#` task (the `#` of its parent block or heading when it has none of its own); with neither, under Quick tasks. A note, an update or a decision goes on each `#` task, else on the task item it's listed under, else on the capture's task; with none, it stays in the notes.
  - **Its title** is its line without the operators: one at the line's start or end goes, one inside a sentence keeps its name ("Ask Tom about the seal"; a task by its title), one ending the line after "with", "for", "see" and so on stays ("done with Mike"), and "to", "will" and the like after a leading name go ("@Sam to book the scaffolding" is "Book the scaffolding"). A task's dates, hours, labels and Urgent are read by Parse and populate from its block; its people come only from its operators. Its description is its block without its own line's operators.
  - **Each item is a capture of its own** (`from_notes` the notes, `item` its kind), with its block as written in its capture.md. A task item creates its task; a note, an update (through the status log, under the item) or a decision is filed to each of its tasks. Editing the notes later doesn't change items already made.
  - **IDs in capture.md** (M0049): each `@` and `#` is kept as `@[Tom Becker](P003)`, `@L.[Priya Shah](P002)` or `#[Rigging plan](T000012)`, so renaming a person or a task never breaks it. Everything that shows or reads the text shows `@Tom Becker` (`items.unstore`); titles read the words without the operators (`items.words`).
- **A discarded capture** (release 5.3, M0021) leaves its tasks' raw text logs, summaries and files, the Unfiled view and search, and is kept in the Discarded view. Its folder and `capture.md` aren't touched, and changes it made to tasks stay in their status logs. A document that came in only with discarded captures leaves the Documents view too.
- Phase 2 provides these records and the file format. Saving captures comes in phase 3.

### 6.6 The logs
- **Status log:** each field change, with when, the field, its old and new values as shown, and where it came from (a capture's ID, or "Browse tool", "Capture window", "Agenda view", "Reminders list", "Today"). In `Task.md` each entry stays on one line, so a value with line breaks, such as an edited description, is shown with spaces. Agenda items add their own entries: "Agenda: None → *target*" when one is added and "Agenda: *target* → Discussed" (or Removed) when it's closed.
- **Raw text log:** the task's captures and its documents' versions, oldest first. Since release 5.25 the browse tool lists it as Captures, and Task.md under Captures.
- **Summary log:** pasted summaries from the task's captures and from its documents' versions.
- **Files:** the task's saved copies (and replaced ones), then the documents of its captures: tracked originals, links and email attachments. `Task.md` shows a link's address as code (`` - Link: name · `address` · D000042 ``), not as a link to follow.

### 6.7 Agenda items
- An agenda item puts a task (its subject), or a note with no task, on the agenda of a target: a meeting, another task or a person. A task can't be on its own agenda.
- It stays open, carrying over, until it's closed by hand as Discussed or Removed. Closing an item never closes its task.
- A target's agenda is its open items. The agenda targets are the open meetings (tasks with Meeting checked), then any other task or person with open items.
- **Today** (release 5.3, M0016) is a built-in target, stored as `today`: the owner's list for the day. Its items carry over until they're closed as Done (or Removed); other targets' items close as Discussed or Removed. A task is on Today at most once. The status log says "Added to Today.", "Done for today." and "Taken off Today.", and `Contents.md` lists Today first under Agendas, with "since" and the day an item carried over from. Today isn't one of the agenda targets above: it has a view of its own.

### 6.8 Dates, lists and the capacity calendar
- **Windows:** a one-time task works from Start to Due, or to Deadline if there's no Due; with neither, it's unscheduled. A routine task's first window runs from Start to Due, or is just the Start day, and repeats every interval until Repeat until, the horizon (`capacity_horizon_years` from today) or the day it closed. Monthly, quarterly and yearly repeats keep the day of the month, or use the month's last day; 29 February becomes 28 February.
- **Days until due** uses Due, else Deadline. A routine task counts to the end of its next occurrence. Closed tasks have none.
- **Lists** (open tasks only, soonest first): Overdue and next 7 days (not routine tasks), Reminders (a reminder in the next 7 days or past), Waiting on others (assignees, none of them me), Assigned to me, Urgent, and No dates or hours (people, but no hours, or hours but no Due or Deadline on a one-time task).
- **The capacity calendar** (`work_calendar`) has a row per person, day and task. For each window and person, the hours are spread evenly over the window's workdays (`workdays` in settings, Monday to Friday by default); a window with no workdays spreads over its calendar days. Parked tasks and tasks with no hours have no rows, and a closed task has none after its close date. Not started tasks count.
- It's a cache: rebuilt for a task whenever that task is saved, for everything by `rebuild`, and (from phase 3) for all routine tasks at the first start each day, so the horizon rolls forward. It always shows the current plan, past weeks included.
- **Unestimated** tasks have people but no hours; **unscheduled** ones have hours but no dates. Both are open tasks the calendar can't place.

### 6.9 Generated pages
- Every task gets `Tasks\<id>\Task.md`, and the data root `Contents.md`. They're one-way printouts for reading in VS Code's Markdown preview or from a backup; DocRepo never reads them back. Links are relative.
- `Task.md`: the title, a note that the page is generated, and a field table (ID, state, then urgent, meeting, plant event and recurrence when set, parents, labels with inherited ones marked, lead and assignees with hours, start, due with days until due, deadline, then reminder when set, each reference field with a value (release 5.9), and the agendas it's on). Then Description, Current status, Subtasks, Agenda (for a target with open items, or an open meeting), Status log (newest first), Summary log, Raw text log and Files. Since release 5.25 (6.11): Notes, after Current status, is the task's notes page, its headings two levels down and each caption a link to its capture.md ("_No notes yet._" when empty); the raw text log is Captures, a capture not on the page saying "· not on the notes page". Since release 5.27 a picture on the page is a picture in Task.md, an attachment a link to its file, each with its description under it, and a table a table.
- `Contents.md`: open tasks as an indented tree, a task with two parents shown under each and marked "also under", then Parked, Closed in the last 30 days, Agendas, Unfiled, People and Labels.
- A page is rewritten only when more than its "Generated from docs.db on" line would change.
- The exact formats are those of the browse tool mockup's examples, kept in `tests/fixtures/examples.md`.

### 6.11 The notes page (release 5.25)

- **One page per task** (`docrepo/notes_page.py`; the notes page plan's decisions 95 to 120 in the parent workspace),
  where its notes are read, written and edited. It's kept in docs.db (`task_pages`) as markup, one line a block:
  DocRepo's markup (5.7) and three more kinds. A **heading** is `# `, `## ` or `### ` and any text (decision 118); one
  that reads as a date ("Thu 8 Oct 2026") is a day heading. A **caption** is a line that's one link to a capture,
  `[Thu 8 Oct 2026 · 10:42 am · Note](capture:C000101)`: it starts the capture's block and dates it (109, 120). A **file
  line** is one link to a document, `[File: Pump spec.docx, the vendor's datasheet](document:D000012)` (96). Since
  release 5.27 (124 to 128): a **picture** is a list item that's one picture of a document,
  `- ![Picture 2026-10-27 1042.png](document:D000031)`, and an **attachment** a list item that's one link to a document,
  `- [File: Pump curve.pdf](document:D000032)`, each with its description as the list item under it; a **table** is
  Markdown's rows (`| Part | Qty |`, then `|---|---|`), its first row the header, one line of text a cell. A line of
  text that would read as one of them starts with a backslash (`\#`, `\[`, `\|`); a link's text escapes `]` and `\`.
- **A capture's block** (`notes_page.block`): its caption, saying what it is ("Note", "New task", "Update: Due date moved
  to Fri 23 Oct.", "Email from Tom Becker: Re: impeller delivery", "Decision from the notes of …", "Meeting notes"), its
  typed text in full with names as written (`@Tom Becker`) and without file and link lines (96, 114), and a file line for
  each of its files. An email's own text stays with the email. A new task's text that's only its title isn't repeated.
  Its headings (release 5.28) are the page's headings, at the level they were typed (the mods log round 4's decision 132).
- **Where it goes** (`notes_page.add_block`): at the end of the page; or, when the task uses day headings, at the end of
  its day's lines, which run to the next day heading whatever other headings come between (release 5.28), or under a
  new heading for its day, made in date order among the day headings (97, 113). Day
  headings are off by default and on for a meeting (119; `Model.uses_day_headings`), and set in the task page's Notes menu.
- **When blocks are added** (`notes_page.add_capture`, `edits.add_to_pages`): when a capture is saved, on each task it
  belongs to (`Model.capture_tasks`), and each item's (5.8) on its own task; when an unfiled capture is filed or made
  into a task; when a discarded capture is brought back; and Add it again (109). A page that can't be changed is a
  problem, not a failed save: the capture is kept, and its Captures tab offers Add it again.
- **A new task's description** is its text's first line (115); the whole text is on its page. Make it a task keeps the
  window's whole text as the description, as the page gets the capture's own text.
- **Discarding a capture** takes its block off its tasks' pages if it's as it was added; a block the owner edited there
  stays unless they say (106; `notes_page.edited_blocks`, `edits.discard_capture`'s `off_edited_pages`). A day heading
  left with nothing under it goes too.
- **The owner's edits** (`edits.save_page`): docs.db, the day's version (103: `task_page_versions`, one row a day, the page
  as it stood at the day's end), the search index and that task's `Task.md` (`pages.write_task_page`). Nothing goes into
  the status log (90). Each day the owner edited a page is a Notes edited line in Activity (111).
- **Two writers** (`notes_page.merge`): a page that changed in docs.db while unsaved typing is open gains the new blocks,
  and loses the blocks taken off there that the owner hasn't changed; the typing stays.
- **The first pages** (107; `notes_page.build_all`): the first time release 5.25 starts, each task's page is built from
  its raw text log, oldest first, after a backup (`CaptureApp.build_pages`). The build only adds pages, so a backup that
  can't be made doesn't stop it; the notification says so. `app_state`'s `notes_pages_built` says it's done. The sample
  data builds its pages as it's loaded.
- **Search** (8.8) indexes each page's words (`search.index_pages`, kind `page`), and lists a hit under Notes unless one of
  the page's captures, the record behind it, is found too.
- **Checklists** (release 5.26, decisions 85 to 91 as redone, and 121 to 123): a checklist line is a line of the page
  (`- [ ] ` or `- [x] `, as in capture.md); a capture's checklist lines arrive with its text. `notes_page.checklist` lists
  them in page order with the heading each sits under. Task.md prints the **Checklist summary** at the top of Notes
  ("**Checklist** · 1 of 4 done", the open lines, then the done ones). Ticks and changes to the lines are edits of the
  page: nothing goes into the status log (90).
- **Pictures and files** (release 5.27, decisions 124 to 127): a picture pasted on the page is written as a PNG in the
  task's `Files` folder ("Picture 2026-10-27 1042.png", made unique; `edits.add_page_picture`, `SafeFS.write_picture`),
  and a file dropped on it is tracked where it is, its text read, as a dropped file is in the capture window
  (`edits.add_page_file`). Each is a capture of its own, a Note on the task with the file as its document and no text,
  **made on the page** (`page_made`): the page shows it at the caret, as a picture or an attachment with an empty line
  under it for its description, so saving it adds no block, and it's on the page while its picture or attachment is
  (`notes_page.on_page`). Add it again puts it back at the page's end, without a caption. A capture's picture (a
  dropped picture or one pasted in the capture window, not an email's, whose pictures are mostly signatures and logos)
  comes onto the page as a picture too, its description under it; its other files stay file lines.
- **A picture's or attachment's description** is the list item under it (125): saving the page keeps it as the
  document's file description (`edits.sync_descriptions`), so Files, search and Task.md read the same words. Left
  empty, it's the made-up one ("*task* – Pasted picture – *name*", release 5.5's rule), which the page shows as an empty
  line to be written.
- **Tables** (128): kept as their rows, read back into a table. Task.md prints them as Markdown tables, and search reads
  their cells' words.
- **captures stay the record** (101): a capture's `capture.md` is written once when it's saved, and then only ever filed
  (112). Its words are fixed on the page; Edit fixes only its title and summary, in docs.db.

### 6.12 Task templates (releases 5.44 and 5.45)

A template is a small tree of tasks without dates. **Make tasks** copies that tree into the task tree, and each copied field remembers its row until it's changed on the task. `docrepo/templates.py` holds the rules, `docrepo/template_pages.py` the pages and `docrepo/ui/templates_view.py` the view and forms.

- **Its own records** (decision 180). A template is in tables of its own, so nothing that reads tasks can see one: not the task tree, the task picker, the lists, Today, Priorities, Activity, the timeline, Capacity, search, the Task view, `Task.md`, `Contents.md` or Parse and populate. Its name and description are its top row's title and description. IDs are integers; there's no ID letter. Backups carry the tables with the rest of `docs.db`.
- **A row** holds a title, description, labels, Inherit parent labels, leads, assignees, lead hours, assignee hours, Urgent, Meeting, Plant event, Repeats and starting notes (decision 182). State, current status, priority, dates, reference fields, notes and captures are each task's own. A template is a strict tree, one parent per row.
- **Make tasks** copies a template, or any row and what's under it (decision 197), under a task or at the top level. The top task's title is typed there (from a row, it starts as the row's title), and is the task's own. Each other row may get a Start and other people; anything left blank stays blank. The tasks are ordinary tasks, `created_by` "Template: *name*", and nothing goes on Today. A task with no dates waits under No dates or hours when it has people or hours, and in the timeline's Plan mode.
- **Starting notes** are notes page markup, checklist lines included, copied onto each new task's page when it's made (decision 194). The page is the task's own from then on, so later changes reach only new tasks.
- **Linked fields** (decisions 183 and 184). Each field the row fills starts linked on the task made from it, and `task_links` names those still following. A field the row leaves blank belongs to the task. A linked value is written into the task's own field, so everything downstream reads it as any other. An open task's linked field holds its row's value:
  - Writing a different value to a linked field ends that link, in `tasks.update_task`, so Edit task, Update captures, Edit selected, Quick edit and Plan mode all keep to it. The status log says "Assignee hours: no longer follows Product trial."
  - Moving a task, or changing its state or its dates, ends nothing.
- **Edit task's marks** (release 5.45, decision 184), for a task whose template isn't discarded. A line at the form's top names the row, with a link to it, and **Detach**. Each field the row fills has a mark beside its label, or beside its tick, except the top task's title. A field that follows has a quiet chain mark: clicking it keeps the task's value and stops following. One that doesn't, or that differs from the row, has a faint **Template: 6 h ↺**: clicking it takes the row's value and follows it again. Typing a different value on a field that follows shows "This task will stop following the template." under it, and it happens on Save.
- **Detach from template** (Edit task's line, or a task's More menu, after asking) ends all of a task's links. Its values stay.
- **The preview** (release 5.45, decisions 186 and 188): before a change reaches any task, a window says what it would do, worked out with nothing changed. With nothing to offer, there's no window, except when taking a row out, which always asks.
  - **A field changed:** each task it would change, ticked, named by its tree, with old and new values and the work across the ticked tasks ("Work across these tasks: 60 h → 20 h"). An unticked task keeps its value and stops following that field. Back returns to the form as typed. Below the list, a folded line: Not changing, for closed and discarded tasks and those with their own value.
  - **A subtask added:** each open tree that holds its parent row, ticked, with its progress ("1 of 5 closed"). The new task arrives undated, its fields linked, under the copy of its parent, or under the tree's top task if that's gone. Closed trees aren't offered. New trees always have it.
  - **A subtask taken out:** its copies stay and their links end. Those not started with nothing on them (no current status, captures, key dates, saved copies or agenda items, a notes page with only its starting notes, and no other subtasks) are offered for discarding, ticked, with the reason "Taken out of template *name*". Bring back restores them.
- **What a change reaches** (`templates.apply_row`). Each ticked task takes the new value through `tasks.update_task`, so it goes into the status log as "Assignee hours 30 → 10 · Template: Product trial." (decision 187) and the capacity calendar follows. A field the row starts filling reaches only tasks where it's empty, and they then follow it; those with their own value are listed as not changing. A field the row stops filling changes no values, and tasks keep what they have as their own (decision 198). Parked tasks keep following.
- **Closed and discarded tasks never change** (decision 185). Their links stay while they're closed or discarded, so a field can fall behind. When the task reopens or is brought back, by any route, each field that fell behind becomes its own, with a status log line and ↺ offered in Edit task, so its hours don't jump.
- **Changes** (decision 187): a template's page lists what was changed, newest first, with what it did ("1 task changed, 1 left as it was"), once tasks have been made from it: building a template isn't a change to anything. Undoing is changing the template back.
- **Taking a row out** takes what's under it too. A top row can't go: discard the template instead. Moving a row (up, down, or under another row of its template) only affects trees made afterwards.
- **Discarding a template** hides it, with a reason, and it's listed in Discarded, where Bring back restores it. Its tasks keep their values and show no marks until it's back, and the task page's line says "(discarded)".
- **Save as template** (decision 195), in a task's More menu and the command palette, makes a template from a task and what's under it: their fields, without dates, state, status, notes or captures, leaving out discarded subtasks. **Link this tree**, on by default, makes these tasks follow it as if made from it. A task that came from another template moves to this one. Each gets a status log line, "Follows *name*."
- **What shows on a task:** the task page's "From template: Product trial › Trial report", whose link opens the row, and `Task.md`'s row, "From template | Product trial, Trial report".

**Reordering (release 5.49, decision 261).** In the Templates list, a row can be dragged: between rows to go beside them, or onto a row to go under it, at its end (`templates.place_row`). Alt+Up and Alt+Down move the selected row among those beside it. The **Move** menu stays. A template's top row doesn't move, nothing goes beside it, a row can't go under itself or into another template (`templates.can_place`), and the drag shows that before the drop. New trees use the new order, and trees already made keep theirs (decision 188). `RowTree.allow_row_moves` turns this on for the Templates view only: the tree moves nothing itself, the records change, and the view draws them again.

**Duplicate (release 5.49, decision 262).** **Duplicate…** on a template's page asks for a name, offering "Product trial copy", and `templates.duplicate` copies every row, in order, with its fields, people, Involvement, hours and starting notes. The copy is a template of its own: no trees, an empty Changes list, and no link to the original, so a change to one doesn't reach the other. It works on whole templates only.

### 6.13 Duration and hours a day (release 5.46)

A task's dates and hours can be stated through its length. `tasks.worked_out` holds the rules, so Edit task, Quick edit, the capture window, Edit selected, Plan mode and a template's own changes all keep to them. `lead_hours` and `assignee_hours` stay the totals everywhere, so the lists, the timeline and Capacity read them as ever.

- **Duration** is a whole number of days, 1 or more, in `tasks.duration`. It counts the workdays in Settings, or every day with **Runs through weekends** (`calendar_days`), for both the Due date and where the hours land. Counting starts on the first workday: a Start on a Saturday stays as typed and counts from Monday.
- **With a Duration** (decision 191):

| You do this | What happens |
|---|---|
| Change Start | Due moves, Duration stays |
| Change Due | Start moves, Duration stays |
| Change Duration or Runs through weekends | Due moves, Start stays. With no Start, Start moves and Due stays |
| Clear either date | Both clear, Duration stays: off the calendar, keeping its size |
| Clear Duration | The dates stay, as plain dates |
| Type two new dates together (a capture, say) | They're the new length |

- **With none typed,** a task's dates are plain dates, as before. Edit task and Quick edit show the length its two dates hold in grey, and typing a number fixes it.
- **A task with a Duration and no Start or Due isn't placed,** even with a Deadline, rather than spreading its hours from the day it was made: `schedule.windows` returns nothing for it, and Capacity lists it as having no dates. A Deadline is never touched, and a Due that moves past one gets a small warning in Edit task. Key dates aren't touched.
- **Plan mode:** a bar moved keeps its days, so one moved across a weekend comes out wider but isn't more work. An end stretched takes the new length. An undated task dropped on the chart takes its own Duration. With no Duration, a drag is as it was. The bar's width is corrected when it's dropped; release 5.48 shows it while dragging.
- **Hours a day** (decision 189): each role's hours box has a unit, **h in all** or **h a day**. A rate is in `lead_per_day` or `assignee_per_day`, and its total is the rate times the task's days, worked out and stored. With h in all, the total stays as typed. Changing the length changes a rate's total, and both go in the status log ("Duration 5 → 3 days.", "Assignee hours 30 → 18."). A total typed over a rate ends the rate.
- **Hours a week** (release 5.49, decision 260): a third unit, **h a week**, on every form with hours, in `lead_per_week` or `assignee_per_week`. A role has one rate at most. The total is the rate times the task's length in weeks, part weeks included: 3 h a week over 30 workdays is 18 h, and over 7 workdays it's 4.2 h. A week is the workdays in Settings, or 7 days with Runs through weekends. The line under the box says "= 18 h over 30 days (6 weeks)". Totals are what the lists, the timeline and Capacity read, so Capacity's even spread makes 3 h a week land as 0.6 h on each workday. `tasks.hours_values` says what a form means by a number and a unit, and `tasks.rate_total` what a rate comes to.
- **Switching the unit** keeps the total: 30 h in all over 5 days becomes 6 h a day, or 30 h a week. With no length, it keeps the number, read as the new unit.
- **A rate with no length** reads "6 h a day, needs a length", or "3 h a week, needs a length", has no total, and stays off Capacity until it has one.
- **A routine task** has no Duration and no rate: its hours are for each time it comes round. Setting a recurrence clears them, and the total stays.
- **On the page:** When has "Duration 5 workdays" (or "5 days, through weekends"), Who has "30 h · 6 h a day", and `Task.md` has a Duration row.
- **Templates:** a row holds a Duration, Runs through weekends and each role's rate or total, and they're linked as any field is. What a row states is compared: a total worked out from a linked rate doesn't end its link, and a typed Duration, a different rate or a total over a rate does. A change to a row's Duration or rate shows in the preview with the dates it moves and the totals it comes to. Make tasks has a Start, Days and the Due and hours they come to, on each row: days kept as offered stay linked, and days typed differently are the task's own. Save as template takes a task's length as the row's Duration, typed or from its two dates, and a linked task takes that Duration too. A routine task isn't reached by a row's Duration or rate.

### 6.14 Involvement (release 5.47)

How much of a role's hours land on one person on one task (decision 196). It isn't a split: on 12 h in all, Priya Shah at 100% has 12 h, Tom Becker at 25% has 3 h and Mike Ortiz at 50% has 6 h, and the role's total stays 12 h.

- **Kept** in `task_people.involvement` and `template_row_people.involvement`: a whole number from 0 to 100, 100 by default. Someone who's both a lead and an assignee has one for each role. `Task.involvement` holds only those that aren't 100, as `{(role, person): percent}`, and `Task.share(role, person)` reads one.
- **Changing it:** `tasks.update_task` takes `involvement`, the task's whole map. Without it, someone kept on keeps theirs when the people change, as an Update capture, Edit selected and Plan mode change people and say nothing of it. Someone taken off loses theirs, and is back at 100% if they return. Anything else is refused: "Involvement is a whole number from 0 to 100."
- **Capacity:** `capacity.roles_of` multiplies each person's role hours by their share, and the even spread is otherwise unchanged. Someone at 0% has no hours, and a task whose people are all at 0% still counts as estimated.
- **On a form:** in Edit task and a template row's form, a person's chip shows their share when it isn't 100, as **Tom Becker 25%**. Double-clicking it, or F2 with it focused, opens a small box just under the chip: "Tom Becker  Involvement [25 %] = 3 h of 12 h", or "of this role's hours" with no total yet. It's a popup, so the form doesn't move. The chip and the line under the role's hours ("Tom Becker 3 h, Mike Ortiz 6 h") change as it's typed. Enter, F2 or a click elsewhere closes it and keeps the number; Esc puts back the one it opened with. None of them saves or closes the form, and the form's Save writes it.
- **On the page:** Who has each person's own hours, "3 h · 25%", and `Task.md` has "Tom Becker (3 h, 25%)". A task with everyone at 100% reads as it did. With no hours, the share still shows.
- **In the status log:** "Tom Becker's involvement 100% → 25%." A template's change adds "· Template: Product trial".
- **Templates:** a row holds each person's share, and it's part of the Lead or Assignees field, so that field's one link covers it, and comparing a field compares the people and their shares. A different share on a task ends the link, and Edit task's mark shows **Template: Priya Shah, Tom Becker 25% ↺**. A change on a row shows in the preview as "Tom Becker's involvement 25% → 50%", counts in **Work across these tasks**, and leaves the other role alone. Make tasks copies shares: someone kept keeps theirs, someone added has 100%, and its chips show them without editing them. Save as template carries them.
- **Quick edit** shows a share on its chip, counts it in the total and keeps it on Save. Shares are set in Edit task. Its chips shorten a name too long for them, with the full name in the tooltip.
- **Not yet:** the timeline's hours text still counts each person's whole hours. `docrepo/timeline.py` waits for its own thread, and release 5.48 changes it. Capacity reads `work_calendar`, so it's right already.

### 7.1 Running it
- `pythonw -m docrepo app` (no console window) or `python -m docrepo app`. It runs in the background with a tray icon. Only one copy runs per data root (a lock file, `System\capture-app.lock`); starting it again shows the running copy's capture window.
- **Tray menu:** New capture, Open browse tool, Mods log, Pause hotkeys (or Resume hotkeys), Quit. Clicking the icon opens the capture window.
- **Hotkey:** `hotkey` in settings, Ctrl+Shift+Space by default, registered with Windows' own `RegisterHotKey` through ctypes. Nothing watches the keyboard. If another program has the hotkey, a notification says so and suggests `set-hotkey`; the tray icon still opens the window.

### 7.3 Parse and populate
- `docrepo/parse.py`, ported from the mockup's `parse.js`: fixed rules with `re` and `datetime`, no LLM. It reads the content text (and any email's text) and fills the fields of the checked capture types. With New task and Update both checked, it fills the new task's fields, and for Update only a quick update's state and status. With a task picked, nothing checked and a quick update ("Closed. …"), it checks Update itself. Release 5.8: an item's lines are the item's, so it reads only the rest, with the new task's own operators taken out (`items.parse_text`).
- **What it fills:** the title (New task), Due and Deadline from date phrases read with the words around them, the deadline description, Reminder, Start, Recurrence, Urgent, labels from their keywords, leads and assignees (known people by name or alias, new names from unmistakable phrases; release 5.30, the mods log round 4's decision 142: also "Mike assists", "Mike and Priya assist", "Mike assisting", "assign Mike", "assigned Mike" and "assignees Mike and Priya", known people only, taken off a title's end as ", Tom leads" is, and "assignee" never read as a person), lead and assignee hours, a quick update's State and Current status, and otherwise an update's first sentence as its Current status. Release 5.18 (M0059, decision 58): Plant event, for New task and Update, from "plant event" or "major event" (not plural, and not before planning, prep, meeting, review or readiness), unless it's denied ("not a plant event") or done before, for or during one ("for the plant event"); then the end date the event's name made a Deadline is its Due. ### 7.4 Saving a capture
- `docrepo/save.py`. What it needs: a new task needs a title or some content text; Update needs a picked task and a change, an agenda or some text; a Note needs some text, a file or an email; a note put on an agenda with no task needs content text. Otherwise it says what's missing and changes nothing. A file's description left empty gets its default (7.2).
- **A quick task** (release 5.6, M0039): a new task with no task picked that goes on Today goes under the built-in top-level task **Quick tasks** (`docrepo/quick.py`), which is made, In progress and created by "DocRepo", the first time it's needed; DocRepo knows it by that creator, so renaming it changes nothing, and if it's discarded the next quick task makes a new one. The task picker's button then says "None: a quick task, under Quick tasks", and Save's line and message say so. `save.quick_task_draft` makes one from a line (Today's box, Make it a task): Parse and populate reads it as a new task (title, dates, recurrence, hours, labels), and keeps only people already on the list.
- One database transaction holds everything: new people and labels; the new task (its description is the content text without email header and file path lines; with no title, the title Parse and populate would give, else the first sentence); the update, whose changes go into the status log under the capture's ID; the capture's record; its documents (an email's kept attachments and pictures become documents held by the capture, and its kept links link documents); saved copies (Save a copy goes into the new task's or the picked task's `Files` folder now, or into the task an unfiled capture is filed to later); and agenda items (the new task, the updated task, or the content text as a note).
- A capture is kept only when it has content text, a file or a summary. An update with only field changes keeps no capture, and its changes are logged as "Capture window".
- **Formatted content text** (release 5.7): the capture is saved with `formatted` and its markup in `capture.md` (6.5); the title, a new task's description and title, Parse and populate and an agenda note read its words.
- **Items and meeting notes** (release 5.8; 6.5, 7.2): in the same transaction, a meeting the notes need is made first, then the capture, then each ticked item's capture and what it makes, and the agenda items the notes discussed close as Discussed (closed by the notes' capture). People an item names who aren't on the list are added. capture.md keeps each `@` and `#` with its ID; a person added by the same save gets theirs too. The notification counts what was made, such as "Made the meeting Business team meeting 8 Oct, under Business team meeting. … Made 2 tasks, 1 note, 2 updates and 1 decision from its items. 2 agenda items closed as Discussed."
- **A note split by `#` task** (release 5.32, 7.2; `save.split_parts`): each part is saved as a capture of its own, all checked first, so none is saved when one can't be. Each part keeps its own lines (its heading included) in its capture.md, its own files, the summary, the item cards' changes, and Add to agenda, which puts its task on the agenda with its text (its own task's agenda gets the note alone). Its items are made from it. The notification lists each capture: "Saved 3 captures, one per #task: C000027, a note on Installation with 1 email and 1 file; C000028, a note on Rigging plan with 1 file; C000029, an unfiled note with 1 file." The browse tool goes to the first task's notes.
- **On the notes page** (release 5.32): a capture's heading that names only the page's own task is left out of its block there; capture.md keeps it.
- **Then the files:** the capture's folder `Captures\YYYY\MM\<id>\` with `capture.md`; each email's own `.msg` file, `email.msg` then `email 2.msg` and so on in the order they were added, and `attachments\`, where each attachment's name is cleaned of characters Windows forbids and made unique within the capture, in any case (a second `image001.png` is `image001 (2).png`), and its document takes that name (release 5.26.1: before it, every email went to `email.msg` and same-named attachments to one file, and Outlook's SaveAs and SaveAsFile replace a file without asking, so only the last of each was kept); each document's text in `Documents\<id>\extracted.txt`, with its size, modified time and SHA-256 in docs.db for the document checks of phase 6; the saved copies, named `YYYY-MM-DD <name>`, cleaned of characters Windows forbids, at most 100 characters and made unique; and the generated pages. A file that fails never undoes the capture: it's listed in the notification and logged.
- After saving, a notification says what Save did, such as "Saved C000026. Created T000020, Book the alignment contractor, under Installation. On the agenda of Business team meeting."

### 7.5 Files, text and Outlook emails
- `docrepo/extract.py` reads text, opening files read-only: `.txt`, `.md`, `.csv`, `.log`, `.json` (UTF-8, UTF-16 with a BOM, or Windows-1252), `.pdf` (pypdf), `.docx` (python-docx: paragraphs and tables), `.pptx` (read with the standard library since release 5.3.1, as a zip of XML parts: each slide's text in the deck's order, shapes inside groups too, tables row by row, and the speaker notes; a part with a DTD, or bigger than 64 MB unpacked, is refused), `.xlsx`/`.xlsm` (openpyxl, read-only: sheet names and cell values), `.eml`. Anything else is recorded with no text. Each document notes how it went (`text_status`: ok, partial when cut at `extracted_text_cap_chars`, none, or error) and how many characters it kept.
- **A picture pasted in the content text** (release 5.27, decision 129) becomes a file of the capture's, as a dropped file does: a row named "Picture 2026-10-27 1042.png" (made unique), written as a PNG in the capture's `attachments` folder when it's saved (`SafeFS.write_picture`), its description left empty becoming "*task* – Pasted picture – *name*". It isn't shown in the text. On its task's notes page it's a picture, with its description under it (6.11).
- **Outlook (phase 3b, tested on the corporate computer):** `docrepo/outlook.py`, through classic Outlook's COM interface (pywin32). DocRepo finds the running Outlook with `GetActiveObject`, and, since Office registers itself late, joins it with `Dispatch` when that fails but Outlook's main window is open; it never starts Outlook. Each field is read on its own, so one Outlook refuses (its security guard can refuse the sender, recipients or body) is left out and the window names it, and every failure shows in the window with its COM error code in words. Each problem is logged and kept for the troubleshooting report (9.4). An email dragged from Outlook isn't a file, so a drop that comes from Outlook, or **Add selected Outlook email**, reads the emails selected in Outlook: subject, sender, recipients, time, plain-text and HTML bodies and attachments, each with its size, content ID and hidden flag (embedded items, such as an attached email, are left out).
- **Add selected Outlook email copies the email whole** (release 5.33.1; `outlook.copy_whole`): the button, the pinned window's mail button, the Outlook email hotkey and a drag DocRepo's own drop target didn't take all attach the selected email to a new email that's never saved or sent (`CreateItem`, then `Attachments.Add` as an embedded item), have Outlook save that attachment as `System\outlook-email.msg` in the data root (`Attachment.SaveAsFile`, which the guard allows, as it allows any attachment's), close the new email without saving, and read the `.msg` without Outlook, as a dragged email is read; the capture keeps it as its own `.msg`. Outlook replaces that one file each time. Where Outlook refuses the copy, the email is read field by field as before, and the guard can refuse its text, sender, recipients and SaveAs; the troubleshooting report's Outlook check has a row for the copy.
- **Reading a `.msg` without Outlook** (release 5.33, `docrepo/msg.py`): a `.msg` is a compound file (MS-OXMSG). pywin32's structured storage calls read it in memory: the subject, sender, recipients, plain text and HTML body from their property streams (`__substg1.0_<tag>`), the time sent from the fixed-size properties stream (a FILETIME in UTC, shown in local time), and each attachment's storage (its name, bytes, content ID, method and hidden flag). An attached email or object is left out. Nothing in it is run, opened or fetched.
- **Categories in Outlook** (release 5.33, decisions 24 to 26; `outlook.mark_filed`): with **Mark filed emails in Outlook with their task's name** on in Settings (off by default), each Outlook email a capture saves on a task gets the task's name added to its categories, and is saved in Outlook; nothing else on it changes. The task is the one whose notes page the capture is on (a new task's first). The name is the task's title with commas and semicolons as spaces, and its top-level task's name in brackets when another open task has the same title (`category_name`). Categories already on the email stay; one already there isn't added again; DocRepo never takes one off, so a renamed or refiled task's old name stays on emails marked before. The email is found by the EntryID and StoreID read when it was added: through Outlook for Add selected Outlook email, and, for a dragged email, from Outlook's selection after the drop, matched by subject (`selected_places`, `match_places`), only while the setting is on. The guard doesn't cover EntryID, StoreID, Categories or Save. Since release 5.33.1 (decision 26 as the owner changed it: a white category didn't show that an email had been filed), a category that isn't on Outlook's list of categories goes on it in **Category colour**, chosen in Settings (Teal by default; `outlook.COLOURS`, Outlook's own 25), so it shows in that colour on every email that has it; one already on the list keeps its own colour, and None leaves the list alone. Also try a test category puts "DocRepo test" on the list in that colour and takes it off again. The Saved notice says how many were marked, and which weren't, and why.
- **Email layer 0** (release 5.4) sorts an email's parts. A picture is an attachment the HTML body shows (an image whose address is `cid:` and the attachment's content ID). Outlook hides most of those from the list of attachments, so hidden doesn't mean a signature: a hidden attachment the body doesn't show is left out, as before release 5.4, and a picture under 10 KB starts unticked as a probable logo or signature picture. Every other attachment is an attachment. The links are the body's `<a href>` addresses, in order: email addresses (`mailto:`) are left out, an address wrapped in Outlook's Safe Links (`…safelinks.protection.outlook.com/?url=…`) is turned back into the real one, anything that isn't http or https (a phone number, a place in the email) is left out, and a repeat is dropped. The body is read with Python's own HTML parser, as data: nothing in it is run, opened or fetched. A `.msg` file dropped from File Explorer is opened through Outlook. The email's text joins the content text, and saving writes each email as its own `.msg` file (Outlook's SaveAs) and its attachments into the capture's folder (7.4); the email's row in the capture window names the file it will be. DocRepo never sends, moves or changes an email.

### 7.6 Copy prompt and summary types
- Summary types are Markdown files in `Config\prompts`: front matter with `name`, `fields` and `scope`, then the instructions. `init` and the app write four defaults when they're missing (General summary, Email extraction and summary, Report high-level summary and topic overview, Ancestor context); edited ones are never replaced. A file whose front matter isn't right is skipped and logged.
- `fields` can be `raw_text_latest`, `raw_text_all`, `file_text`, `summary_log`, `status_log`, `events`, `file_list`, `title`, `description` and `current_status`; `scope` is self, ancestors, descendants or family.
- Copy prompt builds the prompt (a preamble saying the blocks are data, not instructions; the type's instructions; then each block of data with its label), copies it to the clipboard and shows its length, with a warning above `prompt_warn_chars`. In the capture window, the blocks are this capture's text, its files' text and the picked task's records within the scope. An email's attachments are saved only with the capture, so their text isn't in a prompt before then. The Summary box then opens; saving puts the summary in the summary log of the capture's task.

### 7.7 The mods log
- `Mods\mods-log.md`, a plain Markdown file kept out of docs.db so it works when something else is broken and can leave the computer on its own. Entries M0001, M0002 and so on, oldest first: a heading with the ID, date and time, area and open or "done" with the day, then "edited" with the day for an entry that was edited (release 5.5), then the note.
- The panel over the capture window (the **?** button, or Mods log in the tray menu): a text box, an Area (General, Capture window, Task picker, Parse and populate, Copy prompt, Browse tool, Capacity, Documents), Save, Copy open (only the entries not marked done, as Markdown, to the clipboard; release 5.28, M0066), Copy all (the whole log) and the open entries, newest first, each with Edit and Mark done. A line reminds the owner to leave out names and work details.
- **Edit** (release 5.5, M0047; `mods.edit_entry`) puts an open entry's note and area back in the box, and Save becomes Save M00nn: it replaces the note and area, keeps the ID and time, and adds "edited" with the day to the heading, so a copy of the log shows the entry changed. Saving it unchanged changes nothing. Esc or Cancel edit leaves it as it was.

### 8.1 Running it

### 8.10 The Task view (releases 5.34, 5.35 and 5.37)

A window of its own for one task, built so any of its documents can be found and opened in seconds from the keyboard (the design workspace's task overview design, decisions 156 to 167; round 2's item 34, M0043). `docrepo/ui/task_view.py` is the window and `docrepo/ui/result_list.py` its list; what it shows is worked out without Qt in `docrepo/overview.py` (its records), `docrepo/finder.py` (the search) and `docrepo/task_view_pages.py` (the header, preview and empty states as HTML).

- **Opening it:** O on a selected task, **Task view** on the task page's bar, the palette's Open its Task view, Open in Task view on the Files tab, or a crumb or Ctrl+O in another Task view. Open Task views read docs.db again whenever the browse tool does.

- **Searching** (decisions 161 and 162): the box has the cursor and searches as you type, with no Enter and no delay. Every word must match, in any order and case, ignoring accents; quotes keep a phrase; `-word` leaves out; words of one or two letters match only at a word's start. Each word scores by where it matched: the start of the name, a word start in it, inside it, the description, the source (its sender, its subtask, its folders), a slip in a name word (one letter missing, added, wrong or two swapped, keeping the first letter) as the fallback, then the text. Pins, use in the last week and age only break ties, then the later name. All shows each kind's best (8 files, 5 of the others) with Show all; the first result is chosen as you type, so **Enter acts on it**. Typed filters turn into chips once a space follows them: `type:` (pdf, word, excel, powerpoint, picture, email, drawing, link, or `.docx` and the like alone), `in:` a subtask, `from:` a sender or a source, `after:`, `since:` and `before:` a date (2026-09-01, 1 sep, sep, yesterday, last week, last month, 30d; looking back), `is:` pinned, missing, email, link, attachment or picture.
- **The second tier** (release 5.35): files' extracted text, read once from the search index, searched on a worker thread 150 ms after typing pauses. Its finds are a group of their own at the end ("Found in the text of files"), or follow the first tier's under a line, so nothing on screen moves; each says "in its text" with the line. Until it's done, a search the first tier found nothing for says it's still searching the files' text, not that nothing matches.
- **The preview:** the chosen record's facts and its text (the matched lines with a line either side while searching, else its first 40 lines), following the choice after 60 ms, with its actions as buttons. Space (in the list), Ctrl+Space or its button show or hide it.
- **Open** (release 5.35, decision 158; `docrepo/opener.py`): Enter on a file starts a tracked original or a saved copy in its own program (Windows' "open"), only when its type is on the allow-list (Word, Excel, PowerPoint, PDF, Visio, text, CSV, OpenDocument, pictures, Outlook `.msg`), on a worker thread, saying "Still opening…" after two seconds and why it couldn't when it can't. An email attachment is shown in File Explorer instead (one saved to the repo opens as its saved copy); a link is copied; a macro-enabled file, a program, a script or a shortcut is never opened, only shown. Enter on an email opens its `.msg` in Outlook, or its capture when there's none; on a note, its block on the Notes page tab; on a subtask, narrows the window to it. Ctrl+Enter shows a file in File Explorer; Ctrl+Shift+C (or Ctrl+C in the list) copies its path, quoted when it has a space. A file that isn't at its path gets Missing and a line saying so.
- **Pins and uses** (release 5.35, decisions 159 and 160; `docrepo/pins.py`): P (in the list) or Alt+P pins or unpins a file on the task, and Alt+Shift+Up and Down move it among the pins; Task.md lists them as Key documents under Files. Each open, show and copy from the Task view, and each Show in File Explorer and Copy link on the task page's Files tab, is recorded with its task. Neither goes into the status log.
- **The Notes page tab** (release 5.37, decisions 239 to 244; Ctrl+6): the page of the task picked in the outline, in the Notes frame it has on the task page, with its format bar, Checklist summary, ⋯ menu, tables, pasted pictures and dropped files, in place of the list and the Type, Date and From row. Whole task is the top task's own page and a subtask's its own, with no roll-up. The preview stays hidden until a caption, file line or picture is clicked, then shows it with its actions here; Ctrl+Space shows or hides it, apart from the list's. What's typed in the box shows results in place of the page, and Esc or emptying the box comes back. Esc in the page goes to the box, and Tab, Down or Enter from the box go into the page; with the caret in the page, Ctrl+1 and Alt+Shift+Up and Down are the page's. A file dropped on the page goes on the page; an email or a link goes to the capture window. The same page can be open on the task page too, both editable: each saves 0.8 seconds after typing stops and when the caret leaves, the other shows it at once, and Ctrl+Z undoes only what was typed in that window since it last updated.
- **Keys:** as above, and Ctrl+F or / back to the box; Tab from the box into the list, where typing goes back to the box; F6 between the outline, box, list or page, and preview; Esc clears what's typed, then the filters, scope and kind, and never closes the window; Ctrl+W closes it; Ctrl+O another task's Task view; Alt+Up the parent's; Ctrl+K its own palette; F1 every key; and the letters N, U, T, A, D, E and M act on its task, with Alt from the box.
- **Dropping** files, links or an Outlook email on it opens the capture window on its task, as a note, with them added (decision 165).
- **Its look:** a white header band, the outline on the base layer, a 1 px stroke between panes; rows of 48 px (32 compact) with the type's mark in its colour (`type_*` tokens, each 3:1 on white; the type is also in the name), matches in the caution tint, the selected row's tint and pill, and a 2 px accent ring when the list has the keyboard.

## 9. First everyday version (phase 5, built)

### 9.1 Backups
- `docrepo/backup.py`. A backup runs every `backup_every_days` (7 by default) at the app's first start of the day, on its own thread so the windows stay quick, and when the owner asks: **Back up now** in Settings, or the `backup` command. A notification says what it did. The time of the last backup is kept in `app_state`.
- It needs a backup folder (Settings), outside the data root; with none, no backups are made. In the backup folder:
  - `Database\docs-1.db` to `docs-<backup_keep>.db` (8 by default): copies of docs.db made with SQLite's backup API, so they're whole even while DocRepo writes. Each backup fills an empty slot, or overwrites the oldest copy.
  - `Files\`: the data root's files as they are there, except the `System` folder (docs.db is copied whole instead; the lock and the logs stay). New and changed files (by size and modified time) are copied over; nothing is ever removed from it.
  - `backup-log.md`: one line per backup (when, which database copy, how many files were copied), and how to restore.
- A backup writes through a SafeFS that allows only the backup folder. It's the one place DocRepo replaces files: `replace_file` and `replace` work only in a SafeFS's replace roots, which `make_safe_fs` sets to the backup folder, and never when that folder is inside the data root (section 4).
- A file that can't be copied is listed in the notification and the log, and the backup goes on. A missing backup drive stops the backup with a message.
- **Restoring** (by hand, in the README and the log): quit DocRepo, copy `Files` into a new empty folder, copy the newest database copy into its `System` folder as `docs.db`, then `set-data-root` and `rebuild`.

### 9.2 Starting when the owner signs in
- `docrepo/startup.py`. DocRepo may write only in its three places, and the Startup folder isn't one of them, so **Make the Startup shortcut** in Settings (or the `make-shortcut` command) makes `DocRepo.lnk` in `%LOCALAPPDATA%\DocRepo\`, then opens that folder (with the shortcut selected) and the owner's Startup folder in File Explorer, for the owner to drag it across.
- The shortcut runs this copy's `pythonw.exe -m docrepo app` from DocRepo's folder, so no console window opens, and names no data root (DocRepo finds it in `location.json`). Windows' shell (`WScript.Shell`, through pywin32) writes it, to a path the guard checks first. No admin rights, services, scheduled tasks or registry changes.
- Settings says whether DocRepo starts when the owner signs in, by reading the Startup folder: not yet, yes, or a shortcut that starts DocRepo from another folder (made before DocRepo moved), to make again.

### 9.3 Importing the project list from Excel
- `docrepo/excel_import.py` and the form `docrepo/ui/import_dialog.py`, from **Import projects from Excel…** in Settings. A one-time import: each row of the owner's project list becomes a top-level task, created by "Excel import", so its story begins "Imported from the Excel tracker" with its current status. After it, DocRepo is the master list.
- The workbook (`.xlsx` or `.xlsm`) is opened with openpyxl in read-only mode with cached values, so formulas and macros never run, and it's never changed. A workbook open in Excel can't always be read; the form says to close it or import a copy.
- **The form:** the workbook and sheet (a sheet named like "projects" is picked first), the header row (the first row with two or more text cells, so title rows above it are skipped), and the state tasks start in without a State column (In progress). Then each column, with a few example values and a dropdown for what it fills: Title, Description, Add to the description ("Header: value" lines, so nothing is lost), Current status, State, Start, Due, Deadline, Deadline description, Lead, Assignees, Labels, A label (yes or no), Urgent, Lead hours, Assignee hours, or Leave out. The proposal comes from the header's words (Owner and Project lead are Lead, Team is Assignees, Category is Labels, Due date is Due and so on, with Title last so "Project lead" isn't the title), and a column holding only yes, no, x or blank is one label, named by its header (changeable). A State column's values each get the state they become, proposed from their words (complete is Closed, on hold is Parked). Only one column can fill each single field, and one must fill Title.
- **The preview** lists the tasks Import will make (row, title, state, due, lead, assignees, labels), the new people and labels, what to check, and the rows skipped. Nothing is written until **Import**.
- **Values:** dates from date cells, Excel day numbers, or text read as Parse and populate reads date phrases ("Q1 2027", "10/30/2026"); text that isn't a date goes into the description, and the preview says so. Names in Lead and Assignees (split at commas, semicolons, slashes, "&" and "and") match the people list by name or alias; a retired person is left off, as Parse and populate does; the rest become new people. Label names that don't exist become new labels. Urgent reads yes, x, high, urgent, critical or P1.
- Rows with no title are left out. A row whose title is already an Excel-imported task's is skipped, so importing again makes no doubles; the form shows the last import (when, how many, the workbook's name).
- **Import** runs in one transaction (the new people, labels and tasks, each task's capacity calendar rows), then writes the pages. The log records counts only.

### 9.4 The troubleshooting report

Added in mods log round 1, since Outlook can only be tested on the corporate computer. The owner carries the report to the personal computer, so it holds versions, steps, counts and error codes, never captured content.
- **Release 5.33** adds: each email's EntryID and its folder's StoreID in the Outlook check; **Also try a test category on the selected email** (Settings), or `outlook-check --try-category`, which adds the category "DocRepo test" to the selected email, saves it, then puts its categories back and saves again, reporting each step; and **Drops on DocRepo's own drop target**: each drop's formats, whether Outlook made it, how each file came (storage, stream or memory) and its size, and what couldn't be read.
- **What it holds:** DocRepo's, Python's, Windows', PySide6's and pywin32's versions, whether DocRepo runs as administrator (Windows then blocks drags into it) and whether Outlook's main window is open; the Outlook check, each step of reading the email selected in Outlook (finding Outlook, its version, its main window, the selection, each item's kind, each of the email's fields by its length only, the attachments by count (with how many are hidden and how many have a content ID), what email layer 0 would find in the body (links, email addresses, Safe Links and pictures, by count), and whether SaveAs is there, which isn't tried so no file is left behind); Outlook's programmatic access settings, read-only from the registry; this session's drags onto the capture window and pastes into it, by their formats' names and what DocRepo took them as; this session's Outlook problems and uncaught errors; and the log's warnings and errors from the last 7 days, with the start of each traceback.

## 12. The navigation wheels and the Today side panel (releases 5.41 to 5.43)

### 12.1 The wheels

A hotkey shows a small wheel of actions, picked with the arrow keys. **A wheel** has an ID, a name and up to eight slots keyed N, NE, E, SE, S, SW, W and NW. With only N, E, S and W it draws as a cross and a two-arrow chord selects nothing; a diagonal slot makes it 8-way, and nothing moves. Each wheel has its own hotkey (`wheel_hotkeys` in `settings.json`, keyed by wheel ID), and none until set. Pause hotkeys covers them.

**Keys.** One arrow lights a cardinal direction; two at right angles a diagonal; opposites, or three or more, nothing. A pick commits when all the arrows are up, with `release_grace_ms` for a diagonal's second key; holding one key past that re-aims at it. If the hotkey comes up within `tap_ms` with no arrow down, the wheel stays until a pick or a cancel; held longer, it lasts only while held, and letting go with an arrow still down leaves the pick to that arrow's coming up. The numpad's digits are spatial and commit on key-up, and 5 cancels. Enter runs what's lit and confirms a slot marked `confirm`. Esc, the hotkey again, losing the focus, or `idle_ms` with no key cancel. Ctrl+K closes it and opens the command palette. Every other key is swallowed. Nothing watches the keyboard: there's no hook, and the hotkey's own keys are read only while a wheel is open.

**Drawing.** The window is made once and hidden, and each wheel is painted once, unseen, at the start, so its fonts and icons are ready. The whole wheel shows at once (since release 5.43.1), in the middle of the monitor holding the window you were in (or the cursor's). A `draw_ms` above 0 shows only its centre until then, so a pick made by then never shows the rest.

**The config** is `Config\wheels.jsonc` in the data root: JSON with comments, written once and never again, with `wheels.schema.json` beside it. A slot has a `label`, an optional `icon` (one of DocRepo's own), and a `command` with `args`, an optional `confirm`, or `held`. A problem names the field and what's allowed, shows in a notification and the log, and the last good wheels stay in use. It's reloaded when the file changes.

**Commands** are one table (`docrepo/ui/wheel_commands.py`), and a slot can name nothing else, so a config can't start a program and captured content can never become a command:

| Command | Arguments | Does |
|---|---|---|
| `capture.new` | `mode` (note, new_task or update); `blank` (true) | The capture window |
| `capture.pin` | | The pinned window |
| `capture.selection` | | The pinned window with the current email or file |
| `capture.meeting` | | Meeting notes |
| `today.new_item` | | A quick task on Today |
| `today.panel` | `do` (toggle, open or close) | The Today side panel |
| `browse.view` | `view` (any of the browse tool's views) | The browse tool on that view |
| `search.tasks` | `then` (task_view or page) | Task search |
| `search.files` | | File search |
| `search.everything` | | The browse tool, with the cursor in Search everything |
| `task_view.current` | | The selected task's Task view, or the last one opened; with neither, task search |

**The usage log** is `System\logs\wheel-usage.csv`: time, wheel, direction, command, how, whether it had drawn, and the ms to appear and to pick. It holds no content.

### 12.2 A blank capture, with a draft set aside

`capture.new` with something in the draft writes it to `System\capture-draft-aside.json`, with the rest of the form, and clears the window. Saving the blank capture, or hiding it with nothing typed, brings the draft back, and into the pinned window if it was there. Only one is held: with one aside already, it asks whether to keep working on this one or clear it. A restart keeps it, but not its files, as a restart doesn't keep the draft's own; the window says which to add again.

### 12.3 The current email or file

At the hotkey DocRepo notes the window you were in, asking the program nothing: its window, class, process and program, and File Explorer's front tab. Only if `capture.selection` is picked does it read, after checking that the window is still there in the same process. File Explorer's and the desktop's selected files arrive through `add_paths`; Outlook's email through the mail button's read: the one open in its own window, or else the main window's selection, or the newest email of a selected conversation. An attachment selected in the reading pane arrives alone, as a file. They arrive in the pinned window, joining any draft. No keystrokes are ever sent to the other program. If Outlook hasn't answered after 3 s, the pinned window says a dialog may be open, and the email joins when it does.

### 12.4 Task search and file search

**Task search** is the task picker on its own: Enter opens the task's Task view, Ctrl+Enter its page in the browse tool (a slot's `then` can swap them). It also finds closed tasks, marked as closed, and with no match it offers Search everything, carrying what was typed. **File search** is a window with a box, the Task view's list and a preview, across every task's files and saved emails, each file once. It uses the Task view's search (`docrepo/finder.py`), filters included. Enter opens through `docrepo/opener.py`'s allow-list, Ctrl+Enter shows it in File Explorer, Ctrl+Shift+C copies the path, and Tab goes to its task's page.

### 12.5 The Today side panel

The Today view as a floating strip, always on top, opened by its hotkey (`today_panel_hotkey`, none until set), the Execution wheel, the tray or Ctrl+K. There's no second list: its rows are the Today view's, and its buttons call the browse tool's methods.

| State | Width | Shows |
|---|---|---|
| Resting | `rest_width`, 180 px | The count, and one line per item, grouped, with a tick box |
| Widened | `hover_width`, 320 px | A second line, its due date, Done and Remove on the row under the pointer, the box for a quick task or note, and folded Reminders (only while one's day has come, each with Add and Clear), Due in the next 7 days and Done today, which remember whether they're open |
| Detail | `detail_width`, 420 px | The task's page to read, with Done, Remove, Edit and Open in the browse tool; or a note's text, with Edit and Make it a task |

It widens after the pointer rests on it for Windows' hover time (or `hover_ms`), or `inner_edge_hover_ms` on an edge between two monitors, and contracts `contract_ms` after the pointer leaves, never while the pointer is on it, its box has the cursor, a menu is open or a detail is showing. `hover` turns that off, and a click on its top line or its hotkey widens it. A click on anything but the box leaves the keyboard where it is. Its hotkey brings the keyboard to it: Up and Down move, Enter opens the detail, Space ticks Done, Delete removes, and Esc goes back, then contracts it and returns to the window you were in. Done asks "Update the task too?", as the Today view does.

Dragging its top line moves it, and on release it snaps to the nearer side of the monitor it's over. Its side, height and monitor (name, serial number and size) are kept in `app_state`, with whether it's open. If the monitor goes, it moves to the main one and returns with it. While a full-screen window or a slide show covers its monitor it hides (`hide_on_full_screen`), and `exclude_from_capture` keeps it out of screen capture, which also hides it from screenshots and compliance recordings.
