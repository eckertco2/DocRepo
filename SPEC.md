# DocRepo specification

This file describes what DocRepo does and how it's built. It grows phase by phase (see `PROGRESS.md`): sections for finished phases are complete, and later ones are summaries. The hard rules are in `.github/copilot-instructions.md` and apply to everything here.

## 1. What DocRepo is

A Windows desktop tool for someone who manages many projects at once. Information arrives all day as emails, quick notes and documents, many of them on a shared LAN drive. DocRepo lets its owner capture any of it in seconds and organize it as a tree of tasks, where projects are the top-level tasks.

- **Capture app:** runs in the background with a tray icon. A global hotkey opens a small capture window.
- **Browse tool:** a separate window for the task tree, lists, agendas, capacity, people, labels, documents, search and settings (section 8).
- **Capture first.** Every capture is saved at once, with no AI involved. DocRepo never calls an AI. Its Copy prompt button builds a prompt for the owner to paste into an AI chat, and the answer is pasted back as text.

## 2. How it's built and installed

- Developed on the owner's personal computer, in Python 3.12 with PySide6, and published to a public GitHub repo, https://github.com/eckertco2/DocRepo.
- On the corporate computer, the owner downloads the repo, makes a `.venv` and runs `pip install -r requirements.txt`. That computer's pip settings fetch the packages from the company's package repository. DocRepo's code never refers to it.
- No packaging into an .exe. DocRepo runs as `python -m docrepo` from its folder.
- `README.md` has the steps for installing and updating.
- **The release** (release 5.87): `__version__` in `docrepo/__init__.py` is the release's number, shown by `--version`, Settings' Look card and the troubleshooting report. `CHANGELOG.md` has a line per release, newest first, and each committed release is tagged `v` and its number.
- **Upgrading a dependency** (release 5.102): `requirements.txt` pins every package to an exact version, and none moves without the owner's yes (the hard rules). An upgrade, and above all a PySide6 one (6.8.2.1 now; 6.8 is a long-term support line, so a move to another line is the larger step), goes like this:
  1. Make a second venv outside the repo, as ruff's is, so it's never committed (`py -3.12 -m venv %TEMP%\docrepo-next`), and install the new pins there from a copy of `requirements.txt` kept outside the repo too, leaving `.venv` and `requirements.txt` as they are.
  2. From the repo's folder, run the full suite with it (`%TEMP%\docrepo-next\Scripts\python.exe -m pytest`), and `tests/test_real_look.py` on its own, the only tests that run on Windows' real platform instead of offscreen, so a change in how Qt draws or sizes shows there. Both pass with no new skips, and ruff stays at no findings.
  3. Look through the app against `dev_data/` for anything the tests can't see, such as fonts, the tray icon and the hotkeys.
  4. Run one corporate scan: carry the new pins to the corporate computer as text, and install them there into a scratch venv outside DocRepo's folder, through that computer's own pip settings, so the company's package repository has every version and its scanner passes each package. Only then do the new pins go in `requirements.txt` on `main`, with a release of their own and a line in `CHANGELOG.md`, and that release's corporate test makes `.venv` again from it.
  5. If any step fails, `.venv` and `requirements.txt` are still the old ones; delete `%TEMP%\docrepo-next`.

## 3. Data root and settings (phase 1, built)

### Where the data root is
DocRepo keeps all its data in one folder, the **data root**, on the local drive. It must not be inside a OneDrive folder, and for real use it must be outside DocRepo's code folder, so updates never touch it.

DocRepo picks the data root from, in order:
1. `--data-root PATH` on the command line (for development and tests);
2. the `DOCREPO_DATA_ROOT` environment variable;
3. `%LOCALAPPDATA%\DocRepo\location.json`, which holds `{"data_root": "<path>"}` and is written by `set-data-root` or the browse tool's Settings view (8.9).

### Folders
`init` creates `Captures`, `Tasks`, `Documents`, `Mods`, `Config\prompts` and `System\logs` in the data root, plus `Config\settings.json` and the database, `System\docs.db`. Other folders, such as a task's `Files`, appear only when needed.

## 4. Guarded writes (phase 1, built)

`docrepo/safe_fs.py` is the only code that writes, copies or moves files, or creates folders.

- **Allowed places:** the data root, the backup folder (if set) and `%LOCALAPPDATA%\DocRepo\`.
- **Checks on every path:** it must be a full path with a drive or a `\\server\share`. Device paths (`\\?\`, `\\.\`), alternate data streams, names ending in a dot or space, characters Windows forbids and reserved device names (CON, NUL, COM1 and so on) are refused. The path is then resolved through `..`, symlinks and junctions, and must land inside an allowed place.
- **Writing:** `write_text` writes only `.md`, `.json`, `.txt` and `.log` files, as UTF-8, atomically (a temporary file in the same folder replaces the target). Windows refuses a replace while anything has the file open, even for an instant, so every replace waits and tries again for up to a second before it says so (release 5.40.1).
- **Pictures:** `write_picture` (release 5.27, decision 127) writes a picture the owner pasted, as a `.png` file only, atomically, and never over a file that's there.
- **Copying:** `copy_file` copies a file the owner asked to keep. It only reads the source, and never overwrites.
- **Moving:** `move` moves only from one allowed place to another, and never overwrites.
- **Replacing:** `replace_file` (copy over) and `replace` (move over) work only inside a SafeFS's replace roots. `make_safe_fs` makes the backup folder the only one, and none when the backup folder is inside the data root or holds it, so a backup can bring its copies up to date (9.1) while nothing in the data root is ever overwritten by a copy.
- **The Startup shortcut:** `DocRepo.lnk` in `%LOCALAPPDATA%\DocRepo\` is written by Windows' shell, to a path `checked_path` allows (9.2).
- **No delete function.** Every refusal is logged.
- Code that writes on its own (SQLite, the log, Outlook's SaveAs) gets its path from `checked_path` first.
- **Checked by test** (release 5.87): `tests/test_hard_rules.py` fails when any module but `safe_fs.py`, `log_setup.py`, `backup.py` and `opener.py` writes, copies, moves, deletes, makes a folder or starts a program on its own. Only `opener.py` starts another program: Windows' open for the allow-list, and File Explorer with its arguments as a list.

| `email-ids [--dry-run]` | Reads the Outlook identifiers of each saved email that has none from its `.msg` file, without Outlook, and records them, making the rows of emails captured before release 5.74 (release 5.101, the knowledge base's stage K8). DocRepo's log is `System\logs\docrepo.log` in the data root, rotated at 1 MB with 5 old files kept. It records IDs, file names and actions, never captured content. The app logs any error nothing caught, with its traceback, and says so once in a notification (under `pythonw` it would otherwise vanish).

## 6. Data model (phase 2, built)

The words used here are defined in `GLOSSARY.md`.

### 6.1 The database
- `System\docs.db`, SQLite, is the source of truth. Folders never encode the task tree: task folders are named by ID only, and nothing moves when a task is renamed or gets another parent.
- `docrepo/db.py` creates the schema and keeps its version in SQLite's `user_version` (now 25). An older DocRepo database is brought up to date when it's opened (version 2, phase 3: each document's text status, size, modified time and checksum, plus `app_state` and `reminders_shown`; version 3, phase 4: the search index, `search_text`; version 4, release 5.3: `discarded` and `discard_reason` on tasks and captures, and `agenda_items` made again, keeping its rows, so an item can close as Done; version 5, release 5.4: `email_layer_0` on captures; version 6, release 5.7: `formatted` on captures; version 7, release 5.8: `from_notes`, `item` and `meeting` on captures; version 8, release 5.9: `email`, `person_group` and `role` on people, `parent` on labels, `plant_event` on tasks, and `task_references`; version 9, release 5.23: `priority` and `priority_rank` on tasks). A database from a newer DocRepo, or one that isn't DocRepo's, is refused rather than changed. Version 10 (release 5.25): `task_pages` (each task's notes page), `task_page_versions` (the page as it stood at the end of each day it changed, when the owner last edited it that day, and whether they did), tasks' `day_headings`, and the search index made again with pages in it. Version 11 (release 5.27): `page_made` on captures, for a picture pasted or a file dropped on a notes page (6.11). Version 12 (release 5.31): `task_dates`. Version 13 (release 5.35): `document_uses` and `task_pins`, for the Task view (Find files since release 5.98, 8.10). Version 14 (release 5.44): the tables of task templates (6.12). Version 15 (release 5.45): `template_log`, a template's Changes list. Version 16 (release 5.46): `duration`, `calendar_days`, `lead_per_day` and `assignee_per_day` on tasks and template rows (6.13). Version 17 (release 5.47): `involvement` on `task_people` and `template_row_people` (6.14). Version 18 (release 5.49): `lead_per_week` and `assignee_per_week` on tasks and template rows (6.13). Version 19 (release 5.50): `task_ties` (6.15). Version 20 (release 5.51): `anchor_row` on `templates`, and `template_row_ties` (6.16). Version 21 (release 5.74): `capture_emails`, each email in a capture with its description (7.5). Version 22 (release 5.79): the tagged labels' `tagged_labels`, `tagged_aliases`, `tagged_words`, `tagged_mentions` and `tagged_choices` (section 13). Version 23 (release 5.101, the knowledge base's stage K8): each email's Outlook identifiers and its place in Outlook on `capture_emails`, the places release 5.93 kept in `app_state` moved there, and `t_mails` (7.5). Version 24 (release 5.117, decision 416): a reminder that repeats, `reminder_repeat` and `reminder_until` on `tasks`. Version 25 (release 5.125, the cold-eyes plan's decision 485): `t_mails` made again, keeping its rows, so its kinds are `new`, `reply`, `ask` and `report`, with an index on its task and when it was opened.
- Foreign keys are on. Every change runs inside one transaction, so a save happens completely or not at all.
- **Waiting for the database** (release 5.102): each connection waits up to 30 seconds (`db.BUSY_TIMEOUT`, SQLite's busy timeout) while another holds docs.db, before it gives up with "database is locked". A backup's copy (9.1) holds a read lock for as long as it takes, so a save made then waits for it rather than failing after Python's default 5 seconds. The journal stays SQLite's default rollback journal: WAL would let a save go on during the copy, but its shared-memory file (`docs.db-shm`) isn't safe when the data root is in a synced or network folder. Whatever only reads docs.db (a backup's copy, the dump, the troubleshooting report) opens it read-only through `db.connect_read_only`.
- **Names in SQL** (release 5.102): values always go in as parameters. Where a helper writes a table's or a column's name into a statement it builds (an agenda item's table, a person's or a label's list, a task's columns, a tie's source), it first checks the name against its own allow-list with `db.check_names`, which refuses any other. `model.TASK_COLUMNS` is the tasks table's, and a test keeps it the same as the schema.
- **The dump** (release 5.102, the `dump` command, section 5): every table of docs.db as JSON in `System\export\<date>`, so what lives only in the database (templates and their ties, task ties, pins, document uses, notes page versions, label keywords and parents, reference fields) has a plain-file way out. Each row is an object of column and value. The backup doesn't copy `System` (9.1), so a dump isn't backed up; it's made again from docs.db, which is.
- **Upgrades** (release 5.88): every migration from the database's version to now runs in one transaction, so a failed one leaves docs.db as it was. Each script is run a statement at a time, split where SQLite says a statement is complete (`sqlite3.complete_statement`), so a semicolon in a string, a comment or a trigger's body doesn't end one; `executescript` isn't used, as it would commit the transaction first. Before an upgrade, docs.db is copied to the backup folder as `Database\docs-before-v<old version>.db`, when a backup folder is set; with none, or one that can't be used, the log says no copy was taken and the upgrade goes on. `tests/fixtures/roots` holds a sample data root made at each version that carries data, and each is upgraded in the tests with its tasks, captures, notes pages and key dates counted.
- **A damaged docs.db** (one SQLite can't read as a database) stops DocRepo with "docs.db is damaged; restore it from the backup folder", in a window at start-up, as a newer database's message is (release 5.88). A locked one is SQLite's own error, since restoring won't help it.

### 6.2 IDs
- Tasks `T000001`, captures `C000001`, documents `D000001`, people `P001`. Mods log entries are `M0001` (phase 3).
- IDs count up and are never reused, even if a record were removed.

### 6.3 Tasks
- **Fields:** title, state, current status, description, start, due, deadline and its description, reminder (since release 5.117 with how it repeats and until when, decision 416: every week on chosen weekdays, every month on a day or a workday, or every n days, `docrepo/repeats.py`; each time it comes round the task goes on Today and the reminder moves on to the next time), recurrence and repeat until, urgent, meeting, plant event (release 5.9), priority (release 5.23), leads and assignees, lead hours and assignee hours, labels, inherit parent labels (on by default), created (the day), created by (the capture that created it, or "Excel import"), and its reference fields (release 5.9).
- **States:** Not started, In progress, Parked, Closed. Closed means done or cancelled. Closing records the day it closed; reopening clears it. Open means Not started or In progress.
- **Start** defaults to the day the task was created.
- **Recurrence:** Daily, Weekly, Bi-weekly, Monthly, Quarterly or Yearly. A task with one is a routine task. Repeat until can be set only with a recurrence, and clearing the recurrence clears it. Closing a routine task ends the recurrence.
- **Hours** are per person in the role: a total for a one-time task, per occurrence for a routine one. Every lead gets the full lead hours and every assignee the full assignee hours; someone in both roles gets both.
- **The tree:** a task with no parent is a top-level task (a project). A task can have several parents and shows under each. A link that would put a task under itself is refused. Ancestors are every chain upward, without repeats; a chain runs from a top-level task down to the task.
- **Scopes:** this task, with ancestors, with subtasks (descendants), and family (ancestors and descendants).
- **Labels:** a task's own labels come first, then every parent's labels (their own and inherited), unless the task's inherit switch is off.
- **Discarded** (release 5.3, M0021): a task made by mistake can be discarded, with a reason. It keeps its state and everything else, but it's hidden from the task tree, the lists, the counts, the pickers, search, the capacity calendar and `Contents.md`, and kept in the browse tool's Discarded view. Bringing it back clears `discarded` and `discard_reason`. Both go into the status log as "Discarded" (the reason, or None when it's brought back). Nothing is deleted.
- **Key dates** (release 5.31; the design workspace's key dates plan, decisions 146 to 155; `docrepo/key_dates.py`, `tasks.set_key_dates`): any number of dated line items on a task, beside its own Start, Due and Deadline, which still drive the lists, Today, reminders, Capacity and the timeline's bar. Each has a start, an end or both (a start alone is a beginning, "from"; an end alone a target, "by"; both a window; one day at both ends a milestone, "on"), an optional description, and three ticks: **Plant activity** (it's a plant event of its own: the timeline's lane and band, and the "falls during" lines), **Deadline** (a red diamond at its end) and **Done** (the day it was ticked). Every change is in the status log ("Key date added: …", "Key date changed: …", "Key date taken off: …", "Key date done: …"), a new order alone not. They carry no hours. An open key date with an end is due on it on Today and the Overdue and next 7 days list, each a row of its own, and overdue once passed; one with only a start shows from a week before it starts and is never overdue. Done ones stay on the task page and the timeline, grey. They're typed in a capture as a `**key date,` line (release 5.38; `**key date, Dec 1 to 5 trial execution window, plant activity.`, `**key date, by Nov 25 target for trial preparations, deadline.`, `**key date, from Oct 1 trial planning period.`; `items.read_key_date`, its rules in the test vectors' "Quick input"), which goes on its `#` task, the task item it's under, or the capture's task, makes no capture of its own and keeps its line in the notes; or in the capture window's Key dates rows for New task and Update (Update's start as the task's own). They're entered in Edit task's Key dates section (a line each: Start, End, Description and the three ticks; moved up and down, removed, Add key date; a line needs a start, an end or both, and its end can't be before its start) and, until release 5.100, Quick edit's compact one (removed and added only; since then Quick edit names how many and leaves them to Edit task's More options), shown on the task page under When (Done ticked there, done ones grey, Make it a subtask), and on the Overdue and next 7 days list (under a Key dates heading) and Today's Due in the next 7 days, a row each with Done, counted in the sidebar, Mine only filtering by the task's people. **Make it a subtask** makes a key date a subtask of its task, its dates its Start and Due (a Deadline when ticked as one, Plant event when a plant activity, closed when done), and takes it off. Task.md has a Key dates section.
- **Plant event** (release 5.9, M0028, decision 22): a tick box for an outage, a turnaround or the like. The timeline shades a plant event down the whole chart from its Start to its Due (or Deadline), whatever the filters, and since release 5.29 shows it in a lane of its own under the scale, and the capacity view names it over its weeks; where dates are picked (New task, Update, Edit task), a line names a plant event they fall in, such as "Start and Due fall during Spring outage, Tue 3 Nov to Sat 14 Nov." (`timeline.during_text`; a task's own event doesn't count). It's ticked by hand, in Edit selected, by `**event,` (6.5), or by Parse and populate from "plant event" or "major event" (7.3, release 5.18); the event words alone never tick it.
- **Reference fields** (release 5.9, M0034, decision 20): numbers from other systems, such as a change record's. Their names are entered in Settings (`reference_fields`), so the code names no company system. A task has a value for each field, or none (`task_references`); a change goes into the status log under the field's name. Taking a name out of Settings takes its boxes away, and values a task already has still show.
- **Priority** (release 5.23, M0029, M0030, decision 23; `docrepo/priorities.py`): a bucket, Critical, High, Medium or Parking lot, with a place in it (`priority_rank`), or none: Not ranked. A move to another bucket goes into the status log as Priority ("Ranked Critical.", "Priority moved to High.", "No longer ranked."); a move within a bucket doesn't. Urgent stays a flag of its own, and Parking lot isn't Parked: it's an open task ranked lowest. Since release 5.81 (the list rows review's decision L9), an open task's bucket is its row's left edge, in its colour (Critical red, High amber, Medium blue, Parking lot grey; `tree_view.PRIORITY_EDGES`), at any depth, in the browse window's lists and the Today side panel, and the row's tooltip names it; Critical keeps its chip beside Urgent (before, rows showed only Critical). The task page, the Priorities board and Edit task show every bucket, and `Task.md` has a Priority row when it's set.
- `docrepo/tasks.py` creates and changes tasks. Each change goes into the status log, and the task's capacity calendar rows are rebuilt in the same transaction.

### 6.4 People and labels
- Each person has a name, aliases, hours a week (or not set), a status, active or retired, and (release 5.9, M0031, M0033, M0038) an email address, a group and a role, each optional. DocRepo only keeps the address: it never sends email or opens a mail link. A person is in one group at most (decision 19), picked from the groups already used or typed new. Task roles and the calendar store the ID, so renaming someone changes nothing else. One person is me: `me` in `settings.json`.
- Labels have a name (unique, any case), keywords (the name, if none are given) and a status. Renaming a label keeps it on its tasks.
- **Nested labels** (release 5.9, M0051, decision 21): a label can be under a parent label, one level only, so a parent label isn't under another and a label with labels under it can't go under one. A parent label is a heading that tasks don't get on their own: the label pickers show a sublabel as "Production line › Line 1", found by either name, and never offer the parent. Keywords and Find matching tasks stay per sublabel.
- Retired people and labels are hidden from pickers and lists, never deleted.

### 6.5 Captures and documents
- A capture belongs to the task it created; to the task it picked, unless it only made a subtask there (New task without Update); and to the task it was filed to. A capture with no task and no agenda item is unfiled, and waits in the Unfiled view.
- A capture is listed by an email's subject, or else the first sentence of its content text (without email header lines and file path lines, cut at 100 characters), or else its first file's name. Full stops after abbreviations such as "Dr." and "Oct. 19" don't end a sentence.
- A document belongs to the tasks of the captures it came in with, and to the tasks it has saved copies in. Its document versions join the raw text log of each of those tasks.
- **A link** (release 5.4, M0001; `docrepo/links.py`) is a document whose original is a web or SharePoint address (http or https, no spaces), matched exactly rather than in any case. DocRepo keeps only the address: it never fetches a link, so a link has no extracted text (`text_status` none) and no saved copy. Until release 5.67 it was only copied (round 1 plan, decision 5); since then it opens in the default browser on the owner's click (round 6's decision 314, `opener.start_link`, which hands only a checked http or https address to Windows' "open"), and Copy link stays beside it. It's listed by the file its address names (SharePoint's `file=`, else the path's last part, such as "Pump spec.docx"), else by its host, or by the name it was copied with (release 5.66). A capture whose only files are links is typed, not file_path.
- **A folder** (release 5.66, round 6's decision 318; `links.is_folder`) is a document whose original is a folder's path ending in `\`, matched in any case. DocRepo keeps where it is and reads nothing in it: no text (`text_status` none, with the reason), no saved copy and nothing to extract. It's listed by its own name, marked Folder, and showing it opens it in File Explorer.
- **Reading an address** (release 5.66, round 6's item 89; `links.read_address`): wherever an address comes from (Add link, a drop, a paste, the pinned window's landing row), what came round it is taken off (quotes, angle brackets, and a full stop, comma, semicolon, colon or unmatched closing bracket after a web link), `www.` gets `https://`, a `file:` address is the path it names, a box for one address makes a web link's spaces `%20`, and OneNote's Copy link (a web line and an `onenote:` line) gives its web link. Anything else (`mailto:`, `msteams:` and other app links, more than one line, words) isn't kept, and the window says why in words. A drop keeps an address exactly as dragged.
- `capture.md`: front matter whose values are JSON (also valid YAML), then the content text, then a "Summary" section if a summary was pasted. The fields, in order: `id`, `saved`, `source` (typed, outlook_email or file_path), `task` (the picked task, else the task it was filed to, else null), `capture_types` (note, new_task, update), `filed`, `edited`, `created_task`, `changes` (field, from, to), `agenda` (subject and target of each item it added), `documents` (id, name, original, description, save_a_copy, extract), `emails` (release 5.74, only when the capture has emails saved since: each one's file, subject, sender, sent and description, 7.5), `email_layer_0` (release 5.4: what email layer 0 kept from an email and what it left out, 7.5), `content_format` (release 5.7: "markdown" when the content text is formatted), `meeting` (release 5.8: the meeting the notes made), `items` (the captures of the items they made), `from_notes` (an item's notes), `item` (what it is) and `summary_type`. `filed`, `edited`, `created_task`, `changes`, `agenda`, `email_layer_0`, `content_format`, `meeting`, `items`, `from_notes` and `item` appear only when they apply.
- **Formatted content text** (release 5.7, M0045; `docrepo/markup.py`): content text with any formatting or list is kept in `capture.md` as a small, readable piece of Markdown, one block per line: `**bold**`, `*italic*`, `~~strikethrough~~`, `<u>underline</u>` and `<mark class="yellow">highlight</mark>` (yellow, green or pink); a list item is two spaces a level, then `- ` or a number and `. `; any other line is a line of text. A backslash keeps `*`, `~` and `<` as themselves, and `-` or `1.` at a line's start, so a line of text that starts like a list item stays text; a backslash before anything else is just a backslash, so paths read as they are. An email's text in a formatted capture is escaped that way, so it reads back exactly. Content text with no formatting is kept as plain text, as before, with no `content_format`. Whatever reads content text for its words (the title, a new task's description, Parse and populate, an agenda note, search) reads the markup without its marks (`markup.to_plain`); list items keep their `- ` and numbers. Copy prompt sends the markup itself: an LLM reads Markdown. **Checklist lines** (release 5.26, decision 86): a list item whose text starts with a box, `- [ ] ` or `- [x] ` (`markup.CHECK`, `check_of`), shown as Qt's list item with a box (`<li class="checked">`), a ticked one's words grey; `to_plain` keeps the box as text. A checklist line's `@` names stay names: it never makes a task item (decision 87, `items.read`), and it's never a new task's description. **Headings** (release 5.28, the mods log round 4): `# `, `## ` or `### ` and the heading's words, kept as typed without marks, as on the notes page (`markup.HEADING`, `heading_of`); a line of text that would read as one starts with a backslash (`escape_heading`, `text_of`). `to_plain` gives a heading's words alone, so `#Rigging plan` on a heading line is still an item's `#`; pages show a heading as Qt's, a step larger than the text, and the raw text log in bold.
- **Items** (release 5.8, M0048 phase 2, M0049, M0052; `docrepo/items.py`): in any capture, a block of the content text with an operator becomes an item: a task, a note, an update or a decision. Operators are read from the content text's words (never an added email), and only after a space, a "(" or a line's start, so an address such as tom@example.com stays text.
  - `@Tom` or `@Tom Becker` (a name or alias, the longest that fits; a word that isn't on the people list is a new person): a task, with Tom an assignee, several allowed. `@L.Tom`: a task, with Tom its lead. `@__`: a task with no one yet. A task has no lead without `@L.`.
  - `#Rigging plan` or `#T000012`: a link to that task, only when it names one (by title or ID), so "Pump #3" stays text. With no `@` or `**`, the block is a note on it. A line that's only `#` tasks is a **heading**: it covers the lines under it until the next heading, and the plain lines under it are one note on its task. A note naming only the capture's own task (a Note's or an Update's picked task) makes no item: its lines are already the capture's note on it (release 5.32, the knowledge base's decision 28).
  - `**name,`, then the rest (release 5.38, the design workspace's quick input plan, decisions 200 to 209): every `**` name comes from one table, `items.OPERATORS`, and isn't case-sensitive. An entry says either what a line is or which field it fills. Adding a parameter that's a field `tasks.update_task` knows is one entry there, and its match in the mockup's `items.js`.
  - **What a line is:** `**t,` or `**task,`, `**n,` or `**note,`: a task or a note, said outright. `**closed,`, `**done,`, `**parked,`, `**in progress,`, `**started,` (and the quick update's other state words): an update to the `#` task with that state, the rest its current status; `**u,` or `**update,`: an update with no state change. `**decision,`: a decision. `**event,` (release 5.9, decision 22): a task with Plant event ticked, such as `**event, Spring outage, 3 to 14 Nov.`; the end date its own name made a Deadline is its Due, so it runs from its Start to its Due. A task item whose block says "plant event" or "major event" is one too, and `**event,` on a New task's own first line ticks the new task's Plant event (release 5.18, M0059). These take their whole line and the list items under it. With nothing to say they need no comma: `#Rigging plan **closed.`
  - **A parameter:** one sentence fills a field: `**due, 5 Nov.`, `**lead, Tom.`, `**key date, trial window from 1 Nov to 5 Nov 2027, plant activity.` The names: start, due, deadline (the words after its date are its description), deadline description, reminder, repeat until, key date, lead, assignee, lead hours, assignee hours (or hours), duration, weekends (or runs through weekends), involvement, title, description, status, state, priority, recurrence, urgent, plant event, meeting (yes or no), label, parent, and each reference field in Settings, with or without its "#" or "no.". The sentence ends by the sentence rules ("Nov. 1" doesn't end it, and nor does a period in a `#` task's title) or at the line's end, the words after it stay in the notes, and several can share a line. It's for input: a filled field on an existing task stays, and its card says so; a list (key date, lead, assignee, label, parent) adds; on a task being made in this capture, a new task or a task item, the line's value is used, even over the form. Each makes a card, with no capture of its own, and its line stays in the notes. It goes on the nearest of: a `#` task in its sentence, the task item on its line, a `#` task on its line, the task item it's listed under, the new task it's listed under, a `#` above, the capture's task. A window's start takes its end's year when only the end has one ("1 Nov to 5 Nov 2027").
  - **Timing** (release 5.62, decisions 293 to 300): `**duration, 5.`, `5 days` or `2 weeks`, the card saying how many days that is by Settings' workdays, or 7 a week for a task that runs through weekends. `**weekends, yes.` `**hours, 6 h a day.` and `**lead hours, 3 h a week.`, where `6 a day` will do too, and a total as before. `**involvement, Tom 25%, Priya 50%.`, for each role the person holds. `**start` and `**due` take a tie in the words of Edit task's tie line: `**start, 3 workdays after #Line 2 outage ends.`, `**due, the day #Line 2 outage starts.`, `**start, 2 weeks before #Line 2 outage: trial window starts.` for a key date, by its description. "Days" are workdays, and with no "starts" or "ends", after is after it ends and before is before it starts; the card says it in full. A tie's `#` names its source, and only that: it isn't where the value goes, and it files nothing. Its source has to exist already, so a task made in the same capture can't be one. A sentence with no `#` that reads as a date is a date.
  - **Agendas** (release 5.133, decisions 540 to 545): `**agenda,` (or `**agendas,`) isn't a field: it puts the task it goes on, found as any parameter's, on each agenda its sentence names: Today, a person by name or alias (an `@` says it's a person), or a meeting or another task by its title or ID (a `#` says it's a task); a bare name is a person's first, and the whole sentence is tried before its parts. `- @Mike book the crane **agenda, @Tom and #Business team meeting` puts the new task on both; on New task's own first line it's the new task, on a sub-bullet task that task, on a `#task` line that task. Its sentence is all value, so a `#` in it names an agenda and files nothing. The line's other words, without its operators, are each item's note, unless they're the task itself: `Ask about the hire rate **agenda, Tom.` under a task puts that task on Tom's agenda with that note, and with no task anywhere the words go on as a note alone. You aren't an agenda (Today is), a task never goes on its own, and a task already open on an agenda isn't added again. The items are added by the notes' capture, Save's message counts them, and their tasks' and agendas' pages are rewritten.
  - **What stops a timing line,** with a card saying why (`items.stopped`, and `items.value_now` for what's filled): a date that has a date or a tie, even a tie waiting for its source, and a role that has a total or a rate; a Duration on a task with both dates, or typed with them, whether they're on the line, in its own block or already on the task; a rate, Duration, Runs through weekends or tie on a routine task; Runs through weekends on a task whose Duration holds its dates, as it would move them; a share for someone not on the task, or with a different share of their own; and a tie Edit task would refuse (`ties.problem_in`). What's on the task item's line, or another card on the same task, counts, whichever comes first on the line, and an unticked card doesn't. A new task's form isn't known when it's read, so Save checks it: nothing is being edited on a task being made, so the line's value is used over the form's (decision 200), and what still can't go counts as a line not used. A Duration and a share are filled after the capture's other items, so the calendar and the people they need are there.
  - **What can't be read:** a name not in the table, a sentence that can't be read, or an old form such as `**Closed. Mike confirmed` or `**date Dec 1` makes a card that can't be ticked, saying what's wrong or what to write. The line stays in the notes, Save goes ahead, and its message says how many lines weren't used. Saved captures are never read again for operators, so old lines stay as written, and what they made stays. `**` and a space is never an operator. A `**` type wins; else an `@` makes a task; else a `#` alone makes a note.
  - **Found, and loud when it fails** (release 5.92, the review's F6): typing `**` opens the same list `@` and `#` do (`items.star_options`): the kinds first, then the fields, then the reference fields named in Settings, each with an example (`items.STAR_EXAMPLES`, each of which reads with no problem), narrowed by any of its names as you type; choosing one puts in `**name, `. A line with a `**` that starts no operator, such as `**Tom to book the crane`, gets an **Unread line** card ("This ** line wasn't read; check its name and comma", with the line), a click on which goes to it; `**bold**` isn't one. Save keeps the line as it is. A name after `@` that isn't on the people list gets a ticked **Add Tom to people** card; unticked, its `@` makes no one (the item is for no one yet), and the tick holds for every part of a split. The keys (F1) have a **Syntax** tab: six worked lines, every `**` name with its other names and example, and what Parse and populate reads with no `**`. README's table of `**` names is `items.readme_table`, and a test fails when they differ.
  - **A block** is a line, with the list items under it that have no operator of their own; a list item under it with an operator is a block of its own, and a task item listed under another task item becomes its subtask. A task made from a sub-bullet in the capture window's notes has the whole bullet tree its top bullet heads as its notes (release 5.120, decision 446): its block on its own page is the tree as the notes have it, its parent bullet and the lines around it with its own, while its capture.md keeps its own lines, so the notes' page still shows it as one task line where they were (`notes_page.sub_bullet_tree`, `items.bullet_tree`). With New task checked, the first line is the new task itself: its `@`, `@L.` and `#` fill its own assignees, lead and parents.
  - **Where an item goes:** a task under the capture's task (or the meeting, or the new task) and under each `#` task (the `#` of its parent block or heading when it has none of its own); with neither, under Quick tasks. A task in a sub-bullet with no `#` of its own, under a bullet that names a `#` task (a note, an update or a decision on it, or a plain bullet under a `#` heading), goes under that task only, not the capture's task too (release 5.120, decision 445), as one listed under a task item goes under that item only. A note, an update or a decision goes on each `#` task, else on the task item it's listed under, else on the capture's task; with none, it stays in the notes.
  - **Its title** is its line without the operators: one at the line's start or end goes, one inside a sentence keeps its name ("Ask Tom about the seal"; a task by its title), one ending the line after "with", "for", "see" and so on stays ("done with Mike"), and "to", "will" and the like after a leading name go ("@Sam to book the scaffolding" is "Book the scaffolding"). A task's dates, hours, labels and Urgent are read by Parse and populate from its block; its people come only from its operators. Its description is its block without its own line's operators.
  - **Each item is a capture of its own** (`from_notes` the notes, `item` its kind), with its block as written in its capture.md. A task item creates its task; a note, an update (through the status log, under the item) or a decision is filed to each of its tasks. Editing the notes later doesn't change items already made.
  - **IDs in capture.md** (M0049): each `@` and `#` is kept as `@[Tom Becker](P003)`, `@L.[Priya Shah](P002)` or `#[Rigging plan](T000012)`, so renaming a person or a task never breaks it. Everything that shows or reads the text shows `@Tom Becker` (`items.unstore`); titles read the words without the operators (`items.words`).
- **A discarded capture** (release 5.3, M0021) leaves its tasks' raw text logs, summaries and files, the Unfiled view and search, and is kept in the Discarded view. Its folder and `capture.md` aren't touched, and changes it made to tasks stay in their status logs. A document that came in only with discarded captures leaves the Documents view too.
- Phase 2 provides these records and the file format. Saving captures comes in phase 3.

### 6.6 The logs
- **Status log:** each field change, with when, the field, its old and new values as shown, and where it came from (a capture's ID, or "Browse tool", "Capture window", "Agenda view", "Reminders list", "Today"). In `Task.md` each entry stays on one line, so a value with line breaks, such as an edited description, is shown with spaces. Agenda items add their own entries: "Agenda: None → *target*" when one is added and "Agenda: *target* → Discussed" (or Removed) when it's closed.
- **Raw text log:** the task's captures and its documents' versions, oldest first. Since release 5.25 the browse tool lists it as Captures, and Task.md under Captures.
- **Summary log:** pasted summaries from the task's captures and from its documents' versions.
- **Files:** the task's saved copies (and replaced ones), then the documents of its captures: tracked originals, links and email attachments. `Task.md` shows a link's address as code (`` - Link: name · `address` · D000042 ``), not as a link to follow.

### 6.7 Agenda items
- An agenda item puts a task (its subject), or a note with no task, on the agenda of a target: a meeting, another task or a person. A task can't be on its own agenda.
- It stays open, carrying over, until it's closed by hand as Discussed or Removed. Closing an item never closes its task.
- A target's agenda is its open items. The agenda targets are the open meetings (tasks with Meeting checked), then any other task or person with open items.
- **Today** (release 5.3, M0016) is a built-in target, stored as `today`: the owner's list for the day. Its items carry over until they're closed as Done (or Removed); other targets' items close as Discussed or Removed. A task is on Today at most once. The status log says "Added to Today.", "Done for today." and "Taken off Today.", and `Contents.md` lists Today first under Agendas, with "since" and the day an item carried over from. Today isn't one of the agenda targets above: it has a view of its own.

### 6.8 Dates, lists and the capacity calendar
- **Windows:** a one-time task works from Start to Due, or to Deadline if there's no Due; with neither, it's unscheduled. A routine task's first window runs from Start to Due, or is just the Start day, and repeats every interval until Repeat until, the horizon (`capacity_horizon_years` from today) or the day it closed. Monthly, quarterly and yearly repeats keep the day of the month, or use the month's last day; 29 February becomes 28 February.
- **Days until due** uses Due, else Deadline. A routine task counts to the end of its next occurrence. Closed tasks have none.
- **Lists** (open tasks only, soonest first): Overdue and next 7 days (not routine tasks, and since release 5.82 not meetings, whatever their dates: the tasks under a meeting count by their own), Reminders (a reminder in the next 7 days or past), Waiting on others (assignees, none of them me; since release 5.125 a row's right-click menu starts with Ask for an update, 7.5), Assigned to me, Urgent (since release 5.97 the task tree's Urgent only, with no view of its own; the report still lists it), and No dates or hours (people, but no hours, or hours but no Due or Deadline on a one-time task).
- **The capacity calendar** (`work_calendar`) has a row per person, day and task. For each window and person, the hours are spread evenly over the window's workdays (`workdays` in settings, Monday to Friday by default); a window with no workdays spreads over its calendar days. Parked tasks and tasks with no hours have no rows, and a closed task has none after its close date. Not started tasks count.
- It's a cache: rebuilt for a task whenever that task is saved, for everything by `rebuild`, and (from phase 3) for all routine tasks at the first start each day, so the horizon rolls forward. It always shows the current plan, past weeks included.
- **Unestimated** tasks have people but no hours; **unscheduled** ones have hours but no dates. Both are open tasks the calendar can't place.

### 6.9 Generated pages
- Every task gets `Tasks\<id>\Task.md`, and the data root `Contents.md`. They're one-way printouts for reading in VS Code's Markdown preview or from a backup; DocRepo never reads them back. Links are relative.
- `Task.md`: the title, a note that the page is generated, and a field table (ID, state, then urgent, meeting, plant event and recurrence when set, parents, labels with inherited ones marked, lead and assignees with hours, start, due with days until due, deadline, then reminder when set, each reference field with a value (release 5.9), and the agendas it's on). Then Description, Current status, Subtasks, Agenda (for a target with open items, or an open meeting), Status log (newest first), Summary log, Raw text log and Files. Since release 5.25 (6.11): Notes, after Current status, is the task's notes page, its headings two levels down and each caption a link to its capture.md ("_No notes yet._" when empty); the raw text log is Captures, a capture not on the page saying "· not on the notes page". Since release 5.27 a picture on the page is a picture in Task.md, an attachment a link to its file, each with its description under it, and a table a table. Since release 5.67 a reference field whose name has a link address in Settings is a Markdown link to its page, and a Links section after Files lists the task's links as the task page's Links group does, each a Markdown link (a folder's as a file: address). ### 6.11 The notes page (release 5.25)

- **One page per task** (`docrepo/notes_page.py`; the notes page plan's decisions 95 to 120 in the parent workspace),
  where its notes are read, written and edited. It's kept in docs.db (`task_pages`) as markup, one line a block:
  DocRepo's markup (5.7) and three more kinds. A **heading** is `# `, `## ` or `### ` and any text (decision 118); one
  that reads as a date ("Thu 8 Oct 2026") is a day heading. A **caption** is a line that's one link to a capture,
  `[Thu 8 Oct 2026 · 10:42 am · Note](capture:C000101)`: it starts the capture's block and dates it (109, 120). A **file
  line** is one link to a document, `[File: Pump spec.docx, the vendor's datasheet](document:D000012)` (96). Since
  release 5.27 (124 to 128): a **picture** is a list item that's one picture of a document,
  `- ![Picture 2026-10-27 1042.png](document:D000031)`, and an **attachment** a list item that's one link to a document,
  `- [File: Pump curve.pdf](document:D000032)`, each with its description as the list item under it; a **table** is
  Markdown's rows (`| Part | Qty |`, then `|---|---|`), its first row the header, one line of text a cell. A line of
  text that would read as one of them starts with a backslash (`\#`, `\[`, `\|`); a link's text escapes `]` and `\`.
- **A capture's block** (`notes_page.block`): its caption, saying what it is ("Note", "New task", "Update: Due date moved
  to Fri 23 Oct.", "Email from Tom Becker: Re: impeller delivery", "Decision from the notes of …", "Meeting notes"), its
  typed text in full with names as written (`@Tom Becker`) and without file and link lines (96, 114), and a file line for
  each of its files. An email's own text stays with the email. A new task's text that's only its title isn't repeated.
  Its headings (release 5.28) are the page's headings, at the level they were typed (the mods log round 4's decision 132).
  Since release 5.83 (the task pane review's R4 and R4b, in the parent workspace's `docs/ui-design/task-pane-review.md`):
  typed text that only repeats a file's description isn't written; a block with no words of its own beyond its files,
  whose caption would say only "File", "Note" or "Update", has **no caption** (its day heading and file lines say it
  all; a caption that names an email, a change or where an item came from stays), and such a capture is on the page
  while its file lines are (`notes_page.on_page`, `find_block` by its documents; the Captures tab, Discard and Add it
  again find it the same way); and a task made from the notes (an item, 5.8) is a **task line** on the page it came
  from, `[Task: Rigging plan · Mike Ortiz · due Wed 14 Oct](task:T000031)`, in its item's place, with the item's text
  kept in its own capture and on the task's own page. A task line opens the task; it's written once, so a later change
  to the task's title or date doesn't change it. A note that's no capture (5.69) gets its task lines the same way.
- **Where it goes** (`notes_page.add_block`): at the end of its day's lines, which run to the next day heading whatever
  other headings come between (release 5.28), or under a new heading for its day, made in date order among the day
  headings (97, 113). Since release 5.69 every task's page has day headings (`Model.uses_day_headings`): decision 119's
  per-task choice, in the Notes menu, is gone, and `tasks.day_headings` is kept in docs.db, unread.
- **A note that's no capture** (release 5.69; the notes workspace plan's decisions 341 and 345 in the parent workspace):
  a Note on a picked task of typed text alone (no file, email, link or summary, and not with New task, Update or
  meeting notes) keeps no capture. Its text goes straight onto the task's page (`edits.add_note`,
  `notes_page.place_note`), in Save's own transaction, as the owner's edit of the page (the day's version, Activity's
  Notes edited, search, `Task.md`). New text goes at the end of the page (release 5.94, the review of 2026-11-06,
  F13; the rule taken on 2026-11-06, before the notes workspace's shared sections, decision 341, are built). Each of
  its headings goes under the page's heading with the same words (case and spacing aside) only when that heading is
  the page's last; otherwise it goes at the page's end under its own heading, at the level typed, even when a heading
  with its words is higher up (`notes_page.place_note_where`). Its lines under none of its headings go under the day's
  heading, as a block does. The capture window's footer says which before Save: "Save adds this at the end of
  Installation's notes (a Seals heading is higher up)", or "… under Crane, the last heading there". (From release 5.69
  to 5.93 a heading went under the last match anywhere on the page.) Its items (5.8) are made as before, each a capture of its own with no notes behind it (`from_notes` empty),
  and what its parameters fill is logged as the capture window's. A note split by `#task` (5.32) does the same with
  each part of text alone. Save's message says where it went ("Added to the notes of Installation, under Thu 8 Oct
  2026."), and the capture window says so before Save.
- **When blocks are added** (`notes_page.add_capture`, `edits.add_to_pages`): when a capture is saved, on each task it
  belongs to (`Model.capture_tasks`), and each item's (5.8) on its own task; when an unfiled capture is filed or made
  into a task; when a discarded capture is brought back; and Add it again (109). A page that can't be changed is a
  problem, not a failed save: the capture is kept, and its Captures tab offers Add it again.
- **A new task's description** is its text's first line (115); the whole text is on its page. Make it a task keeps the
  window's whole text as the description, as the page gets the capture's own text.
- **Discarding a capture** takes its block off its tasks' pages if it's as it was added; a block the owner edited there
  stays unless they say (106; `notes_page.edited_blocks`, `edits.discard_capture`'s `off_edited_pages`). A day heading
  left with nothing under it goes too.
- **The owner's edits** (`edits.save_page`): docs.db, the day's version (103: `task_page_versions`, one row a day, the page
  as it stood at the day's end), the search index and that task's `Task.md` (`pages.write_task_page`). Nothing goes into
  the status log (90). Each day the owner edited a page is a Notes edited line in Activity (111).
- **Two writers** (`notes_page.merge`): a page that changed in docs.db while unsaved typing is open gains the new blocks,
  and loses the blocks taken off there that the owner hasn't changed; the typing stays.
- **The first pages** (107; `notes_page.build_all`): the first time release 5.25 starts, each task's page is built from
  its raw text log, oldest first, after a backup (`CaptureApp.build_pages`). The build only adds pages, so a backup that
  can't be made doesn't stop it; the notification says so. `app_state`'s `notes_pages_built` says it's done. The sample
  data builds its pages as it's loaded.
- **Search** (8.8) indexes each page's words (`search.index_pages`, kind `page`), and lists a hit under Notes unless one of
  the page's captures, the record behind it, is found too.
- **Checklists** (release 5.26, decisions 85 to 91 as redone, and 121 to 123): a checklist line is a line of the page
  (`- [ ] ` or `- [x] `, as in capture.md); a capture's checklist lines arrive with its text. `notes_page.checklist` lists
  them in page order with the heading each sits under. Task.md prints the **Checklist summary** at the top of Notes
  ("**Checklist** · 1 of 4 done", the open lines, then the done ones). Ticks and changes to the lines are edits of the
  page: nothing goes into the status log (90).
- **Pictures and files** (release 5.27, decisions 124 to 127): a picture pasted on the page is written as a PNG in the
  task's `Files` folder ("Picture 2026-10-27 1042.png", made unique; `edits.add_page_picture`, `SafeFS.write_picture`),
  and a file dropped on it is tracked where it is, its text read, as a dropped file is in the capture window
  (`edits.add_page_file`). Each is a capture of its own, a Note on the task with the file as its document and no text,
  **made on the page** (`page_made`): the page shows it at the caret, as a picture or an attachment with an empty line
  under it for its description, so saving it adds no block, and it's on the page while its picture or attachment is
  (`notes_page.on_page`). Add it again puts it back at the page's end, without a caption. A capture's picture (a
  dropped picture or one pasted in the capture window, not an email's, whose pictures are mostly signatures and logos)
  comes onto the page as a picture too, its description under it; its other files stay file lines.
- **A picture's or attachment's description** is the list item under it (125): saving the page keeps it as the
  document's file description (`edits.sync_descriptions`), so Files, search and Task.md read the same words. Left
  empty, it's the made-up one ("*task* – Pasted picture – *name*", release 5.5's rule), which the page shows as an empty
  line to be written.
- **Tables** (128): kept as their rows, read back into a table. Task.md prints them as Markdown tables, and search reads
  their cells' words.
- **captures stay the record** (101): a capture's `capture.md` is written once when it's saved, and then only ever filed
  (112). Its words are fixed on the page; Edit fixes only its title and summary, in docs.db.

### 6.12 Task templates (releases 5.44 and 5.45)

A template is a small tree of tasks without dates. **Make tasks** copies that tree into the task tree, and each copied field remembers its row until it's changed on the task. `docrepo/templates.py` holds the rules, `docrepo/template_pages.py` the pages and `docrepo/ui/templates_view.py` the view and forms.

- **Its own records** (decision 180). A template is in tables of its own, so nothing that reads tasks can see one: not the task tree, the task picker, the lists, Today, Priorities, Activity, the timeline, Capacity, search, Find files, `Task.md`, `Contents.md` or Parse and populate. Its name and description are its top row's title and description. IDs are integers; there's no ID letter. Backups carry the tables with the rest of `docs.db`.
- **A row** holds a title, description, labels, Inherit parent labels, leads, assignees, lead hours, assignee hours, Urgent, Meeting, Plant event, Repeats and starting notes (decision 182). State, current status, priority, dates, reference fields, notes and captures are each task's own. A template is a strict tree, one parent per row.
- **Make tasks** copies a template, or any row and what's under it (decision 197), under a task or at the top level. The top task's title is typed there (from a row, it starts as the row's title), and is the task's own. Each other row may get a Start and other people; anything left blank stays blank. The tasks are ordinary tasks, `created_by` "Template: *name*", and nothing goes on Today. A task with no dates waits under No dates or hours when it has people or hours, and in the timeline's Plan mode.
- **Starting notes** are notes page markup, checklist lines included, copied onto each new task's page when it's made (decision 194). The page is the task's own from then on, so later changes reach only new tasks.
- **Linked fields** (decisions 183 and 184). Each field the row fills starts linked on the task made from it, and `task_links` names those still following. A field the row leaves blank belongs to the task. A linked value is written into the task's own field, so everything downstream reads it as any other. An open task's linked field holds its row's value:
  - Writing a different value to a linked field ends that link, in `tasks.update_task`, so Edit task, Update captures, Edit selected, Quick edit and Plan mode all keep to it. The status log says "Assignee hours: no longer follows Product trial."
  - Moving a task, or changing its state or its dates, ends nothing.
- **Edit task's marks** (release 5.45, decision 184), for a task whose template isn't discarded. A line at the form's top names the row, with a link to it, and **Detach**. Each field the row fills has a mark beside its label, or beside its tick, except the top task's title. A field that follows has a quiet chain mark: clicking it keeps the task's value and stops following. One that doesn't, or that differs from the row, has a faint **Template: 6 h ↺**: clicking it takes the row's value and follows it again. Typing a different value on a field that follows shows "This task will stop following the template." under it, and it happens on Save.
- **Detach from template** (Edit task's line, or a task's More menu, after asking) ends all of a task's links. Its values stay.
- **The preview** (release 5.45, decisions 186 and 188): before a change reaches any task, a window says what it would do, worked out with nothing changed. With nothing to offer, there's no window, except when taking a row out, which always asks.
  - **A field changed:** each task it would change, ticked, named by its tree, with old and new values and the work across the ticked tasks ("Work across these tasks: 60 h → 20 h"). An unticked task keeps its value and stops following that field. Back returns to the form as typed. Below the list, a folded line: Not changing, for closed and discarded tasks and those with their own value.
  - **A subtask added:** each open tree that holds its parent row, ticked, with its progress ("1 of 5 closed"). The new task arrives undated, its fields linked, under the copy of its parent, or under the tree's top task if that's gone. Closed trees aren't offered. New trees always have it.
  - **A subtask taken out:** its copies stay and their links end. Those not started with nothing on them (no current status, captures, key dates, saved copies or agenda items, a notes page with only its starting notes, and no other subtasks) are offered for discarding, ticked, with the reason "Taken out of template *name*". Bring back restores them.
- **What a change reaches** (`templates.apply_row`). Each ticked task takes the new value through `tasks.update_task`, so it goes into the status log as "Assignee hours 30 → 10 · Template: Product trial." (decision 187) and the capacity calendar follows. A field the row starts filling reaches only tasks where it's empty, and they then follow it; those with their own value are listed as not changing. A field the row stops filling changes no values, and tasks keep what they have as their own (decision 198). Parked tasks keep following.
- **Closed and discarded tasks never change** (decision 185). Their links stay while they're closed or discarded, so a field can fall behind. When the task reopens or is brought back, by any route, each field that fell behind becomes its own, with a status log line and ↺ offered in Edit task, so its hours don't jump.
- **Changes** (decision 187): a template's page lists what was changed, newest first, with what it did ("1 task changed, 1 left as it was"), once tasks have been made from it: building a template isn't a change to anything. Undoing is changing the template back.
- **Taking a row out** takes what's under it too. A top row can't go: discard the template instead. Moving a row (up, down, or under another row of its template) only affects trees made afterwards.
- **Discarding a template** hides it, with a reason, and it's listed in Discarded, where Bring back restores it. Its tasks keep their values and show no marks until it's back, and the task page's line says "(discarded)".
- **Save as template** (decision 195), in a task's More menu and the command palette, makes a template from a task and what's under it: their fields, without dates, state, status, notes or captures, leaving out discarded subtasks. **Link this tree**, on by default, makes these tasks follow it as if made from it. A task that came from another template moves to this one. Each gets a status log line, "Follows *name*."
- **What shows on a task:** the task page's "From template: Product trial › Trial report", whose link opens the row, and `Task.md`'s row, "From template | Product trial, Trial report".

**Reordering (release 5.49, decision 261).** In the Templates list, a row can be dragged: between rows to go beside them, or onto a row to go under it, at its end (`templates.place_row`). Alt+Up and Alt+Down move the selected row among those beside it. The **Move** menu stays. A template's top row doesn't move, nothing goes beside it, a row can't go under itself or into another template (`templates.can_place`), and the drag shows that before the drop. New trees use the new order, and trees already made keep theirs (decision 188). `RowTree.allow_row_moves` turns this on for the Templates view only: the tree moves nothing itself, the records change, and the view draws them again.

**Duplicate (release 5.49, decision 262).** **Duplicate…** on a template's page asks for a name, offering "Product trial copy", and `templates.duplicate` copies every row, in order, with its fields, people, Involvement, hours and starting notes. The copy is a template of its own: no trees, an empty Changes list, and no link to the original, so a change to one doesn't reach the other. It works on whole templates only.

### 6.13 Duration and hours a day (release 5.46)

A task's dates and hours can be stated through its length. `tasks.worked_out` holds the rules, so Edit task, Quick edit, the capture window, Edit selected, Plan mode and a template's own changes all keep to them. `lead_hours` and `assignee_hours` stay the totals everywhere, so the lists, the timeline and Capacity read them as ever.

- **Duration** is a whole number of days, 1 or more, in `tasks.duration`. It counts the workdays in Settings, or every day with **Runs through weekends** (`calendar_days`), for both the Due date and where the hours land. Counting starts on the first workday: a Start on a Saturday stays as typed and counts from Monday.
- **With a Duration** (decision 191):

| You do this | What happens |
|---|---|
| Change Start | Due moves, Duration stays |
| Change Due | Start moves, Duration stays |
| Change Duration or Runs through weekends | Due moves, Start stays. With no Start, Start moves and Due stays |
| Clear either date | Both clear, Duration stays: off the calendar, keeping its size |
| Clear Duration | The dates stay, as plain dates |
| Type two new dates together (a capture, say) | They're the new length |

- **With none typed,** a task's dates are plain dates, as before. Edit task and Quick edit show the length its two dates hold in grey, and typing a number fixes it.
- **A task with a Duration and no Start or Due isn't placed,** even with a Deadline, rather than spreading its hours from the day it was made: `schedule.windows` returns nothing for it, and Capacity lists it as having no dates; in Plan mode its name has the ⋮⋮ grip an undated task's row has (release 5.104). A Deadline is never touched, and a Due that moves past one gets a small warning in Edit task. Key dates aren't touched.
- **Plan mode:** a bar moved keeps its days, so one moved across a weekend comes out wider but isn't more work. An end stretched takes the new length, and with a rate the total follows. An undated task dropped on the chart takes its own Duration. With no Duration, a drag is as it was. Since release 5.48 the bar is drawn while it's dragged with the dates the drop will be saved with: `timeline.dropped` works them out through `tasks.worked_out`, as the save does, in Settings' workdays, or every day with Runs through weekends. The drop's message says the dates, the Duration when an end was stretched, and a rate's total (`timeline.drop_said`), as the Timeline row in 8.3 has it. Since release 5.104 (5.48's open point) a task with a Duration and a Deadline or key dates but no Start or Due has the grip too (`timeline.is_unplaced`, `Row.grip`): its row shows only its deadline's diamond or its key dates, its name dropped takes its own workdays as an undated task's does, the Deadline stays where it is, and the drop's message ends with "past its Deadline …" when the Due lands after it, for any drag. Its tooltip and the line under the chart say "No Start or Due yet" with the Deadline.
- **Hours a day** (decision 189): each role's hours box has a unit, **h in all** or **h a day**. A rate is in `lead_per_day` or `assignee_per_day`, and its total is the rate times the task's days, worked out and stored. With h in all, the total stays as typed. Changing the length changes a rate's total, and both go in the status log ("Duration 5 → 3 days.", "Assignee hours 30 → 18."). A total typed over a rate ends the rate.
- **Hours a week** (release 5.49, decision 260): a third unit, **h a week**, on every form with hours, in `lead_per_week` or `assignee_per_week`. A role has one rate at most. The total is the rate times the task's length in weeks, part weeks included: 3 h a week over 30 workdays is 18 h, and over 7 workdays it's 4.2 h. A week is the workdays in Settings, or 7 days with Runs through weekends. The line under the box says "= 18 h over 30 days (6 weeks)". Totals are what the lists, the timeline and Capacity read, so Capacity's even spread makes 3 h a week land as 0.6 h on each workday. `tasks.hours_values` says what a form means by a number and a unit, and `tasks.rate_total` what a rate comes to.
- **Switching the unit** keeps the total: 30 h in all over 5 days becomes 6 h a day, or 30 h a week. With no length, it keeps the number, read as the new unit.
- **A rate with no length** reads "6 h a day, needs a length", or "3 h a week, needs a length", has no total, and stays off Capacity until it has one.
- **A routine task** has no Duration and no rate: its hours are for each time it comes round. Setting a recurrence clears them, and the total stays.
- **On the page:** When has "Duration 5 workdays" (or "5 days, through weekends"), Who has "30 h · 6 h a day", and `Task.md` has a Duration row.
- **Templates:** a row holds a Duration, Runs through weekends and each role's rate or total, and they're linked as any field is. What a row states is compared: a total worked out from a linked rate doesn't end its link, and a typed Duration, a different rate or a total over a rate does. A change to a row's Duration or rate shows in the preview with the dates it moves and the totals it comes to. Make tasks has a Start, Days and the Due and hours they come to, on each row: days kept as offered stay linked, and days typed differently are the task's own. Save as template takes a task's length as the row's Duration, typed or from its two dates, and a linked task takes that Duration too. A routine task isn't reached by a row's Duration or rate.

### 6.14 Involvement (release 5.47)

How much of a role's hours land on one person on one task (decision 196). It isn't a split: on 12 h in all, Priya Shah at 100% has 12 h, Tom Becker at 25% has 3 h and Mike Ortiz at 50% has 6 h, and the role's total stays 12 h.

- **Kept** in `task_people.involvement` and `template_row_people.involvement`: a whole number from 0 to 100, 100 by default. Someone who's both a lead and an assignee has one for each role. `Task.involvement` holds only those that aren't 100, as `{(role, person): percent}`, and `Task.share(role, person)` reads one.
- **Changing it:** `tasks.update_task` takes `involvement`, the task's whole map. Without it, someone kept on keeps theirs when the people change, as an Update capture, Edit selected and Plan mode change people and say nothing of it. Someone taken off loses theirs, and is back at 100% if they return. Anything else is refused: "Involvement is a whole number from 0 to 100."
- **Capacity:** `capacity.roles_of` multiplies each person's role hours by their share, and the even spread is otherwise unchanged. Someone at 0% has no hours, and a task whose people are all at 0% still counts as estimated.
- **On a form:** in Edit task and a template row's form, a person's chip shows their share when it isn't 100, as **Tom Becker 25%**. Double-clicking it, or F2 with it focused, opens a small box just under the chip: "Tom Becker  Involvement [25 %] = 3 h of 12 h", or "of this role's hours" with no total yet. It's a popup, so the form doesn't move. The chip and the line under the role's hours ("Tom Becker 3 h, Mike Ortiz 6 h") change as it's typed. Enter, F2 or a click elsewhere closes it and keeps the number; Esc puts back the one it opened with. None of them saves or closes the form, and the form's Save writes it.
- **On the page:** Who has each person's own hours, "3 h · 25%", and `Task.md` has "Tom Becker (3 h, 25%)". A task with everyone at 100% reads as it did. With no hours, the share still shows.
- **In the status log:** "Tom Becker's involvement 100% → 25%." A template's change adds "· Template: Product trial".
- **Templates:** a row holds each person's share, and it's part of the Lead or Assignees field, so that field's one link covers it, and comparing a field compares the people and their shares. A different share on a task ends the link, and Edit task's mark shows **Template: Priya Shah, Tom Becker 25% ↺**. A change on a row shows in the preview as "Tom Becker's involvement 25% → 50%", counts in **Work across these tasks**, and leaves the other role alone. Make tasks copies shares: someone kept keeps theirs, someone added has 100%, and its chips show them without editing them. Save as template carries them.
- **Quick edit** shows a share on its chip, counts it in the total and keeps it on Save. Shares are set in Edit task, or by a capture's `**involvement` line (6.5). Its chips shorten a name too long for them, with the full name in the tooltip.
- **The timeline** (release 5.48): its hours text counts each person's share through `capacity.roles_of`, as Capacity does, so a bar's "21 h", its hours a week, Colour bars by hours a week, the tooltip and the line under the chart agree with Capacity for a task with shares. Each person's own hours are given, with their share: "Tom Becker 3 h (25%)".

### 6.15 Ties (release 5.50)

A task's Start or Due set from another date (decisions 245 to 259). What a tie works out is kept in the task's own Start or Due, so whatever reads dates reads them as any other. `docrepo/ties.py` has the rules, and `tasks.follow` does the moving.

- **A tie is one sentence:** a number, workdays or weeks, before or after, a source, starts or ends: "3 workdays after Line 2 outage ends". Zero is "The day Line 2 outage starts". Workdays count by Settings, and a week is 7 calendar days, so it's the same weekday. Each date has one tie at most.
- **Sources:** any other task's start or end, or any key date on any task, its own included. A key date with one date has it at both ends. A routine task's own dates can't be a source, though its key dates can. A task with subtasks and no dates of its own gives nothing, so what's tied to it waits.
- **Refused, saying why:** a task's own dates; a routine task's own dates; and a circle, near or far: "That would go in a circle: Trial report already moves with this task." A key date makes no circle, as it doesn't follow.
- **Moving:** `tasks.update_task` and `tasks.set_key_dates` call `follow` in the transaction that changed the source, so every path that changes a date moves what's tied to it, each after what it's tied to, keeping the gap earlier or later. A key date doesn't follow its task's dates.
- **The rest of the task:** with a Duration, the other date follows. Two plain dates keep their length. With both dates tied, each keeps to its own, Duration is cleared and greyed, the length comes from the dates, and a rate's total follows. Changing the Duration of a task whose Due alone is tied moves its Start. A new tie moves the task in the same way.
- **By hand:** changing a tied date keeps the tie, with a new gap, staying in weeks when it's still a whole number of them. Clearing a tied date puts it back. With a Duration, clearing the other date while the tied one stands brings it back too. A tie ends only on **Remove**, and the date stays.
- **With no date:** a tied date waits while its source has no date, and the line says so. Clearing a source takes what's tied to it off the calendar: two plain dates become a Duration, so it keeps its size.
- **Closed and discarded:** a closed source still counts. A closed task never moves, and a task coming back behind takes a new gap. A discarded source moves nothing, and what's tied to it stays tied, catching up when it's back. A discarded task doesn't move, and takes a new gap when it's back.
- **Ending by itself:** a key date taken off ends the ties to it, and a task gaining a recurrence ends its own ties and those to its dates, though not those to its key dates. Dates stay, and each status log says so. Detach leaves ties as they are.
- **Asking first:** a move that leaves the task's tree, meaning it reaches a task with no top-level task in common, asks first in Edit task, Quick edit and Plan mode. It lists every task that would move, ticked, with each one's Start and Due. An unticked task keeps its date, stays tied and takes a new gap, and what's tied to it stays too. Back changes nothing: Edit task's form comes back as it was, Quick edit stays open, and a drag is undone. `edits.edit_moves`, `change_moves` and `key_dates_move` find what would move by making the change and rolling it back. Ctrl+Z on the timeline doesn't ask.
- **With no one to ask:** an Update capture and Edit selected move them and say so: "Moved 3 tasks with it. 1 closed task stayed." Edit selected's preview says it first. A template's change lists them in its preview (6.16). `**` items move them with no message.
- **On a form:** Edit task has **Tie…** beside Start and Due (since release 5.100 **Tie Start…** and **Tie Due…** under More options, with the Duration, the tied dates' lines and the key dates; a tie or a Duration opens More options by itself). It opens a box that reads as the sentence, and a change counts at once, so the date moves as you go. **Done** closes it, leaving a line in words with **Edit** and **Remove**. A tied date is muted, and its tooltip says what changing it does. A note says how many tasks are tied to this task's dates. Quick edit shows a tied date the same way, and typing gives a new gap, but ties are set only in Edit task, or by a capture's `**start` or `**due` line (6.5).
- **On the page:** "Start tied: 3 workdays after Line 2 outage ends", with the source linked, "Waiting for that date" or "discarded" when it applies, and **Tied to this**, with a task's tree when it's another. `Task.md` has the same rows. A task with no ties reads as it did.
- **In the status log:** "Start Mon 16 Nov → Mon 23 Nov · Follows Line 2 outage." and "Start tie: 1 workday after Line 2 outage ends → 6 workdays after Line 2 outage ends." The entry's `via` is "Follows" and the source's name.
- **On the timeline** (release 5.48, decision 259): selecting a bar draws thin lines in the accent, each from where a tie counts from (a task's start or end on its bar, or a key date's on the key dates' strip, with a dot) down or up to the tied task's row and along it, with an arrow into the Start or Due it sets: to what the bar is tied to, and from it, or its key dates, to what's tied to them. Nothing selected, or a bar with no ties, draws nothing, so the chart stays calm with many ties; a line whose other end is folded away or filtered out isn't drawn. While a bar, a key date or a what-if's whole parent is dragged, each task that follows it, near or far, is drawn as a dashed bar where the drop will put it, its own bar faded and the lines going with it, and the tooltip says how many move with it. `timeline.follows` works those dates out from the model by the save's own rules (`ties.placement`, then `tasks.worked_out`, each after what it's tied to; closed and discarded tasks stay, and a task's key dates don't follow its dates), so the preview is what the drop makes; `timeline.tie_links` lists a bar's ties both ways.

### 6.16 A template's timing (release 5.51)

A template's rows can be tied as tasks are, so a tree gets its dates from one (decisions 248 and 255 to 257). `docrepo/timing.py` has the sums, `docrepo/templates.py` the rules, and `docrepo/ui/timing_view.py` the window. A template with no ties works as it did.

- **A row's tie** is a task's sentence, with a row as its source, or the anchor: "30 workdays before the anchor starts", "1 workday after Trial report ends". `template_row_ties` holds it. Each date has one, and with both tied the row has no Days, as the length comes from them.
- **The anchor** is the one row other rows tie to by default, whose date is typed at Make tasks (`templates.anchor_row`). A template has one at most, and any row with dates of its own can be it. A row spans its subtasks if it has subtasks, no Days, no tie and isn't the anchor, and then it gives nothing to tie to. A row that repeats can't be the anchor or a source, and a row others count from can't start repeating.
- **The Timing window,** from **Timing** on a template's page or **Edit timing** in its chart, lists every row: a circle for the anchor, its sentences, Days, and a lane. The chart redraws as you type, in workdays around the anchor's start, with a week as the workdays in Settings. A row's list offers the anchor first, and leaves out itself, rows that give no date and rows that would make a circle. **+ Tie its Due too** adds a second line. **No anchor** clears the ties to it, and rows tied to a row stay.
- **Another anchor keeps the picture:** the bars stay where they are, the old anchor gets a tie, and what was tied to the anchor counts from the new one, saying so. A tree whose old anchor has a tie of its own, such as to an outage, stays driven from it: that tie stays, and the new anchor's task stays tied to the old one, as its own.
- **The template's page** has a Timing section with the chart, read-only, and each row's sentence. With no anchor it says how to start. The list has an **Anchor** pill and each row's tie and Days, and a row's page has its sentences under When.
- **A row's form** has the same lines under **Tied to**, or says it's the anchor, unless it spans its subtasks or is a top row that isn't the anchor. A link leaves for the Timing window, asking first if something was changed.
- **Make tasks:** the anchor has Start, Days and Due, so either date will do (decision 191), and **Tie…** to set its Start from another task or key date, as a tie of the task's own. Tied rows show their worked-out dates muted, with the sentence under the name. Typing over a Start gives that task a new gap, and ↺ takes the template's back. A date before today warns and stops nothing. Left blank, the tree waits undated, and it all lands when the anchor gets a date. A row whose source isn't being made has its tie dropped.
- **On the tree:** a task made from a row carries an ordinary tie (6.15), counting from its own tree's copy of the source, so changing the anchor's date moves what's tied to it, and only in that tree. `start_tie` and `due_tie` in `task_links` say its gap still follows the row.
- **A different gap** on a task stays tied and stops following the template's number, whether it's typed in Edit task or Quick edit, dragged, or left behind unticked (decision 247). Edit task shows a chain mark on a tie that follows its row, and **Template: 1 workday after the anchor ends ↺** on one that doesn't, which takes the row's number back. Detach ends following, and ties stay.
- **A change to a timing,** from the window or a row's form, is made and rolled back to preview it (decisions 186 and 257). Each task whose dates move is listed by its tree, ticked, with what moves with them by their ties. An unticked task keeps its date, stays tied and takes a new gap, and what's tied to it stays too. Closed and discarded tasks never change, and they and tasks with their own gap are folded under Not changing. A row that starts having a tie reaches only tasks with no date there, and one that drops a tie leaves its tasks tied, as their own. A tie reworded with its date unchanged goes in the status log, not the preview. A task moved by the change logs "Template: Product trial", one elsewhere "Follows …", and the template's Changes list has "Timing around Trial execution window".
- **A new subtask** offered to trees arrives tied, placed from each tree's own rows, and the preview says so. **Taking out** a row, or the anchor, places those tied to it by hand from then on, and tasks made stay tied. **Duplicate** keeps the ties and anchor, pointing inside the copy. **Save as template** carries ties inside the tree as rows tied to rows, leaves out those reaching outside, and has no anchor.
- **Not yet:** the timeline's lines (decision 259). A capture's `**` lines reach tasks, not a template's rows, so a row's ties are set here.

### 6.17 Tree files (releases 5.53 to 5.56)

A **tree file** is a JSON file describing a small tree of tasks. An LLM writes it, DocRepo checks it, the owner reviews it, and it becomes a template, so nothing reaches the lists, Today or Capacity until Make tasks (decision 264). Export writes the same format, and an **edit file** lists changes, matched by ID. DocRepo never calls an LLM (decision 265). `docrepo/tree_files.py` does the work, with no GUI, and `docrepo/ui/tree_import.py` is its window.

**The format.** `format` is `docrepo-tree-1`, with `rows`, and optionally `anchor` (a row's key) and `unplaced` (sentences). Rows are a flat list, so an edit file can hold only what changes (decision 266). A file or a paste is read for its one JSON object, with a code fence or a sentence around it allowed (decision 267).

| Field | What it holds |
|---|---|
| `key`, `parent` | The row's name inside this file, and its parent's. Exactly one row has no parent: the top row, whose title is the template's name. List order is the order among siblings. An export has `id` for `key` |
| `title`, `description` | Short and plain; everything else said about the step |
| `leads`, `assignees`, `involvement` | Names as on the people list, matched by name or alias in any case, with "Me" the owner; a percentage for each person by role, `{"assignees": {"Name": 50}}`, only where it isn't 100 |
| `lead_hours`, `assignee_hours` | Hours in all. Or a rate: `lead_per_day`, `assignee_per_day`, `lead_per_week`, `assignee_per_week`. One form at most for a role |
| `duration`, `calendar_days` | Whole days; Runs through weekends |
| `labels`, `meeting`, `plant_event`, `inherit_labels` | Existing label names; ticks |
| `notes` | Starting notes, as markup: text, lists, headings and checklist lines |
| `start_tie`, `due_tie` | `source` (a row's key), `point` (`start` or `end`), `amount`, `unit` (`workdays` or `weeks`), `direction` (`before` or `after`) |
| `quote`, `assumed` | Shown in the review, never stored (decisions 269 and 271) |

A null is a field left out. `recurrence` and `urgent` are read only from a file with `exported`, so an LLM can't set them and a round trip keeps them (decision 268). Dates and state aren't a row's.

**The checks.** Problems stop Import: not JSON, or cut off; an unknown `format` or field; no top row or two; a repeated key; a `parent`, `source` or `anchor` naming no row; an anchor that's tied, or that spans its subtasks; a row under itself; ties in a circle; a value of the wrong kind; two forms of hours for a role; more than 500 rows; text past 20,000 characters, or a title past 500; a task's export, which Save as template handles. Warnings don't: a tie to a row with subtasks and no dates of its own, a name or label not found, a row with no `quote`, a title over 60 characters, and a template of that name already existing, as Import never merges.

**The Import window,** from **Import…** in the Templates view, has **Copy prompt**, **Choose file…** and **Paste**. A good file shows a line of counts, the warnings (each a link to its row), the rows, what the picked row holds with the words it rests on and what was assumed, and what Make tasks will ask for. The review only shows, and fixing happens in the Templates view after Import (decision 270), but three things are settled there:

- **Ties to settle** (decision 284): a tie to a row that spans its subtasks would wait, so it counts from the parent's last subtask by default, another subtask, or none, with the words kept in the description. Subtasks that would make a circle aren't offered.
- **Names to settle** (decision 272): a close match, anyone on the list, a new person, or by default the row's people left blank with the name kept in its description. Nobody is added silently.
- **Labels that don't exist yet:** left out by default, or added.

**Import as template** runs in one transaction, then keeps a copy of the file as `Imports\YYYY-MM-DD HHMM name.json` in the data root, never over an earlier one (decision 271). **Copy questions** puts what was assumed or fit nowhere on the clipboard. The log has counts, never content. Text goes through `templates._checked` as a form's values do, and starting notes through `templates.page_body`, which keeps any line that reads as a file, picture, capture link or table row as text.

**Copy prompt** shows the prompt, which can be selected by hand, with a Copy button. The rules are `Config\tree-prompt.md`, written the first time and never replaced, so the owner can edit them. DocRepo adds the format and the people and label names, so they can't go stale, then `prompts.PREAMBLE` and room for the notes.

**Export,** on a template's page or as **Export tree…** in a task's More menu, writes `Exports\YYYY-MM-DD HHMM name.json` in the data root, puts it on the clipboard and shows it, with **Copy edit prompt** (rules in `Config\edit-prompt.md`). The file has `of` (`template 12` or `task T000012`) and `exported`, and each row's `id`. A task's export adds `state`, `start`, `due`, `deadline`, its ties, and `also_under`, for information, when it has another parent. What's discarded is left out, and a task with several parents appears once. Export then Import gives the same template.

**An edit file** has `format` `docrepo-edit-1`, `of`, and only what changes. A row left out changes nothing, a field left out changes nothing, and `null` clears a field. New rows have a `key` and a `parent`, which can be another new row. Removal must be stated, `"remove": true`, so a cut-off reply can't take anything away (decision 279). Import reads `format`, so one window takes both kinds (decision 285), and **Bring back an edit file…** in a task's More menu opens it.

**The edit review** lists each change that differs from the database, so a whole tree sent back shows only what differs, and equal after tidying is equal: another case, another order, 30 and 30.0, spaces at the ends. Each has its old value, its new one and its `quote`. A change with no quote starts unticked, "Nothing in what you said asked for this" (decision 286). Anything unticked stays as it is. All that's ticked is made in one transaction, or none of it, and a copy goes in `Imports`.

- **On a template** (decision 280): each change's preview is made and rolled back with `preview_row`, `preview_new_row` or `preview_remove`, and folds out under it with a tick for each task or tree, as a template's previews do (decisions 186 and 188). An unticked task keeps its value and stops following. The template's Changes list says "Edit file: 3 changes", beside each change's own line. The anchor is changed only in Timing.
- **On a task tree:** title, description, labels, people, hours, Duration, Start, Due, Deadline and state, through `tasks.update_task`, so links end, ties move, Capacity rebuilds and the status log says "Edit file". The review says when a linked field will stop following, when a tied date keeps its tie with a new gap, and what a date's move would reach, including other trees. State changes go first, so a task the file closes doesn't move (decision 287). Removing means Discard, with the reason "Taken out by an edit file", from those under it up, and one with other subtasks or open agenda items can't be ticked. New rows are made under their parents. Notes pages, captures, files, ties and moves stay in the app.
- **A stale file** says "Exported 2 Nov; 3 tasks in this tree have changed since", from the status log. Old values are always read from the database.

**Copilot's folder** (item 84), named in Settings under Files and prompts, is where Copilot leaves files. It's outside the data root and DocRepo only reads it. The Import window lists its `.json` files, with **Review it**, leaving out any whose text is already in `Imports`. A prompt file brought over by a handoff has Copilot run `tree-prompt`, write the file, run `tree-check`, and fix what it reports. For edits, `tree-prompt --edit ID` and `tree-export ID` fetch the tree.

### 6.18 Apply template (release 5.63)

A template put into tasks that already exist, instead of making new ones (decisions 301 to 309). `docrepo/templates.py` has the rules (`plan_apply`, `apply_template`), and `docrepo/ui/templates_view.py` the window (`ApplyTemplateDialog`, with the rows Make tasks has, `TreeRows`). There's no schema change: a task follows a row by `task_template` and `task_links`, as any tree's do.

- **Ways in:** **Apply template (n)…** in Select mode, beside Edit selected, for what's ticked. **Apply to tasks…** on a template's page, **Apply template…** under a task's **More**, and **Apply template** in the command palette. It's always the whole template, from its top row.
- **The task** becomes its tree's top and keeps all it has: its title, description, notes, captures, dates, people and status. It follows the top row from then on, as a task made from it does, and a template's later changes reach only the fields that follow.
- **Its fields** (`_landing`): an empty field fills and follows, and one that already says the same follows. One with its own value stays, and doesn't follow, so a later change lists it under Not changing. Labels add, and follow only when they end up the same as the row's. A task with a date or a tie takes no Duration or Runs through weekends, so its dates never change. Inherit parent labels stays as it is, and Recurrence never comes, as a template whose top row repeats is refused.
- **Its dates:** applying a template never changes them. The window says so in amber when the subtasks would fall outside them.
- **The anchor** (`anchor_tie`): one among the subtasks starts tied to the task's Start, "The day Trial 1 starts", as a tie of the task's own, so moving the task moves its tree. Typing over that date keeps the tie with a new gap. A task with no Start has none: the anchor's date is typed, or set by Tie…, or left blank, and the tree waits. When the top row is the anchor, the task's own dates are it, and what's tied to the anchor counts from them.
- **A subtask of the same name:** a row lands on a subtask with its name, whatever the case, under where its parent landed, and nothing else matches. It keeps what it has, by the same rules as the task, and follows the row. With a date or a tie of its own it takes no tie, and what's tied to it counts from its dates. With neither it takes the row's tie, and the anchor's. A row that repeats is always a new task, as is one whose match repeats, is discarded or follows a template already. A subtask under two of the tasks goes to the first. The rest of a task's subtasks stay beside the new ones.
- **New subtasks** are made as Make tasks makes them (6.12, 6.16), with their fields linked, ties following their rows and starting notes copied.
- **Starting notes** on a row that lands on a task go at the end of its notes page, never replacing anything.
- **Refused,** saying why, while the others go on: a task that's closed, discarded, routine or already following a template (`plan_apply`). A template that's discarded, or whose top row repeats, is refused for all (`template_refusal`).
- **The window:** the template at the top, then a section a task, ticked, with its dates, what it adds, uses and fills, where its anchor and subtasks land, and any warning. **Details** unfolds its rows, made on first unfolding so a long list opens quickly. One task on its own, or one with no Start, opens with them showing, as there's something to type. **Add a task…** adds another. Choosing another template starts again. Nothing changes until **Apply to n tasks**, and closing after only unfolding doesn't ask.
- **All or none:** one transaction, so a refusal on the way changes nothing. There's no one-click undo afterwards: a subtask can be discarded, and Detach lets a task go, keeping its values.
- **The log:** each task kept says "Template link: Follows Plant trial" and its filled fields, each by "Template: Plant trial". The template's **Changes** list has "Applied to Trial 1, Trial 2", "To 2 trees".

## 7. Capture app (phase 3, built)

### 7.1 Running it
- `pythonw -m docrepo app` (no console window) or `python -m docrepo app`. It runs in the background with a tray icon. Only one copy runs per data root (a lock file, `System\capture-app.lock`); starting it again shows the running copy's capture window.
- **Tray menu:** New capture, Open browse tool, Mods log, Pause hotkeys (or Resume hotkeys), Quit. Clicking the icon opens the capture window.
- **Hotkey:** `hotkey` in settings, Ctrl+Shift+Space by default, registered with Windows' own `RegisterHotKey` through ctypes. Nothing watches the keyboard. If another program has the hotkey, a notification says so and suggests `set-hotkey`; the tray icon still opens the window.

The main hotkey brings a pinned capture back too (M0054). A hotkey, a wheel's slice or a link that brings the browse tool, a Find files window, file search or the capture window forward restores it if it was minimized, maximized if it was before (release 5.106, decision 405; `ui/front.bring_to_front`): Qt's `show()` alone left it minimized. Settings' **Use the suggested keys** (release 5.6, M0036) fills each empty box with Ctrl+Shift and the topic's letter (`hotkey.SUGGESTED`: B, N, T, U, A, D and E for the Outlook email; Pin has none), the owner's choice; while DocRepo runs, a global hotkey is taken from every other program, such as Outlook's Ctrl+Shift+N, or its Ctrl+Shift+E (a new folder). They're registered like the first, and a taken one is named in one notification. **Pause hotkeys** in the tray menu pauses them all. `docrepo/hotkey.py` lists them (`HOTKEYS`); each one's Windows ID is its place there.
- **First start:** DocRepo asks for the owner's name and adds them to the people list as me (`me` in settings), so "I" and "me" in a capture mean them.
- **Daily work:** at the first start each day, and after midnight while it runs, it rebuilds the capacity calendar (so routine tasks roll forward) and the generated pages. The day is kept in `app_state`.
- **Reminders:** a Windows notification from the tray icon for each open task whose reminder is today or past and hasn't been shown (`reminders_shown`), at start-up and from `reminder_time` each day. More than three become one notification. Clicking a reminder opens the browse tool's Today, on that task when there's one, as the reminder puts it there (release 5.116).
- Saves, reminders and errors are logged by ID only.

- **Mods log round 1 (2026-10-19)** added: an update's first sentence as Current status (not with New task checked too, when the first sentence is the new task's description); a sentence or line that's only a list of names ("Priya, Tom, Mike and Tyler."), or the list after "each:" or "per assignee:", as assignees, when one name in it is known or the sentence before mentions assignees or "each", its new names becoming new people; "is lead", "is the lead", "will be the lead" and "as lead" as lead phrases; half years and quarters with the year joined on ("2H2027", "Q42026"); and "1H" or "2H" before a year, or after "due" or "by", read as a half year rather than hours. The rules in full are in the owner's design notes; `tests/fixtures/test-vectors.md` lists the results for about 150 captures and 100 date phrases, and the tests check every one.
- It uses the people list (me from settings), the active labels, and `event_words` and `reference_fields` from settings.
- It never overwrites a field typed in, and says so in its list. Fields it fills stay marked until edited: a tint and a dot on one or two of them, and only the dot when it fills more (release 5.60). Lists (labels, people) only gain items. More fields stays shut in the new look, since the Understood line names what it filled (release 5.61); in the Classic look it opens when it fills one of them. Nothing is saved until Save.

### 7.4 Saving a capture
- `docrepo/save.py`. What it needs: a new task needs a title or some content text; Update needs a picked task and a change, an agenda or some text; a Note needs some text, a file or an email; a note put on an agenda with no task needs content text. Otherwise it says what's missing and changes nothing. A file's description left empty gets its default (7.2).
- **A quick task** (release 5.6, M0039): a new task with no task picked, made by one of the two ways to a quick task, goes under the built-in top-level task **Quick tasks** (`docrepo/quick.py`), which is made, In progress and created by "DocRepo", the first time it's needed; DocRepo knows it by that creator, so renaming it changes nothing, and if it's discarded the next quick task makes a new one. The task picker's button then says "None: a quick task, under Quick tasks", and Save's line and message say so. `save.quick_task_draft` makes one from a line (Today's box, Make it a task): Parse and populate reads it as a new task (title, dates, recurrence, hours, labels), and keeps only people already on the list. **The two ways** (release 5.99, the consolidation plan's decision 393, until the `usage` counts say otherwise): the mouse way is Today's box (the view's and the side panel's, one box), the keyboard way Ctrl+Shift+D, whose window is in quick-task mode (`CaptureDraft.quick`, kept in its draft) and says so on the task picker's button; the wheels' quick-task slots run Ctrl+Shift+D's command. New task with Today ticked by hand makes an ordinary new task on Today, a top-level task with no task picked ("None: a new top-level task"). D on a row is Add to Today: the task goes on Today as it is. Make it a task, on a note on Today, stays. Until release 5.98 any new task with no task picked that went on Today was a quick task.
- One database transaction holds everything: new people and labels; the new task (its description is the content text without email header and file path lines; with no title, the title Parse and populate would give, else the first sentence); the update, whose changes go into the status log under the capture's ID; the capture's record; its documents (an email's kept attachments and pictures become documents held by the capture, and its kept links link documents); saved copies (Save a copy goes into the new task's or the picked task's `Files` folder now, or into the task an unfiled capture is filed to later); and agenda items (the new task, the updated task, or the content text as a note).
- A capture is kept only when it has content text, a file or a summary. An update with only field changes keeps no capture, and its changes are logged as "Capture window".
- **Formatted content text** (release 5.7): the capture is saved with `formatted` and its markup in `capture.md` (6.5); the title, a new task's description and title, Parse and populate and an agenda note read its words.
- **Items and meeting notes** (release 5.8; 6.5, 7.2): in the same transaction, a meeting the notes need is made first, then the capture, then each ticked item's capture and what it makes, and the agenda items the notes discussed close as Discussed (closed by the notes' capture). People an item names who aren't on the list are added. capture.md keeps each `@` and `#` with its ID; a person added by the same save gets theirs too. The notification counts what was made, such as "Made the meeting Business team meeting 8 Oct, under Business team meeting. … Made 2 tasks, 1 note, 2 updates and 1 decision from its items. 2 agenda items closed as Discussed."
- **A note split by `#` task** (release 5.32, 7.2; `save.split_parts`): each part is saved as a capture of its own, all checked first, so none is saved when one can't be. Each part keeps its own lines (its heading included) in its capture.md, its own files, the summary, the item cards' changes, and Add to agenda, which puts its task on the agenda with its text (its own task's agenda gets the note alone). Its items are made from it. The notification lists each capture: "Saved 3 captures, one per #task: C000027, a note on Installation with 1 email and 1 file; C000028, a note on Rigging plan with 1 file; C000029, an unfiled note with 1 file." The browse tool goes to the first task's notes.
- **On the notes page** (release 5.32): a capture's heading that names only the page's own task is left out of its block there; capture.md keeps it.
- **capture.md first** (release 5.89, the review's F3): the capture's folder `Captures\YYYY\MM\<id>\` and its `capture.md`, and each item's, are written at the end of the transaction, before it commits. The content text is kept nowhere else, so a `capture.md` that can't be written rolls the whole save back: no capture, no task, no note on the page, no ID used, and the capture window keeps the capture with "capture.md couldn't be written (...), so nothing was saved".
- **Then the other files**, after the commit: each email's own `.msg` file, `email.msg` then `email 2.msg` and so on in the order they were added, and `attachments\`, where each attachment's name is cleaned of characters Windows forbids and made unique within the capture, in any case (a second `image001.png` is `image001 (2).png`), and its document takes that name (release 5.26.1: before it, every email went to `email.msg` and same-named attachments to one file, and Outlook's SaveAs and SaveAsFile replace a file without asking, so only the last of each was kept); each document's text in `Documents\<id>\extracted.txt`, with its size, modified time and SHA-256 in docs.db for the document checks of phase 6; the saved copies, named `YYYY-MM-DD <name>`, cleaned of characters Windows forbids, at most 100 characters and made unique; and the generated pages. One of these that fails never undoes the capture: it's listed in the notification and logged.
- **Problems you can see** (release 5.91, `docrepo/ui/problems.py`): a save whose files didn't all go (a copy, an email not marked in Outlook, a file's text) is still saved, and its problems are kept for the session. The capture window's footer and the browse window's status line show "2 problems with the last save" until it's clicked; the click lists them, with Show in File Explorer for the capture's folder. The notification and the log have them too.
- **Save's Undo** (release 5.91): for ten seconds, in the browse window's status line and the capture window's footer when it opens again, Undo discards the capture with the reason "undone" and opens its form again from its draft, kept just before the save. Only a save that made a capture and nothing else has it: no task made or changed, nothing on an agenda, no items, no split, no one new on the people list. Nothing is deleted.
- After saving, a notification says what Save did, such as "Saved C000026. Created T000020, Book the alignment contractor, under Installation. On the agenda of Business team meeting."

### 7.5 Files, text and Outlook emails
- `docrepo/extract.py` reads text, opening files read-only: `.txt`, `.md`, `.csv`, `.log`, `.json` (UTF-8, UTF-16 with a BOM, or Windows-1252), `.pdf` (pypdf), `.docx` (python-docx: paragraphs and tables), `.pptx` (read with the standard library since release 5.3.1, as a zip of XML parts: each slide's text in the deck's order, shapes inside groups too, tables row by row, and the speaker notes; a part with a DTD, or bigger than 64 MB unpacked, is refused), `.xlsx`/`.xlsm` (openpyxl, read-only: sheet names and cell values), `.eml`. Anything else is recorded with no text. Each document notes how it went (`text_status`: ok, partial when cut at `extracted_text_cap_chars`, none, or error) and how many characters it kept.
- **A picture pasted in the content text** (release 5.27, decision 129) becomes a file of the capture's, as a dropped file does: a row named "Picture 2026-10-27 1042.png" (made unique), written as a PNG in the capture's `attachments` folder when it's saved (`SafeFS.write_picture`), its description left empty becoming "*task* – Pasted picture – *name*". It isn't shown in the text, and its row stays as you type on: only a row that came from a path or link line goes when its line does (release 5.135, decision 548). On its task's notes page it's a picture, with its description under it (6.11).
- **Outlook (phase 3b, tested on the corporate computer):** `docrepo/outlook.py`, through classic Outlook's COM interface (pywin32). DocRepo finds the running Outlook with `GetActiveObject`, and, since Office registers itself late, joins it with `Dispatch` when that fails but Outlook's main window is open; it never starts Outlook. Each field is read on its own, so one Outlook refuses (its security guard can refuse the sender, recipients or body) is left out and the window names it, and every failure shows in the window with its COM error code in words. Each problem is logged and kept for the troubleshooting report (9.4). An email dragged from Outlook isn't a file, so a drop that comes from Outlook, or **Add selected Outlook email**, reads the emails selected in Outlook: subject, sender, recipients, time, plain-text and HTML bodies and attachments, each with its size, content ID and hidden flag (embedded items, such as an attached email, are left out).
- **Add selected Outlook email copies the email whole** (release 5.33.1; `outlook.copy_whole`): the button, the pinned window's mail button, the Outlook email hotkey and a drag DocRepo's own drop target didn't take all attach the selected email to a new email that's never saved or sent (`CreateItem`, then `Attachments.Add` as an embedded item), have Outlook save that attachment as `System\outlook-email.msg` in the data root (`Attachment.SaveAsFile`, which the guard allows, as it allows any attachment's), close the new email without saving, and read the `.msg` without Outlook, as a dragged email is read; the capture keeps it as its own `.msg`. Outlook replaces that one file each time. Where Outlook refuses the copy, the email is read field by field as before, and the guard can refuse its text, sender, recipients and SaveAs; the troubleshooting report's Outlook check has a row for the copy.
- **Reading a `.msg` without Outlook** (release 5.33, `docrepo/msg.py`): a `.msg` is a compound file (MS-OXMSG). pywin32's structured storage calls read it in memory: the subject, sender, recipients, plain text and HTML body from their property streams (`__substg1.0_<tag>`), the time sent from the fixed-size properties stream (a FILETIME in UTC, shown in local time), and each attachment's storage (its name, bytes, content ID, method and hidden flag). An attached email or object is left out. Nothing in it is run, opened or fetched. Since release 5.101 it also reads Outlook's identifiers: the conversation index, ConversationID and topic, the conversation index tracking flag, and the Message-ID, In-Reply-To and References, from their own properties or else from the email's transport headers (the standard library's header parser). On the field-by-field route they come from Outlook's `ConversationIndex`, `ConversationID` and `ConversationTopic` and through `PropertyAccessor` (`outlook.item_identifiers`), each read on its own.
- **An email captured before** (release 5.93; since release 5.101 matched on its Message-ID, exactly, when both emails have one, and on the same sender, subject and sent minute only when they don't): a dropped or added email that a live capture already holds is said in the Items panel, "Crane booking is already captured on Installation, 3 Nov", with a link that opens that capture's page. Save keeps it again all the same.
- **A size cap** (release 5.93, `drop_target.MAX_DROP`): a file or email a drag hands over above 200 MB is refused with one sentence, and isn't read when the drag's list of files gives its size; a .msg dropped from File Explorer above it isn't read either. A file from File Explorer is a path, copied later, and has no cap.
- **Categories in Outlook** (release 5.33, decisions 24 to 26; `outlook.mark_filed`): with **Mark filed emails in Outlook with their task's name** on in Settings (off by default), each Outlook email a capture saves on a task gets the task's name added to its categories, and is saved in Outlook; nothing else on it changes. The task is the one whose notes page the capture is on (a new task's first). The name is the task's title with commas and semicolons as spaces, and its top-level task's name in brackets when another open task has the same title (`category_name`). Categories already on the email stay; one already there isn't added again; DocRepo never takes one off, so a renamed or refiled task's old name stays on emails marked before. The email is found by the EntryID and StoreID read when it was added: through Outlook for Add selected Outlook email, and, for a dragged email, from Outlook's selection after the drop (`selected_places`, `match_places`), only while the setting is on. Since release 5.93 (the review's F14) the match is safe: the EntryID the dragged .msg itself carries, when it has one; else the selected email with the same subject and sent minute; else the one selected email with that subject, never by subject when two selected share it (a reply chain), which is skipped and said in the Saved notice; else, with one email dragged and one selected, that one. Where each email is in Outlook is kept with its capture (in `capture_emails` since release 5.101; release 5.93 kept it in `app_state`), so **filing** an unfiled capture later (File to task) marks its emails with the task's name as a save does, under the same setting. The guard doesn't cover EntryID, StoreID, Categories or Save. Since release 5.33.1 (decision 26 as the owner changed it: a white category didn't show that an email had been filed), a category that isn't on Outlook's list of categories goes on it in **Category colour**, chosen in Settings (Teal by default; `outlook.COLOURS`, Outlook's own 25), so it shows in that colour on every email that has it; one already on the list keeps its own colour, and None leaves the list alone. Also try a test category puts "DocRepo test" on the list in that colour and takes it off again. The Saved notice says how many were marked, and which weren't, and why.
- **T-mails** (release 5.105, the knowledge base's stage K8, release B, KB decisions 35 to 39 and 42; `outlook.new_t_mail`, `outlook.reply_all`, `docrepo/ui/t_mails.py`): an email DocRepo opens in Outlook from a task, for the owner to write and send; DocRepo never sends one.
  - **New T-mail** (the task page's bar) makes a new email (`CreateItem`) and opens it (`Display`): empty, with no subject and no To (Outlook adds the owner's signature), tagged only by its conversation index, which no one sees. Outlook gives a new email no index when it's made (check C1), so DocRepo saves it to Drafts first (`Save`), as Outlook's AutoSave does after a few minutes, and reads the index then; if it still has none, DocRepo writes one (`PropertyAccessor.SetProperty` on `PR_CONVERSATION_INDEX`): 0x01, the time in 5 bytes and a new GUID, in MS-OXOMSG's shape (`conversations.new_index`), with the conversation index tracking flag on, so Outlook's ConversationID is the same GUID. An unsent T-mail saved to Drafts stays there, as any draft Outlook has saved does.
  - **Reply all** (decisions 37 and 38) finds the original by its place in Outlook (`GetItemFromID` with its EntryID and StoreID, kept since release 5.93), else opens its saved `.msg` (`OpenSharedItem`, closed without saving after, so the file is unchanged), then makes Outlook's own Reply all (`ReplyAll`) and opens it. The reply carries the original's whole conversation index (checks C1 and C4). From the `.msg`, Outlook doesn't mark the original as replied to. An email dragged in while "Mark filed emails in Outlook" was off has no place kept, so it takes the `.msg` route.
  - **Kept** (`conversations.record_t_mail`): a `t_mails` row with the task, new or a reply (to which capture's email), when it was opened, and its conversation's key and whole index, so its replies fill the capture window's task picker with the task from then on (7.2). A reply's task is the one it was clicked from when its capture is on it, else the capture's own; an unfiled capture's reply is opened and not kept. A T-mail Outlook gave no index isn't kept, and the status line says its replies won't find the task by themselves. The log names it by IDs and the key's first 8 characters.
  - **Captured when sent** (release 5.123, K8's release C, KB decisions 42 to 45; `docrepo/sent_watch.py`, `outlook.watch_sent`, `outlook.sent_since`, `outlook.copy_sent`): while a T-mail waits (not captured, opened in the last 14 days, on a task that's still there) and Outlook's window is open, DocRepo watches Sent Items' `ItemAdd`, reading only each new email's conversation index and place, and sweeps Sent Items (newest first, back to the oldest waiting T-mail, at most 400 emails) on joining Outlook and every 5 minutes. The email whose whole conversation index is a waiting T-mail's is copied whole (`copy_whole`), else read field by field, and saved with no window as a Note on the T-mail's task holding the email, as a dragged email is; its `t_mails` row then names the capture, so it's captured once. No other email in Sent Items is opened, and DocRepo never starts Outlook. A notification names the subject, the task and the capture, and clicking it opens the capture; with "Mark filed emails in Outlook" on, the sent copy gets its task's category. The troubleshooting report lists the waiting T-mails by ID and age, whether Sent Items is watched, and the last sweep.
  - **Ask for an update** (release 5.125, the design workspace's `docs/mods/cold-eyes-plan.md`, decisions 481 to 487; `docrepo/ask_update.py`, `outlook.ask_t_mail`, `t_mails.ask_for_update`): a new T-mail with its To, Subject and words filled in, for the owner to change and send. It's on New T-mail's arrow, after Reply all to the latest email, and first on a task row's right-click menu in Waiting on others; one task at a time, not for a closed or discarded task. Its tooltip names who it would go to.
    - **To** (482): the task's assignees, then its leads, each once, except the owner, who have an email address in People, their addresses joined by "; ". Anyone without one is named in the status line ("Todd has no email address in People"); with nobody left, To is empty and the line says so.
    - **Subject:** "<title>: where does it stand?".
    - **The words** (483, 484, fixed in the code): "Hi Mike," (each person's first name; "Hi Mike and Priya,"; "Hi," for nobody), then one paragraph: "Where does the rigging plan stand?" (the title mid-sentence, its first word losing its capital only when it's merely capitalised; a title that starts with a verb or reads as a sentence is quoted instead: "Where does “Order spare mechanical seal” stand?"), "The last I have (5 Oct): …" (the current status and the day it last changed, or "I have no status for it yet."), "It's due Wed 14 Oct." (or "It was due", or "Its deadline is"; nothing for a routine task), and "Still open under it: …" (its open subtasks, five named, then "and n more"); then "Thanks,".
    - **In Outlook** (`outlook.ask_t_mail`): `CreateItem`, then Subject and To are written (never read), then `Display`, when Outlook adds the owner's signature, then the words go before what Outlook wrote: through Word, the email's editor (`GetInspector.WordEditor`, `Range(0, 0).InsertBefore`), else into the HTML body just inside Word's section (`HTMLBody`), or the text of a plain-text email. Then it's tagged as New T-mail is: the index Outlook gives, else the one it has once saved to Drafts, else one DocRepo writes. Words Outlook won't take go on the clipboard, for the owner to paste; a To it won't take is said. Never sent.
    - **Kept** as a T-mail of kind `ask` (485), with no conversation when Outlook gave it no index (`record_t_mail(untagged=True)`), so its "asked" still counts.
    - **"asked Mon"** (485; `ask_update.asked`): while the newest ask on a task is newer than every live capture on it (by when it was saved or filed; a T-mail's own sent copy doesn't count), its rows say "asked Mon" ("asked today", the weekday within the week, else "asked 4 Nov") in quiet words, first in the people waited on in Waiting on others, and Today's rows say it after their project; the status card says "· asked Mon" after its date, the day in full in its tooltip. Worked out once per model.
    - **Not now** (487): several tasks in one email, since its reply couldn't say which task it's about.
- **Email layer 0** (release 5.4) sorts an email's parts. A picture is an attachment the HTML body shows (an image whose address is `cid:` and the attachment's content ID). Outlook hides most of those from the list of attachments, so hidden doesn't mean a signature: a hidden attachment the body doesn't show is left out, as before release 5.4, and a picture under 10 KB starts unticked as a probable logo or signature picture. Every other attachment is an attachment. The links are the body's `<a href>` addresses, in order: email addresses (`mailto:`) are left out, an address wrapped in Outlook's Safe Links (`…safelinks.protection.outlook.com/?url=…`) is turned back into the real one, anything that isn't http or https (a phone number, a place in the email) is left out, and a repeat is dropped. The body is read with Python's own HTML parser, as data: nothing in it is run, opened or fetched. A `.msg` file dropped from File Explorer is opened through Outlook. The email's text joins the content text, and saving writes each email as its own `.msg` file (Outlook's SaveAs) and its attachments into the capture's folder (7.4); the email's row in the capture window names the file it will be. DocRepo never sends, moves or changes an email.

### 7.6 Copy prompt and summary types
- Summary types are Markdown files in `Config\prompts`: front matter with `name`, `fields` and `scope`, then the instructions. `init` and the app write four defaults when they're missing (General summary, Email extraction and summary, Report high-level summary and topic overview, Ancestor context); edited ones are never replaced. A file whose front matter isn't right is skipped and logged.
- `fields` can be `raw_text_latest`, `raw_text_all`, `file_text`, `summary_log`, `status_log`, `events`, `file_list`, `title`, `description` and `current_status`; `scope` is self, ancestors, descendants or family.
- Copy prompt builds the prompt (a preamble saying the blocks are data, not instructions; the type's instructions; then each block of data with its label), copies it to the clipboard and shows its length, with a warning above `prompt_warn_chars`. In the capture window, the blocks are this capture's text, its files' text and the picked task's records within the scope. An email's attachments are saved only with the capture, so their text isn't in a prompt before then. The Summary box then opens; saving puts the summary in the summary log of the capture's task.

### 7.7 The mods log
- `Mods\mods-log.md`, a plain Markdown file kept out of docs.db so it works when something else is broken and can leave the computer on its own. Entries M0001, M0002 and so on, oldest first: a heading with the ID, date and time, area and open or "done" with the day, then "edited" with the day for an entry that was edited (release 5.5), then the note.
- The panel over the capture window (the **?** button, or Mods log in the tray menu): a text box, an Area (General, Capture window, Task picker, Parse and populate, Copy prompt, Browse tool, Capacity, Documents), Save, Copy open (only the entries not marked done, as Markdown, to the clipboard; release 5.28, M0066), Copy all (the whole log) and the open entries, newest first, each with Edit and Mark done. A line reminds the owner to leave out names and work details.
- **Edit** (release 5.5, M0047; `mods.edit_entry`) puts an open entry's note and area back in the box, and Save becomes Save M00nn: it replaces the note and area, keeps the ID and time, and adds "edited" with the day to the heading, so a copy of the log shows the entry changed. Saving it unchanged changes nothing. Esc or Cancel edit leaves it as it was.

### 8.1 Running it

### 9.1 Backups
- `docrepo/backup.py`. A backup runs every `backup_every_days` (7 by default) at the app's first start of the day, on its own thread so the windows stay quick, and when the owner asks: **Back up now** in Settings, or the `backup` command.   - `Database\docs-1.db` to `docs-<backup_keep>.db` (8 by default): copies of docs.db made with SQLite's backup API, from a read-only connection, so they're whole even while DocRepo writes. Each backup fills an empty slot, or overwrites the oldest copy. A save made while the copy is under way waits for it, up to 30 seconds (6.1, release 5.102).
  - `Files\`: the data root's files as they are there, except the `System` folder (docs.db is copied whole instead; the lock and the logs stay). New and changed files (by size and modified time) are copied over; nothing is ever removed from it.
  - `backup-log.md`: one line per backup (when, which database copy, how many files were copied), and how to restore.
  - Each new database copy is checked with SQLite's `quick_check` before it takes its slot (release 5.89). One that fails isn't kept: the slot keeps the last good copy, the log line says "database copy not kept", the files are mirrored all the same, and Settings' backup card shows the trouble until a backup makes a good copy. A backup that can't be made at all shows there too.
  - `System\Drafts` is mirrored into `Files\System\Drafts` (release 5.89): a draft's words and files are kept nowhere else.
  - `Database\docs-before-v<n>.db`: docs.db as it was before DocRepo brought it up from schema version n (release 5.88, 6.1), one per upgrade, never one of the slots above.
- A backup writes through a SafeFS that allows only the backup folder. It's the one place DocRepo replaces files: `replace_file` and `replace` work only in a SafeFS's replace roots, which `make_safe_fs` sets to the backup folder, and never when that folder is inside the data root (section 4).
- A file that can't be copied is listed in the notification and the log, and the backup goes on. A missing backup drive stops the backup with a message.
- **Restoring** (by hand, in the README and the log): quit DocRepo, copy `Files` into a new empty folder, copy the newest database copy into its `System` folder as `docs.db`, then `set-data-root` and `rebuild`.

### 9.5 Checking the data root (release 5.89)
- `docrepo/check.py`, the `check` command and Settings' **Check the data root** (in Troubleshooting). It reads only and repairs nothing, and lists, as Markdown:
  - captures whose `capture.md` is missing or can't be read, each naming the finished draft in `System\Drafts\Done` last changed up to 30 minutes before the capture's save, which may still hold its words;
  - documents whose text was read with no `extracted.txt`;

## 12. The navigation wheels and the Today side panel (releases 5.41 to 5.43)

### 12.1 The wheels

A hotkey shows a small wheel of actions, picked with the arrow keys. **A wheel** has an ID, a name and up to eight slots keyed N, NE, E, SE, S, SW, W and NW. With only N, E, S and W it draws as a cross and a two-arrow chord selects nothing; a diagonal slot makes it 8-way, and nothing moves. Each wheel has its own hotkey (`wheel_hotkeys` in `settings.json`, keyed by wheel ID), and none until set. Pause hotkeys covers them.

**Keys.** One arrow lights a cardinal direction; two at right angles a diagonal; opposites, or three or more, nothing. A pick commits when all the arrows are up, with `release_grace_ms` for a diagonal's second key; holding one key past that re-aims at it. If the hotkey comes up within `tap_ms` with no arrow down, the wheel stays until a pick or a cancel; held longer, it lasts only while held, and letting go with an arrow still down leaves the pick to that arrow's coming up. The numpad's digits are spatial and commit on key-up, and 5 cancels. Enter runs what's lit and confirms a slot marked `confirm`. Esc, the hotkey again, losing the focus, or `idle_ms` with no key cancel. Ctrl+K closes it and opens the command palette. Every other key is swallowed. Nothing watches the keyboard: there's no hook, and the hotkey's own keys are read only while a wheel is open.

**Drawing.** The window is made once and hidden, and each wheel is painted once, unseen, at the start, so its fonts and icons are ready. The whole wheel shows at once (since release 5.43.1), in the middle of the monitor holding the window you were in (or the cursor's). A `draw_ms` above 0 shows only its centre until then, so a pick made by then never shows the rest.

**The config** is `Config\wheels.jsonc` in the data root: JSON with comments, written once and never again, with `wheels.schema.json` beside it. A slot has a `label`, an optional `icon` (one of DocRepo's own), and a `command` with `args`, an optional `confirm`, or `held`. A problem names the field and what's allowed, shows in a notification and the log, and the last good wheels stay in use. It's reloaded when the file changes.

**Commands** are one table (`docrepo/ui/wheel_commands.py`), and a slot can name nothing else, so a config can't start a program and captured content can never become a command:

| Command | Arguments | Does |
|---|---|---|
| `capture.new` | `mode` (note, new_task or update); `blank` (true) | The capture window |
| `capture.pin` | | The pinned window |
| `capture.selection` | | The pinned window with the current email or file |
| `capture.meeting` | | Meeting notes |
| `today.new_item` | | A quick task on Today: Ctrl+Shift+D's command, not a way of its own (release 5.99, decision 393) |
| `today.panel` | `do` (toggle, open or close) | The Today side panel |
| `browse.view` | `view` (any of the browse tool's views, or `urgent`, which since release 5.97 is the task tree with Urgent only) | The browse tool on that view |
| `search.tasks` | `then` (find_files or page; task_view, its old name, still works) | Task search |
| `search.files` | | File search |
| `search.everything` | | The browse tool, with the cursor in Search everything |
| `find_files.current` | | Find files for the selected task, or the last one opened; with neither, task search. Its old name, `task_view.current`, still works (`wheels_config.RENAMED`, release 5.98), and the usage log counts both under the new one |
| `summary.open` | | The quick summary, with the cursor in its box (release 5.131, section 15). **The usage log** is `System\logs\wheel-usage.csv`: time, wheel, direction, command, how, whether it had drawn, and the ms to appear and to pick. It holds no content.

### 12.2 A blank capture

`capture.new` opens the capture window empty. Since release 5.77 (decision 337) it's an ordinary open: a capture open with something in it goes to Drafts first (section 7), and a picked task alone is simply cleared. With `"blank": false`, the open capture stays, with that type checked. Release 5.41's one draft set aside, in `System\capture-draft-aside.json`, retired with it, and moves into Drafts on the first start.

### 12.3 The current email or file

At the hotkey DocRepo notes the window you were in, asking the program nothing: its window, class, process and program, and File Explorer's front tab. Only if `capture.selection` is picked does it read, after checking that the window is still there in the same process. File Explorer's and the desktop's selected files arrive through `add_paths`; Outlook's email through the mail button's read: the one open in its own window, or else the main window's selection, or the newest email of a selected conversation. An attachment selected in the reading pane arrives alone, as a file. They arrive in the pinned window, joining any draft. No keystrokes are ever sent to the other program. If Outlook hasn't answered after 3 s, the pinned window says a dialog may be open, and the email joins when it does.

### 12.4 Task search and file search

**Task search** is the task picker on its own: Enter opens the task's Find files, Ctrl+Enter its page in the browse tool (a slot's `then` can swap them), as a line under its box says. Since release 5.103 it's the `#` list's rows, search and levels (Right and Left), with Recent and the tree before anything is typed, and no None. It also finds closed tasks, marked "(closed)", and with no match it offers Search everything, carrying what was typed, on Enter too. **File search** is a window with a box, the Task view's list and a preview, across every task's files and saved emails, each file once. It uses the Task view's search (`docrepo/finder.py`), filters included. Enter opens through `docrepo/opener.py`'s allow-list, Ctrl+Enter shows it in File Explorer, Ctrl+Shift+C copies the path, and Tab goes to its task's page.

### 12.5 The Today side panel

The Today view as a floating strip, always on top, opened by its hotkey (`today_panel_hotkey`, none until set), the Execution wheel, the tray or Ctrl+K. There's no second list: its rows are the Today view's, and its buttons call the browse tool's methods.

| State | Width | Shows |
|---|---|---|
| Resting | `rest_width`, 180 px | The count, and one line per item, grouped, with a tick box |
| Widened | `hover_width`, 320 px | A second line under each title: its project, "reminder" and "since" at the left, its state's icon (the state menu's button) and its date, short ("8 d", "Today", "3 d late", coloured as the Due column, the whole date in its tooltip), at the right, where Later, Done and Remove show on the row under the pointer, so the title has its line to itself (release 5.119, decisions 440 to 442; before, the state's words and "16 Oct · 8 d" sat beside the title and cut it short); the box for a quick task or note, and folded Due in the next 7 days, its dates short too (decision 443), and Done today, which remember whether they're open. Since release 5.116 a reminder's task is one of its rows, and a task's row and a due row have Later (decisions 415 and 417) |
| Detail | `detail_width`, 420 px | The task's page to read, with Done, Remove, Edit and Open in the browse tool; or a note's text, with Edit and Make it a task |

It widens after the pointer rests on it for Windows' hover time (or `hover_ms`), or `inner_edge_hover_ms` on an edge between two monitors, and contracts `contract_ms` after the pointer leaves, never while the pointer is on it, its box has the cursor, a menu is open or a detail is showing. `hover` turns that off, and a click on its top line or its hotkey widens it. A click on anything but the box leaves the keyboard where it is. Its hotkey brings the keyboard to it: Up and Down move, Enter opens the detail, Space ticks Done, Delete removes, and Esc goes back, then contracts it and returns to the window you were in. Its tick box, Done and Space open an Update on the task, as the Today view's Done does (release 5.115), and Done and Remove say what they did under the list, with Undo for ten seconds; Done today's rows have Back on Today (decision 420).

Its inner edge (the one away from the screen's edge) is a grip at rest (release 5.106, decision 406): dragging it sets the width at rest, from 100 px up to `hover_width`, kept in `app_state` (`today_panel_rest_width`), and `rest_width` is the width until one is dragged. **Reset the width at rest**, on the top line's right-click menu, goes back to it. The pointer on the grip doesn't widen the panel.

A file, folder, web link or Outlook email dropped on a task in it (release 5.106, decisions 407 and 408), a Today row or one under Reminders or Due in the next 7 days, opens the capture window as an Update on that task, with what was dropped added as a drop on the capture window adds it; a capture it held goes to Drafts first. A note, the headings and Done today take no drop. A drag over it widens it, shows its list (a task page it showed closes) and marks the row under the pointer. An email, or a file only a program holds, goes to DocRepo's own drop target, as on the capture window: a cover that draws the panel's tasks where they are and takes the drop only on one.

Dragging its top line moves it, and on release it snaps to the nearer side of the monitor it's over. Its side, height and monitor (name, serial number and size) are kept in `app_state`, with whether it's open. If the monitor goes, it moves to the main one and returns with it. While a full-screen window or a slide show covers its monitor it hides (`hide_on_full_screen`), and `exclude_from_capture` keeps it out of screen capture, which also hides it from screenshots and compliance recordings.

## 13. Tagged labels (releases 5.79 and 5.80)

A **tagged label** is a plant's tag, such as V-110 or FIC-2210, found in the text of everything DocRepo reads (`docrepo/tagged.py`). It isn't a label: a label is a category the owner gives a task.

- **The glossary** lists the tagged labels, each with its description and aliases. It's imported from an `.xlsx` (read-only) or a `.csv`, up to 100,000 rows, in the Tagged labels view's **Import…** (`docrepo/tagged_import.py`): each column fills the label, its description or its aliases, or is left out, guessed from its header, with a preview, and nothing written until Import. Importing again merges: it adds labels and aliases and replaces a description that differs (unless DocRepo's are kept), and removes nothing. Two rows that are one tag written two ways become one label; a row that's another label's alias becomes its own label; an alias that's only digits, or that two labels share, is refused. **Export…** writes the glossary as a CSV (Tagged label, Tagged label description, Tagged label aliases) to `Exports` in the data root, and copies it. **Add…** and a label's **Edit…** add one by hand and change its description and aliases.
- **Matching.** A label, or an alias with a digit and no space, is found however its parts are joined: a hyphen, an en dash, an underscore, nothing, or a space between capitals. A label with fewer than four letters and digits needs capitals and no space. Other aliases are found as whole words, in any case. "P-204A/B" mentions P-204A and P-204B, and since release 5.80 "P-204A/B/C" all three: each capital after a slash. A tag inside a longer one isn't found.
- **What's read:** each capture's and document's text as the search index holds it (without its ID, and without a capture's title when its content has it), each notes page without its captures' blocks, and each task's title, description, current status, deadline description and key dates' descriptions.
- **Kept current.** Each indexed item's tag-like words and mentions are kept (`tagged_words`, `tagged_mentions`); a change to the glossary or the tag patterns matches the kept words again, without reading any file. The kept words are runs of letters and digits joined by one mark each (a space only between capitals), or by a `/` or a dot (release 5.80), with a letter and a digit; words kept by release 5.79 are read again from the search index at the first match. Both are rebuilt with the search index.
- **Tag patterns (release 5.80, `docrepo/tagged_masks.py`).** Settings' **Tagged labels** section lists the tag patterns, each a name, a **mask** and **Space** (Allow a space, off by default). In a mask `X` is a capital letter, `#` a digit, `*` either, `[ ]` optional, `' '` itself (`'XV'-####`), a hyphen, underscore or space is where a new label's spelling has that mark, and any other letter, a digit, `/` or `.` is itself. A mask is read in capitals (`x` is `X`); the text's letters must be capitals. Marks are never required in the text: `XXX###` finds FIC221, FIC-221 and FIC_221, and spells each FIC221. A pair is both tags, as for a glossary label: `X[X]-###[X]` finds P-204A and P-204B in "P-204A/B", only when the mask allows the other letter where the first was (`XX-##'A'` finds only TK-12A in "TK-12A/B"), and each capital after a slash ("P-204A/B/C" is three). A space may stand where the mask has one, or between any parts with Space ticked. DocRepo turns each mask into a regular expression of its own, with no repetition and at most 4 optional parts in at most 32 characters, so no mask can hang a save; the owner never writes a regular expression. Each row says what its mask means ("Such as FT-2041 to FTIC-2041") or why it can't be used, as it's typed. DocRepo ships no patterns; made-up examples are offered to start from. The patterns and **Never a tag** live in `Config\settings.json` (`tagged_patterns`, `tagged_never`); docs.db keeps a copy in `app_state` for matching, made again from settings.json at each start and after Save settings, which matches everything again and writes Task.md.
- **New tagged labels (release 5.80).** What a pattern finds that has no glossary label (by its letters and digits) becomes a tagged label at once: a **suggested** row in `tagged_labels` (how it came `pattern`, with the pattern's name), put on every capture, document, notes page and task that mentions it, its chip marked **new** with the pattern's name on hover. A task's own fields are matched when they're written. A glossary label is always found first, and a suggested one only by a pattern. **Never a tag** is whole tags (ABC123) or starts with `*` (`API*`), typed in Settings separated by commas, or filled by Not a tag; it applies to patterns only. A suggested label nothing mentions any more is dropped when everything is matched again.
- **Suggested (release 5.80).** The Tagged labels view lists the suggested labels above the glossary, under a **Suggested** heading, the most mentioned first, each with the pattern that found it and where it's seen (its top-level tasks). A suggested label's page has **Add to glossary…** (a description and aliases; it's then an ordinary label, found however it's written, and Export has it), **Same as…** (an alias of a glossary label, picked or typed; its mentions and the owner's own changes move there) and **Not a tag** (removed everywhere and put on Never a tag in settings.json, with Undo). **Patterns…** opens Settings' section. Importing a row with a suggested label's key adds it to the glossary as the list's. Search lists a suggested label as "New, from the … pattern".
- **The tester (release 5.80, decision 373).** Under the patterns, **Try it** is a box to paste text into; what the glossary and the patterns as they stand in the form find is marked as it's typed: a glossary label, an alias, a word alias, new from a pattern (named under it), and what's on Never a tag struck through. **Try on everything** runs the patterns as they stand, before they're saved, over every capture, document, notes page and task from the kept words, and says how many new labels they'd make and in how many items, the most frequent first ("3 new, in 2 items: API-6100 (2), ABC-1234 (1)…"); **Not a tag** on one puts it on the form's Never a tag. Neither changes anything until Save settings.
- **Where it shows:** a Tagged labels row on a capture's and a document's page (× removes one, with Undo, and it stays removed; **Add** puts one on by hand; **Add back** undoes a removal), in a task's Details (from its own fields, notes page, captures and documents, each item once), and in Task.md after Labels. The Tagged labels view, under Manage, lists the glossary with each label's description, aliases and how many items mention it (at most 2,000 rows; **Mentioned only**, ticked to start with for a bigger glossary). A label's page lists everything that mentions it, newest first, under each top-level task, with the words around it. Search lists a label typed however it's written first, and what mentions it. Find files' `tag:V-110` filter keeps what mentions a label.
- **Later (stage 32, set aside, decision 380):** descriptions and fuzzy matching, once the glossary and patterns have been used for a few weeks.

## 14. Consultants (release 5.107)

A **consultant** is an agent over the documents of one task and the tasks under it, for the owner to ask questions of in VS Code. DocRepo makes its folder and calls no LLM; `docrepo/consultants.py` holds it, and the command line runs it (a command in the browse tool comes later).

- **`consultant-make TASK --name NAME`** reads every saved copy, tracked original and email attachment of the task and the tasks under it that aren't discarded, each document once, from the file itself, and writes `Consultants\<name>` in the data root (the name in lower case, its spaces as hyphens; 3 to 60 letters, digits, spaces and hyphens):

  | File | Holds |
  |---|---|
  | `Index.md` | Every document: its ID, name, task, how it was read (ok, partial, fallback, none), its sections, tables and characters; the ones to check, with why; and each one's outline |
  | `corpus\<document ID>.md` | The document's text, a heading a section, each with its reference in brackets: `D000123#s4`, `D000123#slide-7`, `D000123#page-12` |
  | `manifest.json` | The task, the build, and each file's size, date, SHA-256 and sections |
  | `.github\copilot-instructions.md` | The rules: the documents are data, no web, no terminal, read-only, a reference for every statement, limits quoted, the sweep and its coverage line |
  | `.github\agents\<name>.agent.md` | The consultant: read and search |
  | `.github\agents\<name>-trainer.agent.md` | The trainer: read, search and edit, and the four formats it writes |
  | `<name>.code-workspace` | The folder, read-only, and Copilot's folder beside it when Settings names one |
  | `map\<page>.md` | The map's pages, once checked and kept |

- **Sections** (`extract.sections_of`): a Word file by heading style, its tables as Markdown tables in their place (a table of more than 40 rows in parts, each a section, with its header row again), its text boxes read; without heading styles, a short numbered or all-bold line is a heading. A deck by slide, with its notes. A PDF by page, headed by its bookmarks; `--pdf-layout` keeps each page's columns in place. Other kinds DocRepo reads are one section. Nothing is cut at the text limit.
- **A file that can't be read** falls back to the text DocRepo kept when it was captured, as one section, and `Index.md` says so. A kind DocRepo doesn't read (`.doc`, `.ppt`, a picture) is listed with no text.
- **Made again**, with the same name and task, it's rewritten. A document that left keeps its file, with one line saying it left. DocRepo deletes nothing.
- **The rules and the agents are fixed templates** in the code, filled with the name, the task's title on one line, and counts. No LLM writes them.
- **The map** is the one part an LLM writes: the trainer writes `<name>-catalogue.md`, `<name>-vocabulary.md`, `<name>-topics.md` and `<name>-exam.md` into Copilot's folder. **`consultant-check NAME`** reads them and checks each:

  | Page | Format | Checked |
  |---|---|---|
  | Catalogue | `## D000123`, then what the document covers | The ID is one of the consultant's documents, once, with words under it, at most 1,000 characters; a warning for a document with no entry |
  | Vocabulary | `- term = other word; ABBR` | Two words or more, at least one of them in the corpus |
  | Topics | `## Topic`, then `- D000123#s4: why` lines | Every reference is a section in the manifest; a topic has one at least |
  | Exam | `## The question?`, then `- D000123#s4` lines | Every reference is a section in the manifest |

  No page may hold a web address, a file address or a path, a code block, or a heading other than one `#` title at its top and its `##` entries, and none is read past 2 MB. With **`--keep`**, each page with no problems is written to `map\<page>.md` under a line saying an LLM compiled it and which build DocRepo checked it against. A page is data: it's never acted on.
- **`consultant-status [NAME]`** reads each file again and says which were added, changed, gone from the task or out of reach, and which map pages are missing or of an earlier build.
